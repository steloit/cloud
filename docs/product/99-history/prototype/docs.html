Concept · How Steloit is organized

Everything lives in a project. A project has environments (production, staging, previews); an environment has services; services connect through bindings. The region belongs to the environment, and identity belongs to the organization. If you remember one sentence: the URL is the state — org/project/environment reads left to right, exactly like the CLI's context.

Concept · How estimates work

Anything that changes what you pay shows the number before you confirm, marked with ~ because it's honest about being an estimate. If Steloit can't produce an estimate, it won't let you create the thing — no estimate, no create (E-EST-503). Actual spend never wears the tilde.

Concept · How recommendations work

AI recommendations are proposals, not actions. Each one shows its reasons as evidence quoted verbatim from your own description or telemetry, its cost, and toggles you control. Low-confidence items default to off. The assistant answers questions and links to real surfaces; it never executes anything itself.

Concept · Topology

The topology view draws your environment as it actually is: services as nodes, bindings as edges, the connected app at the top. Healthy nodes stay visually quiet; only degraded, provisioning, or suspended states color the ring. It's a map, not a dashboard — click any node to operate on it.

Concept · Branching

A PostgreSQL branch is a copy-on-write copy of your database at a moment in time. Creating one is instant and costs cents per day, growing only with divergence from the parent. Branches power safe experiments, point-in-time restores (restores always land on a new branch), and — in v2 — preview environments that give every pull request production-shaped data with zero production risk.

Concept · Queues & DLQ

Delivery is at-least-once: your handlers must be idempotent. Messages that fail repeatedly move to the dead-letter queue instead of vanishing; inspect them, fix the cause, then redrive. A non-empty DLQ is a signal worth an alert — one exists by default.

Task · Create a project

Console: New project → name it → pick services (or describe your app and review the AI's proposal) → check the estimate → create. CLI: steloit init asks the same questions in the same order. Both end at the same place: a provisioning environment and a connect step.

Task · Connect your app

Run steloit env pull in your app directory. It writes .env.steloit with connection URLs and secrets for the current environment, and updates them when things rotate. Manually copied credentials don't update — the Console warns you every time you reveal one (C-41).

Task · Delete safely

Reversible things are easy; irreversible things are deliberately slow. Archiving is one confirm. Destroying an environment types its name and waits 72 hours. Destroying a project types its slug and waits 7 days, cancellable the whole time. Production environments cannot be destroyed while marked production — demote first (C-38).

Task · Working with context

The bar at the top isn't breadcrumbs — it's the working context, same as steloit ctx. Switching environment never navigates away; it re-filters the page you're on. [ and ] cycle environments from the keyboard. If the current page has no meaning in the target environment, you land on Services with a note.

Runbook · Valkey memory pressure

Symptoms: hit rate falls, evictions exceed 5%/min, state shows degraded. Check the Keyspaces tab for patterns without TTLs — unbounded keyspaces are the usual cause. Fixes, in order of preference: add TTLs to unbounded patterns; flush stale fixture data (typed confirm); raise the size one step — the new monthly price is shown before you confirm. The staging cache in this prototype demonstrates the full scenario.
