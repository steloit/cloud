# Decision log (ADRs)

Append-only register of load-bearing decisions: what was decided, what lost, why, and where it's visible — so nothing gets relitigated by someone (or some agent) who wasn't there. Entries are extracted from the design spec's on-the-record reversals, GOV-002, and the `99-history/` program docs; new entries are added going forward, and **constitution amendments land here too** (18-philosophy §How-this-document-is-used).

Format: **Decision · Context & alternatives · Why · Consequences · Refs**. Status is `accepted` unless marked. Dates before Jul 2026 are era-level.

---

## Era 1 — Architecture (GOV-002)

**ADR-001 · Nine primitives, and Workspace is not one of them.** Considered a Workspace level between Org and Project (as some platforms have); rejected — 95% of customers never need it and it muddies "create a project." Folders + labels + Teams + Policies compose the same outcome; the hierarchy deliberately leaves the slot open if enterprise scale ever demands it. *Consequence:* pressure to add a primitive is a signal to think harder, never a casual extension. → GOV-002 §1.2

**ADR-002 · The Project is the atom.** Infrastructure organized around applications, not service types — the platform's core bet. Everything (provisioning, cost, permissions, deletion) rolls up to a Project. *Consequence:* the first-deploy story is "deploy your app," not "buy a database." → GOV-002 §0, §1.1

**ADR-003 · Never build: IaaS, CI/CD, comms infra, low-code.** The boundary heuristic: build where fragmentation is the pain, integrate where ecosystems have gravity, never sell undifferentiated infrastructure. Kubernetes is an internal detail (Cells), never a product. → GOV-002 §3.7–3.8

**ADR-004 · Region is an environment property; provider is a facet of region.** Alternatives: per-service region dropdown (normalizes accidental cross-region topologies), provider as a second axis (forks the UX per cloud). Environment sets the home region; instances inherit; overrides are explicit, priced exceptions (C7); multi-region production = more environments. *Consequence:* BYOC later slotted in as "ownership is a facet too" with zero new structure. → GOV-002 §2.2 · spec §Region model · X2–X3

**ADR-005 · The four AI laws are permanent.** Suggest-never-act · explainable with evidence · read broadly act within permissions · platform whole without AI. No auto-apply path exists in the API by design, not by policy. *Consequence:* every AI feature everywhere is a proposal object; the `ai-assistant` org policy can remove the layer cleanly. → GOV-002 §7 · 12-ai/

**ADR-006 · Expand/deepen release rhythm; data before compute.** Integer versions change what Steloit *is*, halves make it excellent; never two expansions in a row. Compute ships fourth (v2), not first — data services earn trust while the harder problem is built. → GOV-002 §8

## Era 3 — The console spec (LATTICE, 152 frames)

**ADR-011 · The shell is rail + product sidebar (Dub pattern), not GOV-002 §4.2's two-section sidebar.** Three variants explored. The rail renders only the project's actual products (the app's silhouette), the second sidebar is the selected product's workspace, service tab rows retired. *Consequence:* GOV-002's IA sketch is superseded where they differ — the design spec is the later, binding refinement. → spec §Chosen shell

**ADR-012 · No Organization rail item; org admin lives in settings mode behind the gear.** Org concerns are low-frequency admin; account settings deliberately hang off the avatar instead (a person spans orgs; MFA/sessions/tokens must not live inside any one of them). → spec §Chosen shell

**ADR-013 · Environment is a filter, not a container or dimension.** Three models weighed (filter / AWS-style container / dimension). Filter wins with the refinement *shape is per-project; presence and scale are per-environment*; the rail never reshuffles on env switch; the Environments page is a parity matrix. *(extended: ADR-037 — implicit-by-default)* → spec §M3

**ADR-014 · Create is one surface, not a dialog + per-product pages.** The dialog was defended as "a router, not a workspace" — held until `+` became a lit rail item; a rail destination owns a surface. C2/C3/C9–C12 are *states* of C1. Three doors, one room. → spec §C1 (revision on record)

**ADR-015 · Tier-2 creation chrome keeps the rail.** Began as fully-stripped "creation-as-checkout" chrome; once the canvas shape existed, stripping the rail lost its justification. The checkout signal survives in what's absent: no sidebar, no bell. → spec §Consistency contract

**ADR-016 · Dashboards live under Home — not under Observe, not a rail item.** Observe nesting broke on cross-plane widgets (a parent that doesn't own its child's data); a rail slot taxes the jump-to-the-thing persona and creates a "Home or Dashboards?" decision tax. Single door: reached from Home only. Scope (org|project) is orthogonal to visibility. → spec §Dashboards (reversal on record)

**ADR-017 · Observe and Deploy are the only rail domains besides Home.** Rail admission = weight × frequency; the two are the console's verbs (*watch it*, *ship it*). Environments evaluated and kept off — its everyday presence is the crumb; the manager is reached through the filter (env menu → ⚙). Insights can never be a rail item (Law 4: it must vanish cleanly). → spec §Observe suite, §AI

**ADR-018 · The project sidebar is dissolved; Tier-1 has two shapes.** After Settings went behind the gear and Deploy to the rail, Home held one destination — a one-item sidebar is pure chrome. Domain shape (rail item + sidebar) vs canvas shape (full-width page). → spec §Project surface

**ADR-019 · Interaction tiers are a decided rule; inline forms are prohibited.** Modal (≤4 fields / one decision, typed-confirm escalation) · drawer (previews, live checks) · page (multi-step/provisioning). A full census of all 152 frames found and fixed six inline-form violations. → 06-interactions/ · spec §Interaction tiers

**ADR-020 · Assistant in the chrome, not a FAB; ⌘K imperative, assistant interrogative.** A floating bubble is the archetypal bolted-on chatbot and context-blind. Top-nav violet button (⌘J) → context-scoped drawer ⇄ full workspace, one conversation at two sizes. → spec §AI access

**ADR-021 · Templates copy, never link; secrets never captured.** Editing/deleting a template never touches instantiations; credentials re-mint per consumer; excluded-service bindings become required inputs. Estimate-before-provision extends to a template's birth. → spec §Templates · F8

**ADR-022 · Hybrid pricing; BYOC at Business+ (deliberate deviation, flagged).** Subscription = platform capabilities, pay-as-you-go = infrastructure, overage = beyond quotas. The brief placed BYOC at Enterprise; the console places cells at Business+ (a metered capability, not a contract feature) — Enterprise keeps dedicated cells, audit export, SLA. Gateway *tokens* are infra; assistant *requests* are a platform quota. → spec §Subscription experience · F9

**ADR-041 · Pricing model finalized: product-first presentation; in-database capabilities included (not unlimited); Pro is $29.** Amends ADR-022 (hybrid model) per ADR-039 §4c and the catalog-structure research review (refinement 1, evidence-backed; docs/plan/catalog-structure-review.md). **Presentation:** every product priced by its natural meter, labeled by outcome via the `intent` tag, expanding exactly — product line → cost components → meter rows; the generalized exact-sum invariant; terminal condition: published unit price × metered quantity or a stated plan allowance, nothing else exists; usage ranges honest and bounded by the cap. **Included capabilities:** Jobs (incl. scheduling), basic Search, and Vector are capabilities of the customer's Database — included at no separate line within **reasonable plan allowances** (included, not unlimited), consuming the database's already-priced capacity; the P4 canon ruling demonstrates the model (Jobs = a $21 Dev Postgres, the capability free on it). **ADR-040 · The Developer-First Platform: four planes, extensible execution models, the semantic-contract invariant; architecture stable from here.** Constitutional review (founder-requested 2026-07-18; full analysis: docs/plan/developer-first-review.md, companion review reconciled in its §7). **The principle, promoted from UX law to constitutional organizing rule: developers buy outcomes; infrastructure serves the developer experience and never defines it.** The platform is four planes: **Products** (catalog intents) → **Execution Models** (Composer resolutions) → **Infrastructure** (the State Test; enum unchanged) → **Platform Capabilities** (the governed-resource contract). **Execution models are an extensible concept, never a closed list:** *a Product declares developer intent; the Composer resolves that intent into one or more execution models; execution models may evolve without changing the Product abstraction, provided the semantic contract is preserved or a new semantic variant is introduced* (today's four — in-database capability · dedicated service · shared platform service · external binding — are instances, not the definition). **Core invariant: execution models are replaceable; semantic contracts are not.** The Composer proposes and prices, never silently decides; execution-model migrations are visible, priced, consented. **Catalog v1 is a presentation re-front of ratified surface only** — App · Database—PostgreSQL (an infra name may be a catalog entry when it *is* the outcome; no entry exists *because* the infra exists) · Jobs · Search · Vector · Cache · Storage (Binding) · AI (Binding; A5.4 stands). Roadmap intents (Feature Flags · Auth [= customer end-user auth, v4, distinct from org identity/ADR-0006] · Realtime · Analytics · Streams) enter only through the gate, on evidence, against the **pre-registered M4 pivot checkpoint** (partner questions written now: certainty demo vs feature-shopping · outcomes vs infrastructure · "a Postgres appears when you ask for Jobs" · unprompted comparisons · do they ask to connect an existing RDS). **The Developer-First test** prepends the gate: what developer problem does this solve? · Product, Capability, Binding, or Infrastructure Service? · which execution model gives the best DX? · does it strengthen the certainty story? **Stability clause:** from this ADR forward, architecture changes only on implementation, performance, customer, or security evidence — *a cleaner abstraction is never a trigger.* **Review order (standing):** developer experience first, implementation simplicity second, architectural elegance third; reviews default to implementation thinking. Nothing frozen moves. Next phase: the Composer, the estimate flow, and partner validation. Founder-ratified. (2026-07-18) → ADR-038/039 *(promoted)* · ADR-0001 *(trigger rule extended)*

**ADR-039 · The two-plane rule + product-first pricing: the catalog sells outcomes; architecture stays true.** Founder refinements to ADR-038 (2026-07-18), ratified. **Architecture answers "what is this?" (the State Test); the catalog answers "what problem does this solve?" (intents); the planes never leak.** The catalog plane is flat and outcome-first — Jobs/Search/Vector are catalog peers of PostgreSQL; a catalog entry is an intent, not a product identity; the customer buys the managed experience, the backing is the Composer's concern. **The bridge:** the Composer fans an intent out to *named resolutions with stated semantics — never backend dropdowns* — and the **accepted estimate is the reconciliation contract** between the planes (estimate-before-provision extended to semantics); "backend" is never a customer-facing word; nothing named for an outcome ever silently changes semantics. **Pricing:** label by outcome, account by cost components — product line → cost components → meter rows, same numbers at every level; the generalized exact-sum invariant (*every price is completely explainable and expands to its underlying cost model without hidden arithmetic*); every line is a metered quantity at a published unit price or a stated plan allowance, nothing else exists; ranges honest and bounded by the cap; mechanism = the `intent` tag stamped by the Composer at creation. Full text: docs/plan/product-taxonomy-review.md §4b–4c. Founder-ratified. (2026-07-18) → ADR-038 *(extended)* · F9 · B3

**ADR-038 · The State Test is the canonical product classifier; the product taxonomy is frozen.** Founder challenge (2026-07-18): are Jobs/Search/Vector Postgres capabilities or independent products whose MVP happens to use Postgres? Resolution — neither model as posed; the dependency is *semantic*, not implementational. **The State Test:** a thing is a **Service** iff its state has an independent lifecycle and isolation/scaling boundary · a **Capability** iff its state is *of* a parent service (branches, backs up, joins, transacts with the parent's data) · a **Binding** iff its state lives outside the platform. **Why state decides:** *lifecycle, backup, branching, scaling, permissions, billing, and ownership all ultimately follow state — therefore the location and ownership of state, not implementation or UI, is the canonical classifier for every managed product.* Applied: Jobs/Search/Vector are Postgres **capabilities** because their differentiated semantics (transactional enqueue, branch-coherence, joins with application data) only exist inside the customer's database — the coupling is product truth, not MVP accident (the MongoDB-Atlas precedent: capability-of-the-database wins even when the internal engine differs; the abstraction seam lives *inside* the capability). **Scope clause: Jobs ≠ Messaging** — Jobs is database-native background execution, exactly; event streaming (log-as-state: retention, replay, ordering, consumer groups) is a separate category that passes the State Test as a Service in its own right; if demand arrives the ladder is Messaging **Binding** first (their Confluent/MSK/EventBridge — integrate where ecosystems have gravity), a managed **Streams** service only on evidence, always under its own name and ADR; "Jobs" is never backend-swapped to a broker (A5.2's no-broker strike scoped precisely: it governs the queue, never a future named streaming product). **UX law:** the catalog sells intents ("Jobs", "Vector", "Search"); the composer (C1/AI1) resolves them to shaped services with the estimate shown — dependencies satisfied by composition, never surfaced as homework or error. Model B rejected on the record (swap-optionality is an illusion that forfeits differentiated semantics to the lowest common denominator; re-opens ADR-0004's dead-category evidence; adopts the AWS fragmentation taxonomy). **From this point forward every proposed product begins by answering the State Test before any implementation discussion; it is the first question of the new-managed-product gate.** Full analysis: `steloit/cloud` docs/plan/product-taxonomy-review.md. Founder-ratified. (2026-07-18) → ADR-0004 *(confirmed)* · GOV-002 §3.8

**ADR-037 · Resource model confirmed; Environment implicit-by-default; production is a stable identity, not a deployment state.** The org→project→environment→service hierarchy was adversarially reviewed and **confirmed unchanged** (13-platform evidence: the model is the convergent target flat platforms migrate toward — full analysis `steloit/cloud` docs/plan/resource-model-review.md, incl. the canonical ownership matrix and inheritance table; reaffirms ADR-001/002/013). Its one contested layer was then challenged directly: "does Environment deserve to exist?" — attacked with a 13-platform evidence sweep; the flat alternative (project-per-env) loses decisively (every flat platform re-added the layer: Heroku Pipelines 2016, Render Projects/Environments 2023, Supabase Branching 2024; Fly's holdout costs separate orgs + duplicated config; flat structurally breaks the per-PR-preview wedge, the one-application-cost rollup, and app-level RBAC). Verdict: **keep Environment first-class in the model, make it implicit in the UX** — the Vercel-validated sweet spot. Full UX spec ratified (`steloit/cloud` docs/plan/implicit-environment-ux.md): **six laws** — born not created · implicit ≠ anonymous · presentation-layer only · one reveal rule (envs ≥ 2 ∨ previews, everywhere at once, coachmark once) · URLs never change shape (omitted `?env=` = production forever) · the reveal is lossless (history env-labeled from birth). Second challenge — the birth name: `production` re-ratified under attack; the key insight: **production is a stable identity, not a deployment state** — its strictness is *relational* (every guardrail the word implies is a policy meaningful only relative to another environment; at n=1 the name carries no behavioral semantics). Definition entered in the glossary: *"the primary instance of a project — the one others branch from and the one policies protect; not 'publicly launched.'"* Rejected on the record: `default` (forces a future rename), `development` (wrong migration path), unnamed/system (violates implicit ≠ anonymous), role-flip-on-first-deploy (deploys never mutate governance), `main` (right for branches, wrong for deploy targets). **Environment rename** added as an explicit capability (PATCH /envs — S-process) instead of role magic. Frame variants for the n=1 state = ruling S10. The Environment model and its UX are **frozen**; further changes only from real customer feedback during implementation and design-partner validation. Founder-ratified. (2026-07-18) → ADR-013 *(extended)* · docs/plan/implicit-environment-ux.md

**ADR-036 · Identity & Governance confirmed + codified — the governed-resource contract (ADR-0006).** Adversarial review (founder-requested, two evidence sweeps 2026-07-18; full analysis `steloit/cloud` docs/plan/identity-governance-review.md + docs/adr/0006-identity-governance.md). Outcome: **confirm, don't redesign.** Identity, authZ, policy, and audit are designed once and inherited by every managed product and Binding via the **governed-resource contract** — a product is *governed* iff it is a resource in the org→project→env tree, declares `resource.action` permissions, routes mutations through the two-layer evaluator, and emits lifecycle events to the append-only spine (a depguard-enforced module boundary, not aspiration). **No product/Binding/module may implement its own authN/authZ/policy/audit — all use the contract; any exception requires a new ADR.** Kept: RBAC + a narrowing-policy overlay (the AWS Organizations SCP model — matrix grants a ceiling, policy can only narrow, composing as intersection down the tree); owned identity + libraries for authN primitives (`go-webauthn`/argon2id/TOTP, passkeys-first); the events spine as the single audit source; fixed roles (custom roles = new matrix columns, v3); centralized in the identity module (not a separate service). Rejected: ReBAC/Zanzibar (graph engine for a tree; separate stateful service — overkill), buying auth (Clerk/Auth0/Cognito as primary store — SaaS in the trust path). Clarified: policy = typed-Go evaluator over the finite platform set, Cedar reserved for v3 customer-authored policies; "why was this denied" explainability load-bearing; SSO/SCIM = WorkOS at v3 (federates into our model), priced honestly (anti-SSO-tax). **Net-new: CI/OIDC workload-identity federation (V2)** — Steloit as an OIDC relying party so machines federate into scoped short-lived tokens with zero stored keys, mapped onto the tree via OIDC claims. Founder-ratified. (2026-07-18) → docs/adr/0006-identity-governance.md

**ADR-035 · BYOC review — Enterprise-only, V3, exit-criteria-gated; ADR-022 refined.** Adversarial first-principles review (founder-requested, evidence sweep 2026-07-18; full analysis `steloit/cloud` docs/plan/byoc-review.md + docs/adr/0005-byoc.md). Outcome: BYOC (data plane in the customer's own account) is **not part of the wedge**, remains an **Enterprise-only V3 capability**, and **no BYOC-specific machinery is built until five exit criteria all hold** (signed contract requiring in-account deployment · the deal funds the fully-loaded first-year build+ops+security-review · sovereignty provably un-substitutable by regional cell/dedicated cell/PrivateLink/BYOK · single named cloud, AWS-first, no multi-cloud abstraction until a second signed deal · security model in funded scope). **Refines ADR-022:** distinguish *regional/dedicated cells* (Steloit's account, customer's region — residency + single-tenant isolation, a Business+ metered capability) from *true cross-account BYOC* (data plane in the customer's own account — sovereignty, Enterprise, contract-gated). Canonical routing policy (residency → regional cell; network isolation → PrivateLink; keys → BYOK; only contractually-required sovereignty meeting all exit criteria → BYOC) is the standard for qualifying enterprise requests. Founder-ratified. (2026-07-18) → docs/adr/0005-byoc.md
