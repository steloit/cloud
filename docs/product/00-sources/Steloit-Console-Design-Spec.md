# Steloit Console — Design Specification
### LATTICE Design System + High-Fidelity Screen Designs
**Version 1.1** · Grounded solely in **GOV-002 — Steloit Product Architecture Specification**
**Deliverable pair:** this spec + `Steloit-Console-Screens.html` (12 hi-fi frames, 1440×900, dark & light)

---

## 0. Design Position

The Console is the third client of the API (after the API itself and the CLI), and the first thing most humans will judge. Its design brief comes straight from GOV-002: *the product's structure must teach its philosophy.* Every design decision below is traceable to one of the architecture's tests — five-minute, one-grammar, topology, trust, coherence.

Three design consequences follow:

1. **Dark-first, calm, engineered.** Steloit's audience lives in terminals and editors. The Console defaults to a dark theme tuned for long sessions and log-reading, with a full light theme as a first-class toggle (both ship at v0.5; neither is an afterthought).
2. **The hierarchy is always on screen.** Org → Project → Environment appears in a persistent context bar; it is the answer to "what am I looking at," the mirror of `--project/--env`, and the spine of every URL.
3. **One anatomy, everywhere.** The service page anatomy (GOV-002 §4.3's page contract) is a *design-system component*, not a page design. New service types compose it; they don't redesign it.

## 1. LATTICE — the design system

Named for the platform's internal truth: Cells compose into a lattice. The system's job is to make nine primitives and six product families feel like one machine.

**Light** mirrors the ramp (`#F6F8FA` canvas, `#FFFFFF` surface, ink `#1A2129/#57606A/#8B949E`), same accent hues darkened one step for AA contrast. Theme = class toggle; tokens only, zero component forks.

### 1.2 Status language (the one meaning of "green")

Color never carries state alone:

| State | Dot | Motion |
|---|---|---|
| `ready` | solid `--ok` dot | none |
| `provisioning` | dashed `--prov` ring | slow rotation |
| `degraded` | solid `--warn` dot + label | none |
| `failed / alerting` | solid `--err` dot | single pulse on entry |
| `suspended` | hollow `--ink3` ring | none |
| `deleting` | solid dot at 40% | fade |

The same six marks appear in the topology map, service lists, context bar, CLI (`✓ ◌ ! ✕ ○ ·`), and status page. This table *is* the platform's health vocabulary.

### 1.3 Typography

- **UI:** Inter — 13px base (console density), 13.5 body, 15/600 card titles, 20/600 page titles, 24/600 page heroes. Tracking −1% above 20px.
- **Data:** JetBrains Mono for everything a developer might copy: IDs, slugs, URLs, env vars, log lines, SQL, costs in tables. If it can be pasted into a terminal, it is mono. This single rule does more for "developer-grade" feel than any decoration.
- Numbers in tables: tabular figures always.

### 1.4 Iconography & the primitive glyphs

1.5px stroke, 20px grid. Each primitive owns a permanent glyph: Organization (concentric ring), Project (hexagon — the lattice cell), Environment (layered squares), Service (circuit node), Deployment (tagged arrow), Binding (linked nodes), Secret (key), Policy (shield-rule), Event (pulse line). Service *categories* get type glyphs (database cylinder, memory chip, bucket, queue stack, globe-server, gear-worker, clock-cron). The topology map, sidebar, ⌘K results, and CLI help all draw from this one set.

### 1.5 Component inventory (marketing of none, function of all)

Context bar · sidebar (two sections: PROJECT / ORGANIZATION, exactly GOV-002 §4.2) · service card · **topology map** (nodes+bindings, the coherence proof) · service page shell (tab contract) · metric sparkline & chart grid · **log well** (mono, live-tail affordance, one query grammar hint) · event/timeline row · **proposal card** (the AI artifact — see §3) · cost meter (estimate vs actual, always paired) · binding pill · env switcher (filter, not navigation) · deployment row (immutable: id, git sha, actor, state) · diff block (promotion) · policy row (attachment level badge) · empty states (every list ships one, with the CLI command that fills it) · danger zone (red hairline, type-to-confirm) · toast (bottom-right, never blocking).

### 1.6 Motion

120–200ms ease-out, functional only: provisioning rings rotate; live log tail slides; topology edges draw on first render; deployment promotion animates the diff header; AI proposal cards *never* animate in (they wait — human attention comes to them, per the four laws' spirit). `prefers-reduced-motion` collapses everything to state swaps.

### The chosen shell — product rail + product sidebar (frames D1–D3)

After exploring three variants, the decided shell is the Dub pattern with Steloit semantics:

- **Context bar (top, unchanged):** Org / Project / Environment — the spine. It answers *which instance*, which is what lets the product sidebar go straight to tools instead of instance lists.
- **First sidebar (rail):** all products — Project home (hex), then PostgreSQL, Valkey, Object Storage, Queue, Web services, Workers; Organization and Docs at the bottom. Selecting a product resolves to that project+environment's instance of it (a header dropdown in the second sidebar switches instances when a project has several).
- **Second sidebar:** the selected product's workspace, in three groups — top-level (Overview, Metrics, Logs — the shared grammar), **Browse** (the data tools), and **Manage** (Branches, Backups, Bindings, Settings). A footer shows this service's cost against the project total (§6.5).

**The Browse group per product** (the type-specific tools, GOV-002 §4.3's type-tab slot, promoted to a sidebar section):
PostgreSQL → SQL Editor, Table Viewer, Query Insights · Valkey → Data Browser (keys), CLI Console · Object Storage → Object Browser (buckets/files, signed-URL generator) · Queue → Message Browser, DLQ Inspector · Compute → Deployments, Shell.

Safety grammar carried into the tools: editors run under the caller's **binding role** (readonly by default), the SQL Editor's target selector makes running on a **branch** one dropdown, writes require read-write and land in the audit stream, and the assistant surfaces inside the tools as proposals only (D1 shows the index-opportunity chip).

**All frames run on this shell** (as later evolved — see the structure-audit and Observe/Deploy sections for the final IA): the project overview is a sidebar-less canvas under Home; Observe (O1–O6) and Deploy (DP1–DP3) are rail domains with their own sidebars; PostgreSQL pages (Overview, Branches, Query Insights, and the D-series Browse tools) live under the database rail item. Service tab rows are retired — the product sidebar replaced them.

**There is no Organization rail item.** Org concerns are low-frequency admin, so they live in a **Settings mode** (Dub pattern): the gear at the rail's bottom swaps the second sidebar for a settings navigation with a back chevron and three groups mapping exactly to GOV-002 §4.6's levels — **Project · ecommerce** (General, Members & roles, Git integration, Policies), **Organization · Acme** (General, Members, Billing & usage, Audit log, Policies, API keys), **Account settings are deliberately not here**: they hang off the profile avatar (frames P1–P2) because they belong to the human, not the tenancy — a person may sit in several organizations, and their MFA, sessions and personal tokens must not live inside any one of them. The §4.6 guardrail holds: environment- and service-level settings (scaling, exposure, danger zones) stay on their service pages in the Manage group — context beats catalog. The **Projects home** is not admin and not in Settings: it is the app's front door, reached from the Home rail item and the context bar's org/project switcher; its second sidebar is the project switcher itself (all projects with health dots, plus New project).

What keeps this GOV-002-clean: products in the rail are *lenses over the current context*, never context-free homes — the project remains the unit of creation, cost, promotion and deletion, and the Project-home rail item retains topology, deployments and Observe.

### Resource-model refinements (frames M1–M3)

Three rules, forced by real projects and now normative for the shell:

**1. The rail is the project's shape — never a catalog (M1).** It renders only the product types this project actually uses, plus a dashed `+` to grow it. A Postgres-and-Storage project shows two icons; an empty project shows only `+` (E1/E5 updated accordingly). Nothing is assumed; the rail reads as the application's silhouette.

**2. Instances are peers (M2).** A project may run several instances of one product (`db-main` for checkout, `db-reports` for reporting). One instance → the rail opens it directly. Two or more → the rail icon carries a count badge, clicking lands on a compact instance list, and the product sidebar's header becomes the instance switcher. Every instance is a separate topology node with its own bindings, backups and branches — instances are never nested inside each other, and the platform never assumes "the database."

**3. Environments stay a filter, not a container (M3) — with one refinement.** Three models were weighed: env-as-filter (GOV-002 §4.2), env-as-container (AWS-style — handles asymmetric shapes but hides drift and doubles nav depth), and env-as-dimension (fails for stateful services, where production's database is physically distinct). Filter wins, refined by the distinction **shape is per-project; presence and scale are per-environment**: staging runs everything small, previews provision a subset under a `preview-minimal` policy. Consequences: (a) the rail does **not** reshuffle on env switch — a product absent from the current environment shows an explicit "not in this environment — exists in production, staging · add for $X" state rather than a vanishing icon; (b) the **Environments page is a parity matrix** (environments × service types: present / scaled-down / absent / branch-not-copy), making "same shape, different scale" inspectable and drift impossible to miss, complementing the promotion lane (DP1); (c) per-environment cost sits on each matrix row.

### Region & provider model (frame C7)

Where does region live? The answer is layered, and each layer earns its place:

**1. Provider is a facet of region, never a second axis.** A location is a cell: `aws · ap-south-1`, `gcp · us-central1`. The provider tag is visible metadata (it matters for co-location with a team's external compute) but never forks the UX — one grammar, one console, every cloud. "We're a GCP-only shop" is an org **Policy** (`allowed-regions`), not a per-create decision.

**2. The environment sets the *home region*; instances inherit it.** The environment is already the isolation unit — one private network, one credential domain, one data boundary — and bindings assume co-location. A routine per-instance region dropdown would normalize cross-region topologies by accident: every edge a latency + egress liability, the private network quietly a mesh. The org holds only a *default* home region for new environments. Multi-region production is **more environments** (`production-eu` in `eu-central-1`) — which is also what data-residency compliance actually wants.

**3. Region is physically per-instance — and overriding the home is an *explicit exception*, offered in exactly two cases:** (a) **availability gaps** — the product doesn't exist in the home region yet (new capabilities launch in few cells; frame C7 shows a beta GPU Worker); (b) **typed cross-region features** — read replicas near users, multi-region buckets — exposed inside those type blocks. In both, the console states the physics up front: added latency per binding, egress priced into the estimate (never a billing surprise), the edge rendered dashed-with-globe in the topology, org policy checked inline, and a promised "move home" proposal when availability catches up.

**4. The client-in-another-region scenario (frame C8).** An India-based org launching for a US client doesn't move one instance — it moves the *stack*: a new environment (`production-us`) with home region `aws · us-east-1`, cloning production's shape at small scale, bindings co-located, no egress tax on every query. The org's default region is only a prefill in this flow. Side benefits fall out: per-client cost is a free rollup line, and data residency is cleanly satisfied (empty schema recommended over a cross-region branch for client data). If the client warrants separate members and billing, the same logic scales up one level: project-per-client. Only when it is genuinely a single resident resource (compliance-pinned database, read replica) does the C7 instance-level exception apply.

**5. The region selector is one combined list — provider is a filter, never a gate.** "Where should this run?" is a single geographic decision, so the selector is a single list sorted by distance/latency from the relevant anchor (environment home; org location during onboarding), each row faceted `provider · region-code · city`. Filter chips (All · AWS · GCP) and search serve the co-location case without forking the flow; long lists group by **geography**, not provider, because geography is the decision axis. Provider-first two-step selection is rejected: it hides the closest option behind a gate, implies the product differs per cloud, and re-asks per create what the org `allowed-regions` Policy already answers — policy-restricted regions render disabled with the policy named, never silently hidden. Product-availability badges appear inline (C7's pattern).

**6. Availability is a rollout dial, not a launch obligation.** A product "release" is per-cell, never global: each product × cell pair has a state — **available**, **limited** (beta / capacity-gated), **planned** (requestable), or **not offered**. Steloit enables a product in a region when demand justifies the capacity, and the console is honest about the current state everywhere it matters (C1 badges, C7's constrained region list). The demand loop that drives the dial: (a) **explicit** — a "Request it here" affordance on every unavailable state registers `org × product × region` demand and promises notification; (b) **revealed** — every C7 cross-region exception is a live demand signal, priced in the egress its org is already paying. When a cell flips on, the loop closes: requesters are notified and every exception instance receives the one-click, downtime-free **move-home** proposal, logged in the audit trail.

**7. Availability is surfaced at selection, not the dead end.** On the create surface (C1), a product absent from the current home region carries a "not in ap-south-1 · nearest: …" badge — you learn before you commit, and the create flow (C7) opens with only the regions where the product exists, sorted by distance from the environment.

### Consistency contract (audited across all 152 frames)

A programmatic audit pass enforces these rules; they are the definition of "aligned" for this console.

**Chrome tiers.** Every frame belongs to exactly one tier:
- **Tier 1 — full app chrome** (all W/D/S/M pages, C4, C5, E1/E3/E5, P1/P2): context bar with breadcrumbs + **⌘K search** (placeholder may be contextual, the component and shortcut may not vary) + bell + avatar; icon rail reflecting the active project's shape; section sidebar with cost footer. Exception: W7, where the palette itself replaces the search affordance.
- **Tier 2 — creation canvas** (creation & review flows C2–C3, C6–C12, G9–G11): the canvas shape with the rail present — **the dashed + lights up as the active rail item during service creation** (creation is a rail destination; + is its home), and the gear lights up during policy creation (that flow belongs to the governance plane). Breadcrumbs + avatar in the ctx bar; no sidebar (creation has no sections); the full width belongs to form + estimate rail. *Revision note:* this tier began as fully stripped "focus chrome" (creation-as-checkout); once the canvas shape existed (see structure audit), stripping the rail lost its justification — the rail costs no form width, keeps services visible for mid-form reference, and preserves the escape hatch. The checkout signal survives in what's absent: no sidebar, no bell.
- **Tier 3 — identity chrome** (A-series, E2, E4): brand mark only; no tenancy UI exists yet.

**Canonical state.** All current-state frames agree on one world: ecommerce runs 7 services; **db ×2 is the only rail count badge** (PostgreSQL: db-main + db-reports); project total **$208/mo** in every sidebar cost footer ($58 db-main, $24 db-reports, $22 cache, ~$9 assets, $12 jobs, $61 api, $22 worker); month-to-date spend is shown as spend, never conflated with the estimate. Everything else the C-series creates (admin, sessions, uploads, emails, mailer, gpu-encoder, production-us) is **in-flight** — depicted at its moment of creation and not yet in any total; D11 accordingly shows admin's binding as *issued · activates at ready*, matching C4's contract.

**Instance landings (M2 · M4–M8).** Every product has its landing page designed and mocked: PG's (M2) is live canon; M4–M8 show each remaining product's landing **as it appears the day that product reaches ×2** — same grammar (vitals table with product-native columns, New instance, switcher in the sidebar header, rail badge on that product within the frame), each with a why-two rationale card: risk appetite (Valkey), quarantine boundaries (Storage), failure domains (Queue), blast radius (Web), latency isolation (Worker). These are grammar frames like M3, not assertions about today's ecommerce.

**Navigation rules.** Settings destinations (Members, Billing & usage, Audit log, Policies, API keys, project/org General) have **exactly one navigation home: settings mode behind the gear**. Nav columns never carry links to them — a link inside a sidebar reads as a nav item and creates a second claimed home; the project sidebar's cost footer is therefore pure display (the rollup is the information). Page *content* may deep-link into settings freely (a cost card linking to Billing & usage is fine, as is E5's "Invite members → Settings" empty-state CTA); navigation may not. The same discipline bans **signage-in-nav**: nav columns contain destinations, not documentation — no notes explaining where *other* things live (the removed "org admin lives in Settings ⚙" and "account settings → profile icon" footers). A note in a nav column is an admission the structure doesn't explain itself. Nav footers may state only the **scope of their own column** — "Acme · Pro plan" on the settings nav, "these settings belong to you" on the account nav, or an empty-state line describing the rail itself. The instance-switcher chevron (▾) appears in a service sidebar header **only when the product has >1 instance** — a switcher over one item is noise. Rail badges likewise only at n>1. Sidebar item sets match the coverage matrix exactly, in the order Overview/Metrics/Logs → Browse → Manage, with Settings always last.

**Shared canon.** Regions render provider-faceted (`aws · ap-south-1`) at first mention on any surface; CLI flags use `aws/ap-south-1`. The incident timeline is identical everywhere it appears: deploy #142 at 13:58 → p95 alert 14:02 → dead letters 14:03 → 642 ms log lines from 14:03 onward. Destructive actions everywhere follow one grammar: stated blast radius → dependency block → type-to-confirm → audit event with actor (and reason where the action destroys data). Monospace means copyable; steel means selected or primary; amber means degraded-but-diagnosed; violet is reserved for the assistant.

**Create-surface entry points (one rule, three doors).** The create surface has a single unselected form (C1) and preselected states (C2/C3/C9–C12). Three entries reach it, differing only in how much context they carry: the **rail +** (generic — nothing decided, product grid shown); **⌘K / `?add=type`** (product carried — lands on that product's state); and a **product page's "New PostgreSQL"** button (product *and* environment carried — the page is already scoped, so both resolve). The governing principle is the switcher rule applied to creation: **context already committed is carried, not re-asked** — a generic entry shows the grid, a product-specific entry collapses it to the selected state. Preselection is a smart default, never a lock: the selector strip stays live, so a PostgreSQL landing → New PostgreSQL → *actually, Valkey* switches in place without a dead end. No product keeps a separate create page; its landing button is just the context-richest of the three doors.

Provisioning for all products: C4. "Grammar" = the referenced frame's layout applies verbatim with the product's own data; each shared surface is mocked once at full fidelity.

**Product Overview grammar (W4 · S1–S5).** All six overviews are generated from one template; consistency is structural. Zones, top to bottom:
1. **Identity header** — glyph, name, status label, and a **metadata chip row** replacing prose subtitles: engine/version, size or contract, region (provider-faceted), notable flags (HA off, TLS enforced, DLQ on), and a copyable service id. Header actions: one contextual primary + Docs.
2. **Vitals strip** — the product's four vital signs with deltas (same delta grammar as Metrics pages), plus **cost as the always-last cell** ("$58/mo · of $208 project"), keeping cost ambient rather than hidden in Billing.
3. **Attention panel** (left) — one position, a mood-driven label: it reads **"Needs attention"** (amber eyebrow) when something needs a human and **"Activity"** when calm — the label itself is part of the signal, and it is always truthful. A **fresh instance shows the empty state** (S6): dashed panel, honest zeros in the vitals ("no queries yet", "— "), the two bootstrap actions (first query, import), the ambient facts already true (backup schedule, PITR accruing, binding active), and the promise stated in-product: *the panel turns amber only when something needs you.* **Amber card** when something needs a human (db-main's slow query, jobs' dead letters, api's regressed deploy — each carrying its evidence line and the two next actions, with the AI proposal button where one exists); **calm activity** otherwise (cache's keyspace shape, assets' event feed, worker's schedule table). A one-line status strip pins the panel's floor (branches/backup state, healthz, oldest message age).
4. **Connect panel** (right) — identical structure everywhere: injected env-var pills, one copyable CLI line, then the relationship list — *Consumers* for data products, *Uses via bindings* + *Serves/Triggers* for compute — each row with role pill and rotation/scope metadata, footed by the relevant security promise ("no static secrets", "nothing world-readable by accident").
5. **Act row** — four quick-action tiles per product; destructive tiles render in the danger treatment with their guard named in the hint ("unlock + confirm", "typed name + reason").
The two amber overviews (db-main, api, jobs) all point at the same incident from their own vantage — one story, three doors, converging on prp_7c31a2.

**Scaling grammar (D22, shared by Worker with mode differences).** Scaling is configured as a flow, not a form: **(1) Strategy** — mode cards (Fixed / Autoscale / Scale-to-zero), with ineligible modes shown dimmed *with the reason* ("an HTTP service keeps a floor so first requests never cold-start"); Worker shows the same cards with Scale-to-zero eligible. **(2) Range** — a visual instance-slot track instead of min/max number fields: solid slots = the floor (paid always), the current count marked, dashed slots = burst headroom (paid only when traffic asks), and slots beyond the org compute-ceiling policy rendered struck. The Settings pages (D12/D14/D16/D18/D23) share a settings grammar with product-specific stakes: **changes state their blast radius before apply** (resize = failover seconds; mode switch = restart + cost; contract fields are immutable where consumers depend on them), and **danger zones are dependency-aware** — deletes are blocked while bindings/branches/schedules/domains depend on the instance, require type-to-confirm, and leave a recovery path (final snapshot 30 d, soft delete, drain-first).

### Interaction tiers — modal, drawer, page (frames T1, U1–U8)

Create/edit actions previously had two extremes (inline affordances and dedicated pages) and one improvisation in between — T1's delete popover. That's now a system with a decision rule. **Centered modal** for a single decision or a couple of fields where the page context isn't needed to fill it: scrim + 460px card, title/body, actions bottom-right; destructive actions get the danger button, and *data*-destructive ones escalate to **typed-confirm** (U6: delete db-main names its dependents — api and worker will break, knowingly — takes a final backup restorable for 30 days, and enables the button only when the typed name matches). **Right drawer** (AI4's exact grammar: scrim + 424px sheet, header/✕, scrolling body, sticky footer) for complex forms that benefit from previews, live checks, or the page behind: create binding (U2 — target, scope, injected env-var preview, credentials minted at bind), lifecycle rule (U3 — dry-run preview; the manual path to the same rule the assistant proposed in AI7), schedule (U4 — cron with next-runs preview and D17's {{date}} payload grammar), and custom domain (U5 — the async case: DNS records, live dig checks, "close this — we keep checking," cert issues automatically). **Dedicated page** for multi-step or provisioning workflows — already the norm: service creation (C-series), policies (G9), save-as-template (T3), BYOC connect (X2), promotion (DP).

**The census was then verified against every page, not assumed.** A full scan of all 152 frames for create/edit affordances found six inline-form violations, all fixed: Personal tokens (P5) and org API keys (G8) had inline "new token/key" rows → now clean Create buttons opening the token modal, with **U7** showing its reveal state (the secret shown once, hash-only promise, "carries your roles and shrinks the moment your roles do"); Alerts (O5) had an inline rule composer → now opens the rule drawer (**U8**: query pre-filled from the ⚑ buttons, condition + window, routes, and a 7-day backtest that finds the 431 ms incident — how you tune a threshold without a week of false pages); and the db/storage/queue deep pages (D11, D15, D17) had inline binding/rule/schedule forms → now triggers into U2/U3/U4, the drawers that already owned those flows. The census, so nothing improvises again: **modal** — invite member (U1, seat-aware), delete template (T1), remove member, revoke API key, rename anything, cancel-deploy confirm; **typed-confirm modal** — delete service/project/org, delete environment with data; **drawer** — binding, lifecycle rule, schedule, alert rule, custom domain, add secret, edit service shape, webhook; **page** — create service/project/env, policy, template capture, cell connect, promote/rollback, plan change. ### Dashboards — the platform at a glance, under Home (frames DB1–DB8)

**Placement, with the reversal on record.** First proposal: under Observe ("dashboards are views over telemetry"). The cross-plane widget list broke that premise — a grid holding a billing stat, a deploy marker, an AI insight and a p95 chart ranges over four planes, and nesting it under Observe puts data in a child that the parent doesn't own. A top-level rail item was the next candidate and passes the admission rule (a personalized home is the highest-frequency destination) — but for a *developer-first* product it taxes the primary persona: developers move by jump-to-the-thing, the rail's terseness is a feature, and "do I land on Home or Dashboards?" is a decision tax nobody should ship. The resolution uses a seam that already existed: **Home's sidebar**. Home is already the org-wide, cross-plane landing (nouns and costs); Dashboards joins it as a first-class group (the vitals), with its own full section — Overview · Pre-built (PostgreSQL Health · Valkey Performance · AI Gateway · Infrastructure · Cost & Usage · Deployments) · My dashboards · Shared · Templates. No new rail item, no second home, nothing cut — and the rail promotion remains a one-anchor insert if usage ever argues for it.

**Three object types, distinct semantics.** *Pre-built dashboards are views, not files* — generated from the topology, always current as services come and go; "Customize" forks a copy into My dashboards (template copy-semantics, reused). The per-product ones are **fleet-level** — DB2 shows every PostgreSQL across projects *and* environments (db-main production and staging, db-reports, events-db), answering the question product pages can't: *how is the fleet?* Depth stays on the product pages ("Open →"); composition is the dashboard's job — the line that keeps the system non-redundant. Same rule for DB4 Cost & Usage: the ledger and the contract live in Billing; this page *watches* spend as telemetry (MTD $171.42 → $482, the egress-87% warning as a widget). DB3 Infrastructure is the "Production Health" that ends tab-jumping: golden signals with deploy markers (#143) on every chart, so "what changed?" is never a second investigation. *Custom dashboards* are assets with the org/restricted/personal visibility grammar; shared ones are live-for-everyone and audited. *Dashboard templates* (DB6) are **layouts only** — they bind to your services at instantiation, never provision, and are deliberately fenced from Settings → Templates (infrastructure shapes): same word, different asset, stated on the page.

**Scope is a property of the dashboard, not of the system.** The *section* is org-level by necessity (it hangs off Home, the only surface that can host a cross-project view), and the *pre-builts* are org-level by definition (a fleet view or org spend scoped to one project collapses into what product pages already do). But custom dashboards are mostly project creatures — the developer persona builds single-project views almost exclusively — so each dashboard carries a **scope** (org-wide, or a project) set at creation, orthogonal to **visibility** (personal / org / restricted — who sees it vs what it ranges over). Project-scoped dashboards are *born filtered*: they inherit the crumb's env-as-filter when opened in-project and the project's permissions outright, which also answers the access question an all-org model would have dodged (an org-wide dashboard renders only the projects the viewer can access, and says so). Canon: `checkout-health` is ecommerce-scoped — it always was, in fact; the org badge was the error.

**Access is deliberately single-door.** Dashboards are reached from Home only — considered and decided against a second, project-context door to keep one canonical path; project-scoped dashboards remain born-filtered assets, opened from the org library.

**The canon dashboard.** `checkout-health` (DB7, edit mode) was born Jul 2 during the incident — the view asha wished existed at 14:31: api p95 with the #143 marker, order.paid errors, DLQ depth, MTD spend and the deploy list on one grid — the cross-plane composition that justifies the placement. Drag handles (⋮⋮), a dashed add-slot, and the add-widget drawer (interaction tiers respected: create-dashboard is a modal, DB8; add-widget is a drawer) with sources across Metrics · Logs · Cost · Deploys · AI insights · Alerts — or skip the drawer: **⚑ Add to dashboard** on any chart lands here pre-filled, the same grammar as alert rules (U8). Filters (project / environment / region / product) apply to every widget at once; dashboards sit above project context like Home itself, so they carry their own filter row — consistent with, not an exception to, env-as-filter. AI-suggested dashboards are deliberately deferred, with the constraint set now: they obey Law 4 and vanish cleanly when AI is disabled. Personas get their answer in DB6's five layouts — Golden Signals for the SRE, Release Review for the shipper, On-call Handoff, Postgres Deep-dive, Team Weekly for the manager, honestly labeled.

### Templates — from consumption to management (frames T1–T3, with C5–C6)

Templates previously existed only at the point of *consumption* — the official gallery (C5), its detail page (C6), the create surfaces and onboarding — plus W2's "Save as template" with nowhere for the result to live. T1–T3 complete the loop with a **management home**, placed by the established rule: templates are **org-scoped reusable assets**, so they're managed where Cells are — **Settings → Organization → Templates** (a sidebar item with a count, in all 26 settings frames) — while consumption stays in the create flows. Same consume-here / manage-there split as environments (crumb) and cells (region selector).

**The load-bearing semantics.** A template is a **frozen copy of a shape, never a live link**: instantiation copies, so editing or deleting a template never touches anything created from it — T1's delete modal says it at the moment of doubt ("a template instantiates copies, never links; deleting the recipe doesn't touch the meals") and T2's "Used by" panel is explicitly informational. **Secrets, data and keys are never captured**: bindings are stored as placeholders and credentials are re-minted per consumer at create — the template is a recipe, not a pantry. In the capture flow (T3), a binding to an *excluded* service (api → db-main when db-main isn't selected) becomes a **required input** the consumer wires at create — the dependency is surfaced, never silently dropped. And **estimate-before-provision extends to birth**: a template carries its instantiation price from the moment it's saved (T3's $117/mo rail), through the management list, to every consumer's confirm.

**The frames.** T1 is the list — provenance ("saved from ecommerce/production · v4"), contents summary, monthly estimate, visibility (org / restricted), usage count, updated-by, with edit/duplicate/delete per row, the official gallery linked but separate (managed by Steloit). T3 is the capture flow on the gear-lit creation canvas (like policies — saving creates an asset; nothing provisions, nothing bills), reached from W2's button, with CLI parity (`steloit template save checkout-stack --from ecommerce/production --services api,worker,jobs,cache`). ### AI as a native layer, not a chatbot (frames W10, AI1–AI3)

The AI experience is governed by four laws, each demonstrated by a frame rather than asserted:

**Law 1 — AI suggests, developers decide.** No AI interaction mutates state; each ends in a reviewable proposal. Demonstrated by W10 (the `prp_7c31a2` index proposal as an approvable diff) and AI1 (describe-to-provision yields a *set* you approve, never auto-creates).

**Law 2 — every recommendation is explainable.** Each suggestion shows why it was made and the evidence used. AI1 gives every suggested service an inline *Why* tied to a stated requirement; AI2 answers "Why is my database slow?" with cited sources (metric p95 812ms, trace tr_8814, the 642ms SeqScan) before proposing anything.

**Law 3 — analyze broadly, act within permissions.** The assistant reads metrics, logs, traces, schema, config and cost, but any action runs through the human's own permission and approval path. AI2 states its read-scope explicitly and routes writes back into the standard flow (e.g. "Review proposal (W10)").

**Law 4 — the platform works without AI, and orgs can disable it.** This is the trust anchor, and it gets its own page: **AI3** is the `ai-assistant` Org policy in full — reached from the Policies row in G7 — with an enforcement control (Enabled / Opt-in only / Disabled), the *exact inventory* of surfaces it hides (the Assistant workspace AI2, the drawer AI4, describe-to-provision AI1, the product panels W10/AI6–AI8, follow-ups AI9, the coachmark AI5), a matching list of what it *never* affects (Create, Observe, Deploy, Settings — all unchanged), a live impact summary (members affected, insights hidden, **no data deleted**, applied changes kept), per-project overrides, and audit. AI is an enhancement, never a dependency.

**Surfaces.** Rather than one AI page, AI appears where work happens: **describe-to-provision** (AI1, a state of the create surface — the product grid always works alongside it); a **dedicated Assistant** (AI2, reachable from the ⌘K palette, global search, the `steloit ask` CLI, and product panels); **product-level panels** (the slow-query/index flow on PostgreSQL, extensible to Valkey/Storage/Queue by the same pattern); and **Observability** (Observe/Events already carry the assistant's incident narrative into W10). 

**Product-level AI panels (frames W10, AI6–AI8).** Every fleet product exposes its own AI panel as an *AI insights* section in the product sidebar, and all four share one grammar — a `.prop` panel: **Evidence (what I read)** → **Reasoning** → **Proposed change** (a diff/config/steps) → **Impact**, with the apply buttons reserved for the human and every application audited as *you, via assistant*. PostgreSQL is the index proposal (W10, `prp_7c31a2`). Valkey (AI6, `prp_ca11e0`) reads memory pressure and OOM-reject errors and proposes an eviction-policy + maxmemory change applied through Settings. Object Storage (AI7, `prp_st77a4`) reads object age/access and proposes lifecycle rules (expire temp uploads, tier cold originals) applied via the Lifecycle composer with a dry-run and no immediate deletes. Queue (AI8, `prp_qu20b9`) analyses the two `order.paid` dead letters, correlates them to deploy #142's missing gift-card receipt, and — recognising it as a code fix, not a retry problem — routes the fix through Deploy #143 before replaying. The panels differ only in evidence and remedy; the visual and interaction pattern is identical, and each carries the four-laws rail and points back at the shared pattern.

**Continue the conversation from an insight (frame AI9).** Every proposal panel carries an *Ask a follow-up* affordance in its header. It opens the Assistant **seeded with that specific proposal** — the evidence and reasoning already loaded — so a question like “why allkeys-lru and not volatile-lru?” is answered in context instead of from a blank chat. The drawer pins an **attached-insight** card (the carried context, e.g. `prp_ca11e0`) at the top of the thread, with a *1 of 3 open* control acknowledging that a user may be juggling several recommendations and can switch between them. Two rules keep it honest: the conversation is grounded in the insight (this is the “context already committed is carried, not re-asked” principle applied to recommendations), and **talking never changes the proposal** — the footer keeps *Review proposal* present, so discussion informs the decision but the human still approves in the panel. Follow-ups can also spawn alternatives (“I can draft a TTL policy first, then volatile-lru becomes safe”) as new reviewable proposals — the discussion feeds back into the same suggest→approve loop.

**The insights inbox — a home for many recommendations (frame AI10).** Because a project accrues several recommendations at once, they get a consolidated inbox: a cross-service list ranked by impact and severity, filterable by category (Reliability · Performance · Cost · Security) and status (Open · Applied · Dismissed), with a summary strip (open count, reliability fixes, cost identified, applied-this-week). Each row is the same proposal in miniature — product, category, one-line, evidence count, impact, `prp` id — with per-card **Review → · Ask a follow-up · Snooze · Dismiss**. It is a **section of the Assistant workspace** (the hub’s standard sidebar — Ask · Insights · Activity · Capabilities; the drawer’s *1 of 3 open* control jumps here), deliberately **not a rail item**: insights are AI-generated, so by Law 4 they must disappear cleanly when AI is disabled — a permanent rail slot that vanished on a policy toggle would violate the rail’s admission rules. Applied and dismissed insights persist with their state (the orders index shows *applied via #143*; a dismissed worker scale-down stays faded and logged), so the inbox is a durable ledger of what the AI proposed and what the humans decided.

**The Assistant workspace — one hub, four sections (frames AI2, AI10–AI12).** The full-page Assistant is not a single chat; it’s a workspace built on the console’s own grammar — the standard `.snav` sidebar, `.pgpad` gutters, the standard page header, and shared components (cards, metric tiles, the audit table, chip filters) — so it reads exactly like a product or domain page. Its sidebar (**Ask · Insights · Activity · Capabilities**) and a standing footer that restates how it works and where to disable it. **Ask (AI2)** is the complete conversational experience: a conversation list with search and time-grouped history (Today / Earlier), an active thread whose header names the scope and permissions, and a context rail that shows the exact **sources the assistant read** (metric, trace, query plan — Law 2 made literal), the proposal that came out of the chat, and actions to turn a conversation into a proposal, share it, or export it as a runbook. **Insights (AI10)** is the recommendations inbox. **Activity (AI11)** is the audit ledger — every question asked, proposal made, application and dismissal, each with actor, evidence and timestamp (“applied as asha, via assistant”; “dismissed by marco, reason logged”) — the accountability half of *AI suggests, developers decide*. **Capabilities (AI12)** is a directory of everything the AI can do and where each surfaces, closing with the safety boundary (never IAM, secrets, network or destructive actions directly) and the org-wide off-switch. The quick drawer remains the fast path from any page; this workspace is where the AI’s conversations, recommendations, history and capabilities are organised in one place. The drawer expands into it, carrying the conversation. The surface is reached from the ctx-bar Assistant button, so — like the notifications inbox — no rail item is active; conversation selection uses the platform’s steel highlight while only AI-authored content carries the violet accent, keeping the Assistant visually of-the-platform rather than a separate app.

**Visual language.** One reserved accent — violet `--assist`, never used for anything else — plus the `pill ai` badge and suggestion-card treatment, so AI-authored content is always recognizable at a glance. **Safety:** the assistant never performs IAM, secrets, network or destructive actions directly; it explains or drafts, and the human executes through the standard workflow.

### AI access & discoverability (frames C1, AI4, and the global top-nav)

Two discoverability fixes, both resolved by putting the affordance where the work already is rather than behind a named page.

**Describe-to-provision is discovered at the create surface itself.** The intent path is not a hidden mode: the default create surface (C1) leads with a violet *"describe what you're building — or pick a product"* card above the grid, with a divider between the two. Every existing door into create (rail `+`, ⌘K, a product page's New button) therefore surfaces the describe path for free — no separate entry to find. Typing expands it into the suggestion state (AI1). The grid is always present, so the describe path is an offer, never a gate.

**The Assistant lives in the platform chrome, not on a floating chatbot.** This is a direct consequence of the AI principle "a native layer, not a chatbot bolted on" — so the entry is a **violet Assistant button in the top nav** (adjacent to ⌘K search, shortcut ⌘J), present on all 73 tier-1 (full-chrome) frames, *not* a bottom-right FAB. A FAB is the archetypal bolted-on chatbot and is context-blind ("How can I help?"); the top-nav button reads as a first-class tool beside search and the notification bell, and its surface is **context-aware**.

Clicking it opens a **right-side drawer** (AI4) — not a floating chat window — pre-scoped to the current page (a "Context: api · ecommerce / production" chip, changeable), for quick questions without leaving the page. The drawer **expands to the full-page Assistant (AI2)** and the full page **collapses back to the drawer**, carrying the same conversation — one conversation at two sizes, the same "context is carried, not re-asked" rule the switchers and create surface follow. Division of labor with ⌘K stays clean: **⌘K is imperative** (go there / do that — you know the target), **the Assistant is interrogative** (explain / why / recommend — you have a question); cousins sharing the chrome, not duplicates.

The FAB's one real advantage — grabbiness — is recovered without its downside via the reserved violet accent and a first-run pointer, so the button is noticed without pretending to be a separate product.

**First-run coachmark (AI5).** That first-run pointer is a concrete frame: on a new user's first tier-1 screen, a one-time spotlight rings the top-nav Assistant button (the rest of the console dimmed behind it) with a violet popover that says what it does — reads your telemetry, answers with evidence, proposes a change you approve, never acts on its own — plus the ⌘J shortcut and both dismissals (“Got it” / “Don't show again”). Critically it names the opt-out in the same breath (“your org can disable it in Policies; the platform works fully without it”), so the very introduction of AI also teaches Law 4. It teaches the affordance without blocking work and never reappears once dismissed.

### Extensibility: the services zone has two shapes (frame X1)

The rail's lower zone is a **services zone, not an instances zone** — a distinction that matters the moment a non-fleet product arrives (AI Gateway, and future single-endpoint capabilities). The governing test: **a new rail *zone* requires a new *primitive*, not merely a new product.** Run any candidate against GOV-002's nine primitives; a product that is provisioned, holds secrets, emits events, costs money and is bound by others is a **Service**, however it's shaped — so it takes a service slot, not a new zone. What varies is cardinality:

- **Fleet services** (PostgreSQL, Valkey, Web, Worker): pointable instances. The `×n` count badge means what it says; the instance switcher (SW3) appears at n>1; scaling is instance counts (D22).
- **Capability services** (Storage, AI Gateway, …): one endpoint, config-shaped. **No count badge** (a badge on a singleton is noise), **no instance switcher**; scaling is internal (lifecycle rules for Storage; route weights & fallbacks for the Gateway); the sidebar holds the capability's own sections (Models · Routes · Policies · Keys) instead of an instance list.

This isn't new machinery — the badge and switcher were *already* conditional (the db ×2 rule made them render only at n>1), so a capability service is simply the n≡1 case where they never render. Storage has quietly been a capability service all along; X1 (AI Gateway) makes the shape explicit and named. Everything else is identical across both shapes: one rail icon, the `+` create surface (a capability is just another card in the C1 grid), the cost footer, the binding grammar (X1 is consumed by api and worker through ordinary bindings — rotation, revocation and audit unchanged), and Observe/Events/Billing integration. The rail was designed for a *model* (Services with cardinality), not for today's product list — which is why a genuinely different product type drops in without a structural change.

### BYOC as a deployment target, not a product (frames X2–X3)

BYOC is the region model's final vindication: the spec already held **provider is a facet of region, never an axis**; a customer cell extends that to **ownership is a facet too** — a cell is a region whose hardware the customer owns. So BYOC adds a *value* to the target axis, not a new axis, and touches exactly two surfaces while leaving Projects, Services, Deployments, Observe, Policies and every workflow byte-identical.

**X2 — Cells (org setup).** A new item in Settings → Organization, framed as connecting **infrastructure, not creating a product**: connected cells (Acme Production Cell · customer AWS · healthy; Acme EU Cell · customer GCP · upgrade available) show environments-deployed, agent version, heartbeat, and links to Health & upgrades / Network / Support access. The connect flow is a stepper — provider → **prerequisites validated before provisioning** (quotas, SCPs, region enablement) → **cross-account trust** (external-ID-guarded assume-role via one CloudFormation stack; no static keys leave the account) → provision → health check. Governance is explicit: a cell is Infrastructure an `allowed-regions` Policy (G7) gates exactly like a managed region — no BYOC-specific policy engine.

**X3 — environment creation (the only place a developer meets BYOC).** The region selector becomes a **target selector**: one combined, distance-sorted, filterable list where customer cells (Acme EU Cell · 12 ms · customer GCP) sit beside managed regions (GCP europe-west1 · managed · 9 ms), each tagged by ownership. Policy-restricted targets show disabled with the policy named — the exact grammar already used for regions. After the target is chosen, **the rest of creation is identical**; the only honest difference surfaces in the estimate rail, which splits **Steloit control-plane fee** (bills to us) from **infra** (bills to your cloud account). Inherited unchanged: private networking & IP allowlists (Network on the cell), Observe/Events/Deploy, time-boxed audit-logged support access.

The design goal — *users barely notice whether workloads run on managed or their own cloud* — falls out of the IA rather than being engineered: because the platform never modeled "provider" or "location" as structure, a new kind of location needs no new structure. Future deployment models drop into the same target axis.

### The subscription experience — the hybrid model, complete (frames B5–B12)

**The pricing architecture in one line: subscription = platform capabilities · pay-as-you-go = infrastructure · overage = beyond included quotas.** Pure subscription with "unlimited" infra is unsustainable as workloads vary; pure pay-as-you-go loses predictable revenue and has no clean home for premium platform features. The hybrid keeps pricing simple, predictable, transparent — and customers pay only for what they use.

**Four tiers.** Free (small limits, community) · **Pro $29** (individual developers & startups) · **Business $99** (teams: 20 seats, custom roles/RBAC, SAML SSO, advanced observability — 50M events, 30-day retention, org-wide AI insights, **BYOC cells** with a control-plane fee per cell) · **Enterprise** (custom: dedicated cells & private regions, audit export/streaming, SCIM, 99.95% SLA, 24×7, private AI upstreams). The subscription determines features, team capabilities, security & governance, support, retention, and AI capabilities. **Infrastructure never appears in the plan table** — databases, caches, storage, compute, bandwidth, backups and AI Gateway *tokens* are metered pay-as-you-go on every tier. **Quotas are platform meters** — observability events, AI *assistant* requests, egress, build minutes, seats — included per plan, then priced as overage (+$1.20/M events, +$2/1k AI requests, +$0.09/GB egress, +$0.01/min builds, +$7/seat), so customers grow without being forced to upgrade early. The AI distinction is deliberate: Gateway tokens are a resource you provision (infra), assistant requests are a platform capability (quota).

**One deliberate deviation from the brief, flagged:** the brief places BYOC at Enterprise; the console places **BYOC at Business+** (Enterprise adds *dedicated* cells and private regions). Reason: the BYOC design brief made cells an ordinary deployment target with a per-cell control-plane fee — a metered capability, not a contract feature — and canon (Acme, a 12-person team with two cells) would otherwise force a mid-size team onto sales-led pricing for a self-serve capability. Enterprise keeps the genuinely contractual parts: dedicated/private infrastructure, compliance-grade audit export, SLA.

**Canon re-anchored:** Acme is a 12-member team → **Business, $99/mo**; org total **$482/mo** ($383 resources + $99 plan), reconciled everywhere (B1 MTD $171.42, invoices $477.00 with the plan inside the $132.08 subtotal, switcher and Home rows $482). Borealis (the lifecycle org) stays **Pro** — now correctly the individual/startup tier (5 seats, so its trial shows 2/5 and onboarding "3 seats left").

**The frames.** B5 Plans is the four-column matrix with the hybrid model stated in the header and the current plan marked; blocked-downgrades stay honest per column (Pro's says "2 cells need Business"). **B6 Feature gating shows both sides of a gate on one page**: SAML SSO *enabled* (a Business capability in use, with its green tier pill) above the *locked* audit-export card (Enterprise) and the same lock at button scale — visible, explained, priced, never a dead end, one grammar from card to button. ## 3. Interaction & keyboard model

- **Global:** `⌘K` palette · `g` then `o/s/d/b/v` (overview/services/deploys/observe/settings) · `e` env switcher · `[` sidebar collapse · `?` shortcut sheet.
- **Lists:** `↑↓` move, `enter` open, `y` copy ID/slug (mono values are always one-key copyable), `l` jump to logs of selected service.
- **Palette grammar:** noun → jump; verb → action with inline confirm (`roll back api` shows target + revert sha before enter commits); question → assistant (answers cite the data they read).
- **Danger discipline:** destructive verbs never execute from the palette without the same type-to-confirm surface as the page. The palette accelerates; it never removes friction that was designed in.

## 4. Responsive behavior

Console targets ≥1024px as primary (developers, external monitors). 1440+: inspector panels inline. 1024–1439: sidebar collapses to icon rail; panels overlay. <1024: read-mostly mode — monitoring, logs, approvals work; provisioning flows push to CLI (stated in-product, honestly). No separate mobile app by design (this project's scope).

## 5. Accessibility

AA contrast on both themes (log wells included); status = shape+label, never color alone (§1.2); full keyboard reach incl. topology map (nodes are a roving tabindex graph); live regions for provisioning state changes and log tails (throttled); focus rings 2px `--steel` on all interactive elements; reduced-motion collapse per §1.6.

## 6. Developer implementation notes

- Tokens ship as one CSS custom-property sheet consumed by Console and docs site; themes are class swaps (proven in the deliverable HTML).
- The service page shell is one component with slot-based type tabs — the §4.3 page contract in code; new services implement slots, never pages.
- Topology map: nodes from `services`, edges from `bindings`, layout deterministic (seeded by creation order) so the map is *stable* across sessions — a memorable map is a usable map.
- Sparklines and charts share one scale/axis/tooltip kit — one data-viz standard platform-wide; log well virtualizes and tails via the Event pipeline's query API.
- Every empty state renders the equivalent CLI command — the Console teaches the CLI by existing (one-grammar test, enforced through copy).
- The proposal card is a single component bound to one platform-wide proposal-artifact schema; teams *cannot* ship AI features outside it.
