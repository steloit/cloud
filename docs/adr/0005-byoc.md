# ADR-0005 · BYOC: enterprise feature, v3, contract-gated; the residency ladder

**Status:** **Accepted** · founder-ratified 2026-07-18 · confirms existing placement (INF-001 D2/D6, roadmap v3); ADR-022 refinement applied (product log ADR-035). Full analysis: `docs/plan/byoc-review.md`.
**Trigger (measured):** founder-requested adversarial review of BYOC; one evidence sweep (19-company landscape, 2026-07-18).

## Decision

BYOC (data plane in the customer's own cloud account, control plane at Steloit) is an **enterprise feature at v3, built only against a signed enterprise contract that funds it.** Placement was already correct; this ADR adds four disciplines so we neither over-invest early nor under-deliver later.

1. **Free-rider reframe.** The cell / reconciler / `cell_id` architecture is justified by tenant isolation (D7), regional cells (residency, A1.7), DR, and scale caps (D6) — needed regardless of BYOC. **BYOC rides free on it.** Therefore: carry the portable *shape* (cheap; we keep it), and build **zero BYOC-specific machinery** (no multi-cloud abstraction, no cross-account IAM, no AWS/Azure drivers) before a signed deal. "Cheap on capacity, never on shape" applied exactly.

2. **The residency ladder.** Most "BYOC demand" is not sovereignty demand. Answer it at the cheapest sufficient rung: (1) **residency** → a regional cell in Steloit's account (already exists); (2) **network isolation** → v3 private networking (PrivateLink/PSC) into the managed data plane; (3) **key custody** → BYOK/CMEK; (4) **sovereignty** ("data in an account we own") → true BYOC. On every "BYOC" ask, force the qualifying question — region, network, keys, or genuinely my account? Only rung 4 needs true BYOC.

3. **Hard demand-gate + AWS-first.** True BYOC is built only against a signed contract that funds it (industry norm — every comparable vendor gates it behind sales). When it comes it is AWS-first (where enterprise accounts/commits live; consistent with INF-001 D2's "AWS is a future dedicated-cell SKU"). Steloit is GCP-only until then.

4. **Anti-lock-in narrative preserved, for enterprise only.** "Start managed, move to your own account with zero application changes — never locked in" is the one wedge-adjacent value BYOC carries. It is delivered for free by the portable architecture (§8) and is a **v3 enterprise-sales narrative — not a wedge message.**

## Exit criteria — the gate from roadmap to implementation (ALL must hold)

BYOC moves from roadmap to build **only when every one of these is true**. It is an AND gate; failing any single criterion means BYOC is not built — route the request through the decision tree below to the cheapest sufficient rung.

1. **Signed contract requiring in-account deployment.** A countersigned enterprise contract whose terms *explicitly require* the data plane to run in the customer's own cloud account — a contractual requirement, not a preference or a nice-to-have.
2. **The deal funds the feature.** The contract's committed value covers the **fully-loaded first-year BYOC cost** — engineering build + 12 months of BYOC-specific operations + the security review — with margin. Steloit never funds BYOC speculatively. *(Sizing anchor for the founder's math at gate time: a first BYOC build is on the order of 8–15 EW plus ongoing per-account ops; the founders write the actual ACV floor into the gate record when the deal is real.)*
3. **Sovereignty is genuinely un-substitutable.** A *documented* data-sovereignty requirement that provably cannot be satisfied by any lower rung — **regional cell, dedicated cell, PrivateLink/private networking, or BYOK/CMEK**. If any of those clears the customer's auditor/regulator, BYOC is not required and must not be built.
4. **Single named cloud; no multi-cloud abstraction.** Scope is limited to the one cloud the contract names (AWS *or* GCP). No multi-cloud/provider-abstraction layer is built until a *second* provider independently clears this same gate with its own signed deal and evidence.
5. **Security model chosen and in funded scope.** The cross-account access design (least-privilege tag-scoped role, external-ID confused-deputy protection, metadata-only control plane where feasible) and its security review are inside the funded scope **before** any customer-account infrastructure is provisioned.

## Canonical routing policy (decision tree)

**This is the standing policy: not every enterprise request is a BYOC request.** Run it on every "BYOC" ask.

```
Customer requests "BYOC"
        │
        ▼
Is the real requirement data RESIDENCY ("data in my region/country")?
        ├─ yes → Regional cell (Steloit's account, customer's region).  ✅ done — not BYOC
        ▼ no
Is it NETWORK ISOLATION ("off the public internet") — or single-tenant isolation?
        ├─ yes → Private networking (PrivateLink/PSC) into a dedicated/managed cell.  ✅ done — Enterprise managed
        ▼ no
Is it KEY CUSTODY ("my encryption keys")?
        ├─ yes → BYOK / CMEK (data stays in Steloit's account).  ✅ done — not BYOC
        ▼ no
Is true CUSTOMER-ACCOUNT SOVEREIGNTY contractually required
   AND are all five Exit Criteria satisfied?
        ├─ yes → BYOC (single named cloud, AWS-first).  ✅ build
        └─ no  → Do NOT build BYOC. Record the finding; offer the highest rung that fits.
```

## Context

Evidence (`byoc-review.md` §3): BYOC lives in data/streaming platforms (data-gravity + regulatory weight + egress economics) and is **categorically absent in app-hosting PaaS — Steloit's closest analog** (Railway/Render/Fly/Vercel/Cloudflare: zero). It is a *late* enterprise unlock everywhere except Redpanda/WarpStream, who made BYOC their architectural thesis. A category leader (Confluent) calls naive BYOC "the worst of both worlds" — data stays in the account, but the vendor gains standing high-privilege access. BYOC ships a *degraded* product and carries an N-cloud debugging matrix, which is why every vendor gates it behind sales.

## Consequences

No architecture change (D6 already specifies that only the cell relocates; Postgres/Web/Workers/Valkey support BYOC by construction; Bindings are already external; billing stays centralized). No enum/product-surface change. F13/X2/X3 remain the v3 spec. The security build (cross-account least-privilege tag-scoped roles, external-ID confused-deputy protection, metadata-only control plane) is a v3, deal-funded, security-reviewed effort.

## ADR-022 refinement (applied — product log ADR-035)

**Applied 2026-07-18** to `docs/product/18-philosophy/decisions.md` as ADR-035: distinguish **regional/dedicated cells** (Steloit's account, customer's region — *residency* + single-tenant isolation, a Business+ metered capability) from **true cross-account BYOC** (data plane in the customer's own account — *sovereignty*, Enterprise, contract-gated). "Cells at Business+" never meant cross-account BYOC.
