## Goal

Deployment records (immutable history) + rollback endpoint

## Summary

States: queued|building|migrating|canary|verifying|live|failed|rolled_back|aborted.

## Acceptance criteria

- [x] history append-only at the DB level: DELETE raises; identity columns (id, number,
      env, service, sha, actor, created_at, lineage) never rewrite; only lifecycle
      columns (state, gates, canary, annotation) advance.
- [x] rollback creates a NEW record (next number, previous image's sha, rollback_of
      lineage) and 409s when no earlier successful deployment exists.

## Outcome

- `deployments`: immutable history (DP1) via a column-selective trigger — lifecycle
  advances, identity never rewrites, DELETE never. Per-env `number` (#142 grammar),
  unique-index-arbitrated with one retry.
- The DP1 state machine as data (queued→building→migrating→canary→verifying→live;
  failed/rolled_back/aborted terminal) — the T4.2 pipeline drives it when the cell lands.
- Rollback = redeploy of the previous image as a new record; the superseded live
  deployment flips to rolled_back; migrations never auto-revert (expand-contract).
- Deployments target compute services only (web/worker) — databases change through
  their own lifecycle; 422 explains.
- `promote_from` records lineage and carries the promoted sha (full diff computation
  arrives with the pipeline).
- US-4.4 rides along: every deployment lands a `deploy`-kind spine event with number +
  sha — integration-asserted (QA scenario 1's marker replay depends on it).
