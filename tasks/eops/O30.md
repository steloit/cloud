## The defect, measured

One postgres service priced at **$24.00/month**, running for exactly one hour,
rolled up and then invoiced through the real code path:

```
quota_usage.used       = 3600
quota_usage.rate_cents = 8640000
invoice TotalCents     = 8640000   →  $86,400.00
a fair hour of a 31-day month      →  $0.03
```

Off by `secondsInMonth` — a factor of ~2.7 million.

## Why no test caught it

Nothing drives `Rollup` **and** `invoice.Close` in the same test.
`rollup_integration_test.go` asserts `rate_cents == 3600*2400 + 5400*5800` — the
cent-seconds figure — and `invoice_integration_test.go` seeds `quota_usage`
**directly** with `rate_cents = 20800` as if it were cents, bypassing the rollup
entirely. Each half is self-consistent and the seam between them is untested.

## The conflict is real, not a typo

Both readings are written down, by different files:

| says cent-seconds | says cents |
|---|---|
| `Rollup`: `weighted += secs * rate` (`rollup.go`) | `invoice.Close` → `Line{Cents: u.RateCents}`, `total += u.RateCents` |
| the column comment: `rate_cents bigint -- weighted snapshot for span meters (Σ seconds × monthly rate)` | `mtdSpend`: `metered += u.RateCents`, then `billing.SpendToDate` — the number the **hard spend cap** enforces against |
| **`usage_http.go:73`: `cents := int(r.RateCents / secondsPerMonth)`** — it DIVIDES, under a comment naming the unit "cents-seconds" | `billing_export.go` |
| | `budget_http.go`'s own doc: "plan fee + Σ quota_usage.rate_cents" |

One writer and **two** readers on the cent-seconds side; **three** readers on the
cents side. Measured on the same row: `invoice.Close` → **$86,400.00**, and
`GET /orgs/{org}/usage` → **3 cents**. Two customer-facing surfaces disagree by
a factor of 2.7 million about the same number.

*(An earlier version of this task said "one writer, four readers" and counted
`usage_http` as a cents reader. That was inferred from a grep for `RateCents`
without reading the body. It is the premise of a founder ruling, so: three, not
four — and O30 executed as written would have moved the writer to cents and left
`usage_http` dividing already-prorated cents by 2.6 million, reporting $0.00.)*

## NEEDS FOUNDER INPUT

1. **Which side moves.** Recommended: the writer. Four consumers, the column
   name, and the console's "one arithmetic everywhere ($383 + $99 = $482)"
   grammar all say the stored value is money.
2. **The proration convention**, if the writer moves. `feature-specs.md` says
   pay-as-you-go infrastructure with monthly rates, so a running service accrues
   a fraction of its monthly rate — but the divisor is a pricing decision:
   - **actual period seconds** (Feb bills a 28-day month; a service running a
     whole period invoices exactly its monthly rate — this is the only divisor
     consistent with "one arithmetic everywhere"), or
   - **a fixed 730-hour month** (AWS/GCP convention; a 31-day month bills
     slightly more than the sticker rate).

   **There is already prior art in the tree, and it is a third convention:**
   `usage_http.go:29` hardcodes `secondsPerMonth = 30 * 24 * 3600` — a fixed
   30-day month, chosen in implementation code, which is exactly the class of
   decision the 2026-07-27 ruling reserves. Whatever is ruled must replace that
   constant too, not sit beside it.
3. **Rounding**, and whether a sub-cent hour bills 0 or accrues.

This task stays `blocked` until 1 and 2 are ruled. **Do not pick a divisor in
implementation code** — founder ruling of 2026-07-27.

## Not blocked on this, and already done (O19)

The *overflow* in the same accumulator is fixed independently: `money.Accrual`
carries 128 bits, so Σ(rate × seconds) cannot wrap however the units are later
resolved, and the single narrowing point fails loudly without writing.

## Blast radius of the O19 fix, recorded here because it lands on this seam

`Rollup`'s only production caller is `GetUsage`'s recompute-on-read
(`usage_http.go:45`), not a scheduler — there is none. So once O19 makes an
unrepresentable accrual return an error, `GET /orgs/{org}/usage` becomes a
permanent 500 for that org and period: it falls to the `default:` arm of
`identity/http.go` → `problem.Internal`, whose remediation is "Retry; if it
persists, contact support" — advice that can never succeed. And there is no
operator correction path, because `usage_events` forbids UPDATE and DELETE by
trigger (corrections are new events).

That is still the right trade against writing a wrapped figure, but the
remediation is a lie and should be replaced with a truthful one when this task
settles the unit.
