### Fixed here — and the FIRST attempt at this fix made it worse

`currency_code` was hardcoded `"USD"`. My first change made it a variable. **That
was wrong twice**, and review caught both:

1. **It removed a guard.** `units` is fed by `monthly_budget_usd = 300` — a value
   chosen as dollars, in a variable saying so. With the currency free, an operator
   doing the obviously right thing at P1 (`budget_currency = "INR"`, matching the
   account) gets a **₹300/month** budget ≈ US$3.60: alerts firing permanently,
   with nothing in terraform, the provider or the API objecting. The hardcoded USD
   was crude, but USD-on-an-INR-account *failed loudly at apply* and forced someone
   to confront the mismatch. I converted a loud failure into a silent 83× error.
2. **`currency_code` must not be set at all.** Verified from Google's discovery
   doc: *"`currency_code` is optional. If specified when creating a budget, it
   must match the currency of the billing account… The `currency_code` is
   **provided on output**."* The server supplies the account's own currency. So
   setting it is the ONLY path to failure, and making it a required module input
   pushed every future caller toward that path.

**The correct fix is deletion.** `currency_code` is gone; the server fills it in.
And because the amount is therefore denominated in the account's currency,
`monthly_budget_usd` is renamed **`monthly_budget_units`** — the old name was
load-bearing and wrong. The amount/currency pairing is now a founder decision
(below) rather than an implication of a variable name.

On evidence: an earlier version said INR was "the only observable evidence" for
the account's currency. It is not the only one —
`docs/founder-config.md:43` records the same account as *"Free Trial **$300**"*.
That is weaker: Google quotes the trial as "$300 or local equivalent", so it is
plausibly a dollar-quoted description of a local-currency credit, whereas the live
budget's `currencyCode: INR` is the account's actual denomination. Named and
disposed of rather than ignored.

**And the rename alone was not a guard.** Review's Q3 answer: `monthly_budget_units`
is required at the module but was satisfied by a hardcoded literal in each env, so
an operator supplying only `billing_account` at P1 still gets a 300-unit budget
with no prompt — the trap named in three places and enforced in none. The amount is
now an **env-level variable with no default**, the same idiom `project_id` already
uses. Verified: with `billing_account` set and the amount omitted,
`terraform plan` refuses — *"No value for required variable … monthly_budget_units"*
— and with it supplied, resolution passes and the plan proceeds to credentials.
The loud apply-time failure the hardcoded USD used to give now has a
machine-checkable successor at plan time.

Verified on the shipped state: `terraform validate` **Success** for
`infra/envs/dev` and `infra/envs/cell0`, `terraform fmt -check -recursive infra`
clean, and no `currency_code` or `budget_currency` HCL attribute anywhere under
`infra/`.

### NEEDS FOUNDER INPUT — six decisions, none of them mine

1. **Which instrument?** A recurring monthly budget and a one-off trial-credit
   exhaustion alarm are different alarms. `INCLUDE_ALL_CREDITS` makes a monthly
   budget approximate the credit view, but they diverge the moment the credit is
   exhausted or the month rolls.
2. **Which amount?** $300/mo (terraform) vs ₹1000/mo (live) is roughly a 25×
   difference. ₹1000 is a tight runaway-tripwire; $300/mo is "the trial's whole
   value each month".
3. **Which middle threshold — 80% or 90%?** Terraform and the task say 80, live
   says 90.
4. **What happens to the existing budget when P1 lands?** Terraform will create
   `"<cell> budget"` **alongside** `steloit-dev tripwire` — different display
   names, so no adoption. Two budgets, two alert sets. Either `terraform import`
   the existing one, delete it, or accept both deliberately.
5. **The amount, paired with the account's currency.** `monthly_budget_units` is
   300 (dev) / 700 (cell0). Those were chosen as dollars; the server will
   denominate them in the account's currency. 300 on an INR account is ~US$3.60.
   The number and the currency have to be decided together.
6. **`alert_emails`.** Empty everywhere, so even after a P1 apply the AC "alerts
   fire to founders" is **not met** — the budget would fall back to default IAM
   recipients, exactly like the live one. Founder emails are a P1 input this task
   did not previously list.
