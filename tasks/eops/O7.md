## Goal

CI's drift gate regenerates the oapi contracts (`make gen-go`) and canon, but
**never `make gen-sql`**, so a `.sql` query edited without regenerating its
`*.sql.go` ships a stale generated file that CI cannot catch.

## Why — found in US-1.3a, a near-miss

US-1.3a added a `WHERE ... AND status <> 'deleting'` fence to `UpdateServiceShape`
(the atomic backstop for an edit-on-deleting race). The source `.sql` carried it;
the generated `services.sql.go` did **not** — the runtime query had no fence, so
the security close and its `ErrNoRows → Conflict` mapping were dead code. Tests
passed (they hit the Go pre-check, not the fenced query), and the drift gate
would not have caught it because:

```
# .github/workflows/ci.yml — Generate (drift) step:
make gen-go     # oapi-codegen: types, server, contracts — NOT sqlc
make gen-canon  # fixtures copy
git diff --exit-code
```

`make gen-go` does not run sqlc. A reviewer caught the stale const by inspection;
CI would have shipped it. Any `.sql` edit is exposed to the same gap.

## Acceptance criteria

- [x] CI's drift step runs `make gen-sql` (alongside `gen-go`/`gen-canon`) and
  diffs, so a `.sql` edit without regeneration fails the build.
- [x] Verified by editing a query and confirming the drift step goes red without
  the regenerated `*.sql.go`.
- [x] No new false positives on a clean tree.

## Related

US-1.3a (the near-miss) · `.github/workflows/ci.yml` · `Makefile` (`gen-sql`)

## Outcome

One line in `ci.yml`: the drift step now runs `make gen-sql` alongside `gen-go`
and `gen-canon`. `sqlc` was already pinned (`Makefile:16`, v1.30.0), so no
version work was needed — a bump would reformat generated output and fail the
gate for the wrong reason, which is why the pin matters and is noted in the
comment.

**Verified in all three directions**, in a throwaway `git worktree` off `main`
that was deleted afterwards (never the working tree). The `.sql` edit is
COMMITTED before the gate runs in each case, because that is what CI sees — an
uncommitted edit makes `git add -A` stage the `.sql` itself and the gate goes red
for any change at all, which proves nothing. My first attempt made exactly that
mistake and its result was discarded.

| case | today's CI | with `gen-sql` |
|---|---|---|
| `.sql` edited **and** regenerated (an honest PR) | green | **green** — no false positive (AC 3) |
| `.sql` edited, generator never run (the US-1.3a shape) | **green — stale `services.sql.go` ships** | **red** (AC 1, AC 2) |

In the failing case the staged diff is exactly one file,
`internal/identity/store/services.sql.go` — the gate names the stale artifact
rather than the edit that caused it, which is the right thing to put in front of
whoever has to fix it.

The control row is the part worth keeping: the same commit passes today. This
was not a theoretical gap.

**A second hole, found by the QA review and closed here.** `sqlc` writes output
but never REMOVES stale output, and the gate can only diff what the generator
writes. So *deleting* `db/queries/mfa.sql` left
`internal/identity/store/mfa.sql.go` on disk — 4459 bytes, **nine live query
functions**, still compiling and still callable — and the gate reported GREEN.
That is this task's own property ("the SQL that executes is the SQL that was
reviewed") approached from deletion instead of edit. A *rename* was already
caught, because the new `*.sql.go` appears and stages; only deletion slipped
through.

`gen-sql` now sweeps the generated directory before regenerating. Verified both
directions: on the deletion commit the gate goes **RED** naming exactly
`D services/api/internal/identity/store/mfa.sql.go`; on a pristine tree
regeneration reproduces the tree byte-for-byte, so there is **no false
positive**. `gen-sql` and `migrate-new` were also missing from `.PHONY` — a
phony target the CI gate now depends on should be declared.

**Not in scope, still open.** O13 owns the other two holes in the same step
(`gofmt -l` in every module, and `-race`, which has never run in CI at all).
O13's Approach item 3 asks for exactly this `gen-sql` change; it is delivered
here, so that item is already met when O13 is picked up.
