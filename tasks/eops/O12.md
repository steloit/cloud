## The defect

`scripts/spec-sync/validate.mjs` errors when a context pack exceeds **160** lines, but the
message it prints says `> 150 cap`, and `contexts/README.md` documents 150. So a pack can
sit 10 lines over its documented budget and pass, and an author who trims to satisfy the
message is trimming to a limit the tool does not hold.

`contexts/api-conventions.md` is **159** lines by the validator (158 by `wc -l`) after O11 added its silent-acceptance entry
— already over the documented 150 cap, under the enforced 160. O11 chose that pack knowing
this, on the reviewer-verified basis that the enforced limit had headroom.

Found in O11: a first attempt at a mistake-bank entry hit the error, and the resulting
diagnosis ("the pack is exactly at its cap, so nothing can be added") was **false** — the
short form always fit. A gate whose message disagrees with its behaviour produces wrong
decisions from correct-looking evidence.

## A SECOND instance of the same defect, in the same file (found by O24)

Line 62 of the same validator:

```js
if (bodyLines > 320) err(t.file, `body ${bodyLines} lines > 300-line cap`);
```

Enforces **320**, reports **300**. Identical shape to the context-pack cap this
task is named for, so whatever is decided below should be applied to both rather
than leaving the file with one honest gate and one dishonest one.

It is not hypothetical here either: `tasks/e10-observability/US-10.3.md` is
**316** body lines — comfortably over the reported cap, under the enforced one.
O24 added a two-line note to it, hit `body 322 lines > 300-line cap`, and the
message named a limit 22 lines below the one that actually fired. Same failure as
O11's: a correct-looking error producing a wrong estimate of how much room there
is.

Check line 74 (`AGENTS.md`, `> 150` reported as `150`) at the same time — that
one appears consistent, but the point of this task is that the file's caps should
be audited as a set, not one at a time.

## Decide

Which number is real? 150 is documented and cited in `contexts/README.md`; 160 is enforced.
Either is defensible — the point is that one of them must go.

- If 150: the enforced limit tightens, and `api-conventions.md` needs ~8 lines trimmed —
  **O11's silent-acceptance entry is exactly that size**, so choosing 150 means moving it
  or an equivalent. Size the decision off the CURRENT length — 159 as the validator counts it, which is the number the threshold compares — not the pre-O11 one, and not the `wc -l` figure.
  Note the validator counts `split("\n").length`, one MORE than `wc -l` on a
  newline-terminated file — an author trimming to the reported number will overshoot.
- If 160: `contexts/README.md` and the error message both change to say 160.

## Acceptance criteria

- [ ] The enforced limit, the error message, and `contexts/README.md` state the same number.
- [ ] Every existing pack satisfies it (trim, or the cap changes).
- [ ] Mutation-verified: a pack one line over the limit fails `validate.mjs` with a message
  naming that same limit.
