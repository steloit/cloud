## Goal

Two platform changes, reviewed on their own merits rather than as the tail of a
feature branch:

1. **`internal/platform/money`** — a `Cents` type that makes unrepresentable
   monetary arithmetic uncompilable, replacing raw `int64` cents across the API.
2. **`problem.FromDenial`** — one authorization denial→response mapping, shared
   by every handler and every transport.

Both are implemented and green on branch **`task/PLAT-1`** (HEAD `6bb5a09`),
extracted out of `task/US-3.8` at the founder's direction (2026-07-27). This
task exists to give them their own review; the code is not new work.

## Why this is infrastructure, not a feature detail

US-3.8 took six review rounds. Every round after the first found the defect in
the *previous round's fix*, and each was the same error — a guard applied per
site instead of made unrepresentable:

| round | the fix | what it missed |
|---|---|---|
| 1 | a test for the desired-doc guard | it re-implemented the guard, so deleting the real one stayed green |
| 2 | a guard on the sweep's cast | an earlier OR arm already held it, so the new one was dead |
| 3 | 404-for-no-standing on `listEvents` | the SSE half of the same operation still 403'd |
| 4 | 404 for authenticated callers | the env lookup preceded the principal check, so anonymous callers still got an oracle |
| 5 | an overflow bound on `override.instances` | two sibling arms of the same pricing switch still wrapped |
| 6 | a bound derived from one multiply | the billing rollup multiplies again |

Reviews caught all six. That is the pipeline working — and also the problem: a
rule enforced by repetition holds at the rate reviewers notice.

## Scope

### Money

`money.Cents` is a **struct**, not `type Cents int64`: a named integer still
compiles `a + b` and `a * b`; a struct does not. All arithmetic goes through
`Add`/`Sub`/`MulInt`/`AddMul`/`Sum`, each returning an error, using `math/bits`
for the exact 128-bit product. The invariant belongs to the type — a `Cents` in
hand is in `[0, MaxMonthly]` — so callers never range-check.

`MaxMonthly` is **derived** (`MaxInt64 / secondsInLongestMonth`) because
`metering.Rollup` multiplies an accepted rate by a month of seconds. It is not a
commercial ceiling: choosing "at most N instances" or "at most $X/month" stays a
pricing decision the implementation never makes (founder, 2026-07-27).

### Denial mapping

One decision (`AccessDeniedError.AccessDeniedNoStanding`, beside the strings it
classifies) and one mapping (`problem.FromDenial`, importable by every transport
— including `events`, which cannot import `identity` because `identity` imports
`events`; that asymmetry is exactly why the SSE half diverged).

## Bugs this migration fixes, which US-3.8 deliberately does NOT

These are real, live, and **pre-existing** — none was introduced by US-3.8, and
all are reachable without an instance pin. They are listed here so the risk of
deferring them is explicit rather than implied:

- **`POST /v1/estimates` with `postgres {storage_gb: 1e18}` returns 200 with
  `monthly_total_cents = -5340232221128652948`, and `POST .../services` persists
  it.** Because `enforceBudget` projects against `SumOrgMonthlyEstimate`, one
  such row leaves the org's committed run-rate at ~-5.3e18 **permanently** — the
  hard spend cap is then bypassed for every subsequent create. `valkey
  {memory_mb: 4.3e18}` wraps identically.
- **`PriceAll`'s total wraps** from two individually-legal lines
  (`monthly_total_cents = -3016`), reachable through `shape.instances`.
- **`enforceBudget`'s own projection wraps**, so the cap can be jumped and then
  stays disabled.
- **The JSON decoder accepts a quoted number** (`"5800"`), because `json.Number`
  is a string type — the wire contract is quietly bivalent.
- **Valkey's GB rounding goes through `float64`**, losing precision above 2^53 on
  caller-supplied `memory_mb`.
- **`/v1/envs/{env}/events` answers 403 on SSE where the JSON half answers 404**,
  and looks up the env *before* checking the principal, so an anonymous caller
  distinguishes a real env id from a fabricated one.

**Sequencing note:** the first item is the sharpest — a permanently-disabled
spend cap from one authenticated request. If this task cannot be scheduled
immediately, that specific fix is worth pulling forward on its own.

## Evidence already gathered

- API 24/24 packages serial, 0 failures, 0 skips; cell-agent 5; CLI 2.
- Net **−62 lines** despite adding a package: the type absorbed scattered,
  partial checks.
- Converting the codebase surfaced **eight money boundaries across five files**,
  three in files no review round had opened.
- Mutation-verified on `task/PLAT-1`: per-arm bounds, aggregate bound, ceiling
  inclusivity, ceiling derivation, checked projection, SSE ordering, denial
  classification arms.

## What review should ask

- Is `MaxMonthly`'s derivation right, and is it re-derived if `Rollup` changes?
- Is the `Cents` API complete enough that no caller needs `.Int64()` except at a
  genuine boundary (wire, DB, log)?
- Is `problem.FromDenial` the right home, given `events` cannot import
  `identity`?
- Does ADR-0014's rule generalise correctly, or is it stated too broadly?
