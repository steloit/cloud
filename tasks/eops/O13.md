## Goal

Add two gates CI does not have: `gofmt -l` must be empty in every Go module, and
`sqlc diff` must be clean in `services/api`.

## Why

Both were found as *findings from other work*, which is the point — nothing in
the repo was going to surface them on its own.

**`sqlc diff`.** `db/queries/*.sql` is the source and
`internal/*/store/*.sql.go` is generated from it, but only the generated file
executes. CI (`ci.yml:96`) runs build/vet/test and never regenerates, so the two
can disagree indefinitely and every test still passes — the tests are running
the generated file. US-3.8 hit this from the other side: every SQL mutation in
two independent QA sweeps had to be applied to the *generated* file to have any
effect, which is the same fact stated as a threat model. A `.sql` edit that
never reached the generator is invisible to the entire pipeline, and the failure
mode is a query that silently is not the query anyone reviewed.

**`gofmt -l`.** `services/api/internal/billing/plans_test.go` and
`services/api/internal/metering/metering_test.go` are unformatted on
`feat/phase-1-shell-auth-workloads` today. Neither is large or interesting —
that is why they went unnoticed. CI runs `go vet`, which does not check
formatting, so nothing has ever reported them.

**`-race` is never run anywhere.** `ci.yml:96` runs `go test ./...` plain. The
detector has therefore never executed against this repo in CI, which is how O14
(a data race in the reconcile test fixture) reached the base branch unnoticed.

## Approach

1. `gofmt -w` the two files (a formatting-only commit, nothing else in it).
2. Add the `gofmt -l` gate to `ci.yml` in the Go job, before the build step, so
   a format failure reports as itself rather than as a confusing test failure.
3. **`sqlc diff` does not need a new mechanism** — `ci.yml:88-93` already runs
   `make gen-go && make gen-canon` followed by `git diff --cached --exit-code`,
   and `make gen-sql` exists at `Makefile:18`. Add `gen-sql` to that same step.
   Pin sqlc to v1.30.0 (what `sqlc.yaml` and the generated headers say), since a
   version bump reformats generated output and would fail the gate for the wrong
   reason.
4. **Add `-timeout` to the Go test step.** CI runs `go test ./...` with no
   timeout flag, so every package gets Go's 10-minute default, and packages run
   in PARALLEL. `internal/identity` measured 346s serially and **exceeded 600s
   under contention** on an M-series Mac (US-3.8, 2026-07-27) — a hosted runner
   is slower. A timeout there presents as a broken suite rather than as "raise
   the limit", which is the kind of failure that gets diagnosed wrong. Set an
   explicit `-timeout 30m`, and consider `-p 2` for the container-heavy packages
   so the wall clock is predictable rather than load-dependent.
5. Decide whether CI runs `-race`. It roughly doubles integration-test wall
   clock, so this is a real trade-off and not an obvious yes — but "never" is
   the wrong answer, and O14 is the evidence. A `-race` run on the unit-test
   packages only, or a nightly full `-race`, are both cheaper middles.
