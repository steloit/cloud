## Goal

Add two gates CI does not have: `gofmt -l` must be empty in every Go module, and
`sqlc diff` must be clean in `services/api`.

## Why

Both were found as *findings from other work*, which is the point — nothing in
the repo was going to surface them on its own.

**`sqlc diff`.** `db/queries/*.sql` is the source and
`internal/*/store/*.sql.go` is generated from it, but only the generated file
executes. CI (`ci.yml:96`) runs build/vet/test and never regenerates, so the two
can disagree indefinitely and every test still passes — the tests are running
the generated file. US-3.8 hit this from the other side: every SQL mutation in
two independent QA sweeps had to be applied to the *generated* file to have any
effect, which is the same fact stated as a threat model. A `.sql` edit that
never reached the generator is invisible to the entire pipeline, and the failure
mode is a query that silently is not the query anyone reviewed.

**`gofmt -l`.** `services/api/internal/billing/plans_test.go` and
`services/api/internal/metering/metering_test.go` are unformatted on
`feat/phase-1-shell-auth-workloads` today. Neither is large or interesting —
that is why they went unnoticed. CI runs `go vet`, which does not check
formatting, so nothing has ever reported them.

**`-race` is never run anywhere.** `ci.yml:96` runs `go test ./...` plain. The
detector has therefore never executed against this repo in CI, which is how O14
(a data race in the reconcile test fixture) reached the base branch unnoticed.

## Approach

1. `gofmt -w` the two files (a formatting-only commit, nothing else in it).
2. Add the `gofmt -l` gate to `ci.yml` in the Go job, before the build step, so
   a format failure reports as itself rather than as a confusing test failure.
3. **`sqlc diff` does not need a new mechanism** — `ci.yml:88-93` already runs
   `make gen-go && make gen-canon` followed by `git diff --cached --exit-code`,
   and `make gen-sql` exists at `Makefile:18`. Add `gen-sql` to that same step.
   Pin sqlc to v1.30.0 (what `sqlc.yaml` and the generated headers say), since a
   version bump reformats generated output and would fail the gate for the wrong
   reason.
4. **Add `-timeout` to the Go test step.** CI runs `go test ./...` with no
   timeout flag, so every package gets Go's 10-minute default, and packages run
   in PARALLEL. `internal/identity` measured 346s serially and **exceeded 600s
   under contention** on an M-series Mac (US-3.8, 2026-07-27) — a hosted runner
   is slower. A timeout there presents as a broken suite rather than as "raise
   the limit", which is the kind of failure that gets diagnosed wrong. Set an
   explicit `-timeout 30m`, and consider `-p 2` for the container-heavy packages
   so the wall clock is predictable rather than load-dependent.
5. Decide whether CI runs `-race`. It roughly doubles integration-test wall
   clock, so this is a real trade-off and not an obvious yes — but "never" is
   the wrong answer, and O14 is the evidence. A `-race` run on the unit-test
   packages only, or a nightly full `-race`, are both cheaper middles.

## Notes

Filed from US-3.8's QA review (2026-07-27). Not US-3.8's to carry: both are

## Outcome

Three gates this pipeline did not have, plus the two Approach items that were
*declined* — recorded, because a gate PR that silently drops its own Approach
items leaves the next person re-deriving them.

**1 · `gofmt -l`, every Go module, before the build.** `go vet` does not check
formatting, so nothing here had ever reported the two unformatted test files on
the base branch. Fixed in a separate formatting-only commit so this diff stays
reviewable.

The loop is `gofmt -l "$m" 2>&1` **plus an exit-status check**, and both halves
are load-bearing. My first version was the obvious `out="$(gofmt -l "$m")"`,
which reports **CLEAN for a file that does not parse** — gofmt writes parse
errors to stderr and lists nothing on stdout. Found by mutating a file into a
syntax error and watching my own new gate pass. Verified three ways in a copy:
clean → green, parseable misformat → red, unparseable → red.

The module list is **derived** (`git ls-files '*/go.mod' | xargs -n1 dirname`),
not retyped. The QA review confirmed the four modules are complete today *and*
that a fifth would be invisible to a hardcoded loop — no gofmt, no vet, no test,
no `-race`, and nothing saying so.

QA attacked the hardened loop across seven representations — unparseable files,
file symlinks, symlink-only package dirs, a typo'd module path, `gofmt` absent
from `PATH`, vendor/testdata — and could not make it lie. The only green-that-
should-be-red was a module the loop does not look at, which the derivation now
closes.

**2 · `-race`, which is the decision this task asked to be MADE.** It had never
run in CI, which is how O14 reached the base branch and sat there a month.
Measured on a 4-vCPU-equivalent run with real containers: **5m56s** total,
`internal/identity` 347s, reconcile 147s, everything else ≤16s.

> **MERGE ORDER IS A PRECONDITION, not a preference.** This gate is only green
> once **Q10** has landed — Q10 fixes the very race `-race` would otherwise
> report. And the dependency is *non-deterministic*, which makes it worse rather
> than better: QA measured the race at **13/30 (43%)** for the isolated test and
> **2/6** for the full package. Land O13 first and `main` goes red about one push
> in three — and a brand-new gate that is red one run in three gets diagnosed as
> "`-race` is flaky", the fix becomes "re-run", and the gate is dead on arrival.
> Q10 merged first (PR #305); this branch is rebased on a main containing it.

**3 · `-timeout 30m`, explicitly.** The default is 10 minutes **per package**,
and `identity` measured 346s serially and exceeded 600s under contention on an
M-series Mac (US-3.8). 347s against 1800s is ~5x headroom here, and even at a
hosted runner's 2-3x slowdown that stays comfortably inside 30m while being
safely *outside* the 600s default. That failure presents as a broken suite rather
than as "raise the limit", which is the kind of failure that gets diagnosed wrong.

**Declined, with reasons:**

- **Approach item 4, `-p 2` for container-heavy packages.** Not done. Only three
  packages use containers, so a 4-vCPU runner cannot over-subscribe them badly,
  and the measured 5m56s was stable across runs. Adding it would trade real wall
  clock for a problem that did not reproduce.
- **Approach item 5, unit-only or nightly `-race` as cheaper middles.** Not
  taken. The measured delta is ~5 minutes for a detector that currently runs
  never; a nightly run finds the same defect a day later and after it is already
  on main, which is most of the value gone. Revisit if CI wall clock becomes a
  constraint.
- **`-timeout 10m` on cell-agent and cli is exactly Go's default**, i.e. inert.
  Kept for explicitness — their slowest packages measure 3.96s and 2.68s under
  `-race`, ~150x headroom — but the comment must not imply a measurement drove
  that number.

Item 3 of the Approach (add `gen-sql` to the drift step) is delivered by **O7**,
which this branch is stacked on, along with O7's later fix for a *deleted* query
leaving an orphaned `*.sql.go`.

**Filed, not fixed here.** QA found that CI has no assertion that any container
ever STARTED: three integration packages `t.Skipf` when the runtime is
unavailable and the suite still prints `ok`. That silently voids both of this
task's headline decisions — `-race` degrades to a unit-only detector and the
timeout reasoning becomes moot. **O23** owns it; the repo already contains the
pattern (`ckm3_checkpoint_test.go` gates on `STELOIT_CHECKPOINT` and fails in
`t.Cleanup` if the test skipped).

**Known ordering side effect:** `task/O15` and `task/O16` predate the formatting
commit, so each goes red on the gofmt gate until rebased. Correct behaviour, and
worth saying out loud because it lands on several branches at once.
