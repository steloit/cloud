## Goal

`status: in-progress` means "someone is working on this right now, and the
branch `task/<id>` is the lock". Three tasks carried it with no one working on
them. AGENTS.md makes GitHub Issues and the board **generated views** of these
files, so the board was reporting three in-flight work items that were not
in flight.

## What was actually true

| task | claimed | actual |
|---|---|---|
| **T1.3** | in-progress | **done** — `origin/task/T1.3` is fully merged (0 commits ahead of main) |
| **US-10.3** | in-progress | **done** — fully merged, and it already had its `## Outcome` written |
| **O2** | in-progress | **a stub** — never enriched, never started |

T1.3 and US-10.3 are the same shape: the work landed via the consolidation
merges, and the status flip that protocol step 6 requires in the same PR did not
happen. Both verified before flipping rather than assumed:

- **T1.3** — all three of its `verify:` commands pass on main today
  (`image.yml` parses, `infra/k8s/policy/*.yaml` parses, `terraform -chdir=infra/envs/dev validate` → Success),
  and its deliverables are present (`cluster-image-policy.yaml`, three cosign
  references in `image.yml`). It had **no `## Outcome`**; one is added.
- **US-10.3** — `internal/notify/bell.go`, the `bell_scanned` migration, and the
  `notify.bell` worker in `main.go` are all on main, and its Outcome was already
  written. Status flip only.

**O2 is the different one, and the more interesting one.** Its own body still
says *"**Stub** — run the spec-author skill to enrich to `ready` before starting"*,
with `files: []` and `verify: []`. It was never a claim; the status is simply
wrong. Returned to `stub` rather than `ready`, because enriching it needs
decisions this task should not make — see below.

## Findings recorded for O2's eventual enrichment

Gathered with live `gcloud` access (project `steloit-dev`, billing account
`016006-61AFB9-0DD7E7`), so whoever enriches O2 starts from fact:

- **A budget already exists** — `steloit-dev tripwire`, **₹1000 per calendar
  month**, scoped to project `steloit-dev`, `INCLUDE_ALL_CREDITS`, thresholds at
  **50% / 90% / 100%**.
- **O2 asks for 50/80/100% of the $300 trial credit.** That is a different
  instrument (a one-off credit balance, not a recurring monthly budget), a
  different amount, and a different middle threshold.
- `notificationsRule` is **empty** — no Pub/Sub topic and no explicit monitoring
  channel, so it relies on GCP's default email to billing-account admins.
- The terraform module `infra/modules/cost-guardrails` declares **50/80/100%**,
  matching O2 and *not* matching the live budget. It is also the module whose
  duplicated call kept CI's infra job red (O22).

So terraform, the task, and live GCP disagree on the instrument, the amount and
the thresholds. Reconciling them is a founder-visible decision about what the
guardrail is actually for, which is why O2 stays a stub.

## Outcome

Three statuses corrected: T1.3 → `done` (with an Outcome added), US-10.3 →
`done`, O2 → `stub`. `node scripts/spec-sync/validate.mjs` passes, and
`status: in-progress` now appears only where a branch really is the lock.
