## Goal

O23 converted "no container runtime" from a skip into a CI failure. That is a
**negative** guard: it fires on an error. It cannot see a suite that started zero
containers for any other reason.

## The hole, reproduced

With the runtime **present** and `STELOIT_REQUIRE_CONTAINERS` **set**, adding
`t.Skip("quarantined: flaky on CI, see #999")` to both container tests in
`internal/platform/db` gives:

```
ok  	github.com/steloit/cloud/services/api/internal/platform/db  0.619s
```

Gate fully armed, zero containers started, green.

Quarantining a flaky integration test is the single most likely way this happens
for real — and it is a reasonable thing to do in the moment. What is not
reasonable is that it silently removes a whole suite from the evidence while CI
keeps reporting success, which is the precise failure O23 exists to close, one
step removed.

## Approach

A **positive** assertion closes the class a negative one cannot:

1. A package-level counter in `testenv` — `Started()` increments from each helper
   after a container actually runs.
2. `testenv.AssertRanContainers(m)` called from a `TestMain` in each of the three
   packages: when `Required()` and the package started **zero** containers, exit
   non-zero naming the package.

The distinction worth preserving in the message: "no runtime" (O23's case) and
"runtime fine, nothing asked for a container" are different failures with
different fixes, and a single message for both will send people the wrong way.

## Also in scope — the ckm3 mechanism O23 made redundant

`identity/ckm3_checkpoint_test.go` panics in `t.Cleanup` when `STELOIT_CHECKPOINT`
is set and the test skipped. Reproduced: with `STELOIT_CHECKPOINT=1`,
`STELOIT_REQUIRE_CONTAINERS` unset and no runtime, it **panics out of cleanup,
which aborts the whole test binary and discards every other `internal/identity`
result.** A clean failure would report one test; this loses ~100.

It predates O23 and O23 does not break it (both env combinations verified), but
O23 now covers the container case properly, so route it through `SkipOrFail` and
drop the panic. `STELOIT_CHECKPOINT` is not in `ci.yml` — only in task verify
blocks and `.claude/skills/verify` — so CI never hits this today.

## Acceptance criteria

- [ ] With the gate armed, a runtime present, and every container test in a
  package skipped, that package FAILS.
- [ ] The message distinguishes "no runtime" from "started no containers".
- [ ] `ckm3_checkpoint_test.go` no longer panics out of `t.Cleanup`; a skipped
  checkpoint fails that test without discarding the rest of the package.
- [ ] Local runs with the var unset are unchanged.
