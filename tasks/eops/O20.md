## Goal

O16 closed the ingress. It shipped nothing to find rows already written through it.

## Why

Before O16, `POST /v1/estimates` with `postgres {storage_gb: 1e18}` returned 200
with `monthly_total_cents = -5340232221128652948`, and `POST .../services`
persisted that into `monthly_estimate_cents`. Measured live on `main` at
`28fa30f`, so the window was open for that whole period.

After O16 the platform is **correctly fail-closed** on such a row — and that is
precisely why this task exists. **The failure mode changed from
silent-permissive to silent-BLOCKING:**

- a service with an out-of-range stored price gets a permanent **409 on every
  PATCH** (`services.go`), and
- its org gets a permanent **409 on every create** if it has a budget row,
  because `enforceBudget` re-validates `committed` through `money.FromInt`.

Both are the right behaviour. Both are escapable only via "contact support", and
support has no query to run.

## Approach

1. **Detection.** The bound is `money.MaxMonthly` = 3,443,612,618,300:

   ```sql
   SELECT id, org_id, monthly_estimate_cents FROM services
    WHERE monthly_estimate_cents < 0 OR monthly_estimate_cents > 3443612618300;
   ```

   Do the same for estimate rows' stored `lines` totals, which `PricedShapes`
   now refuses to decode.

   **Per ROW, not per org.** The `committed` re-validation is on the AGGREGATE,
   so two poisoned rows of near-opposite sign sum back into range, pass
   `FromInt`, and the cap is then evaluated as if neither existed. Contrived, but
   it is the difference between "no row is out of range" and "the sum is in
   range".

2. **Remediation — decide, do not guess.** Re-pricing from the current table is
   the obvious move, but it silently changes a number a customer may have been
   shown. Nulling the column makes the service un-PATCHable in a different way.
   Either is a founder-visible decision if any real row exists.

3. **Run it before deciding how much to build.** If production has zero affected
   rows, the answer is a documented query in `docs/dev/` and nothing more. The
   shape of this task depends entirely on the count.

## Also worth closing while here

`identity/budget_http.go` reads `SumOrgMonthlyEstimate` for `used_percent`
WITHOUT the `FromInt` re-validation `enforceBudget` applies. Display-only, but
the same wrapped row that 409s a create renders an absurd percentage in Billing —
one representation of "the committed run-rate is validated" is covered, the other
is not.

## Acceptance criteria

- [x] The detection query exists somewhere support can find it (`docs/dev/`).
- [x] It has been RUN, and the affected-row count is recorded in this task.
- [ ] If the count is non-zero, a remediation is chosen and applied, with the
  choice recorded.
- [x] The 409s stay fail-closed — this task must not weaken them to make a
  poisoned row usable.

## Outcome

`docs/dev/money-range-audit.md` — the queries support runs, plus what the symptom
means. The framing that matters for whoever picks up a ticket: **the failure mode
inverted.** Before O16 a poisoned row silently *disabled* the org's spend cap;
after O16 the same row makes the platform fail closed with a permanent 409 on
every create and every PATCH. Both are correct; only the second generates a
support ticket.

**Five storage locations, not one.** O20 as filed named
`services.monthly_estimate_cents` and the estimate `lines`. There are four money
COLUMNS (`services.monthly_estimate_cents`, `estimates.total_cents`,
`budgets.limit_cents`, `usage_events.rate_cents`) plus the `estimates.lines`
jsonb. A query checking one of them finds one class of poisoned row and reports
the database clean.

**The queries are TESTED, not just written** —
`TestO20DetectionQueriesFindPoisonedRows` seeds a poisoned row per location and
asserts each query finds it, and asserts a clean row is *not* flagged. It
extracts the SQL from the doc by parsing its ```sql blocks rather than retyping
it, so the runnable version and the copy-pasted version cannot drift.

That test earned its place immediately: my first documented query referenced
`services.org_id`, **which does not exist** — the chain is
`services → environments → projects → org_id`, two hops. A query that plausible
and that wrong would have been run once against production, returned an error or
nothing, and been read as "clean".

**Mutation-verified:** widening the bounds so the scalar sweep matches nothing →
red; deleting the jsonb query so only the scalar one remains → red.

**Per row, not per org**, and the doc says why: `enforceBudget` re-validates the
AGGREGATE, so two poisoned rows of near-opposite sign sum back into range and the
cap is evaluated as if neither existed.

**Not done, and it is not mine:** the queries have not been run against
production — I have no production access, and remediation (re-price vs null the
column) changes a number a customer may have been shown. The doc says to record
the count and the decision here. `files:` widened to
`internal/reconcile/` because it is the only package with a migrated `realDB`.
