## Goal

O16 closed the ingress. It shipped nothing to find rows already written through it.

## Why

Before O16, `POST /v1/estimates` with `postgres {storage_gb: 1e18}` returned 200
with `monthly_total_cents = -5340232221128652948`, and `POST .../services`
persisted that into `monthly_estimate_cents`. Measured live on `main` at
`28fa30f`, so the window was open for that whole period.

After O16 the platform is **correctly fail-closed** on such a row — and that is
precisely why this task exists. **The failure mode changed from
silent-permissive to silent-BLOCKING:**

- a service with an out-of-range stored price gets a permanent **409 on every
  PATCH** (`services.go`), and
- its org gets a permanent **409 on every create** if it has a budget row,
  because `enforceBudget` re-validates `committed` through `money.FromInt`.

Both are the right behaviour. Both are escapable only via "contact support", and
support has no query to run.

## Approach

1. **Detection.** The bound is `money.MaxMonthly` = 3,443,612,618,300:

   ```sql
   SELECT id, org_id, monthly_estimate_cents FROM services
    WHERE monthly_estimate_cents < 0 OR monthly_estimate_cents > 3443612618300;
   ```

   Do the same for estimate rows' stored `lines` totals, which `PricedShapes`
   now refuses to decode.

   **Per ROW, not per org.** The `committed` re-validation is on the AGGREGATE,
   so two poisoned rows of near-opposite sign sum back into range, pass
   `FromInt`, and the cap is then evaluated as if neither existed. Contrived, but
   it is the difference between "no row is out of range" and "the sum is in
   range".

2. **Remediation — decide, do not guess.** Re-pricing from the current table is
   the obvious move, but it silently changes a number a customer may have been
   shown. Nulling the column makes the service un-PATCHable in a different way.
   Either is a founder-visible decision if any real row exists.

3. **Run it before deciding how much to build.** If production has zero affected
   rows, the answer is a documented query in `docs/dev/` and nothing more. The
   shape of this task depends entirely on the count.

## Also worth closing while here

`identity/budget_http.go` reads `SumOrgMonthlyEstimate` for `used_percent`
WITHOUT the `FromInt` re-validation `enforceBudget` applies. Display-only, but
the same wrapped row that 409s a create renders an absurd percentage in Billing —
one representation of "the committed run-rate is validated" is covered, the other
is not.

## Acceptance criteria

- [ ] The detection query exists somewhere support can find it (`docs/dev/`).
- [ ] It has been RUN, and the affected-row count is recorded in this task.
- [ ] If the count is non-zero, a remediation is chosen and applied, with the
  choice recorded.
- [ ] The 409s stay fail-closed — this task must not weaken them to make a
  poisoned row usable.

## Found by

O16's architecture review, 2026-08-23 ("the branch closes the ingress but ships
no detection or remediation for rows main's live defect may already have
written"), with the silent-blocking framing added by its QA review.
