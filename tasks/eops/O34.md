## The mechanism — named and reproduced, not inferred from suggestive bytes

Three container-backed tests were each written off as flaky. One preserved its
output, and that one is the whole thread:

    migrate init: failed to open database: failed to connect to `user=app database=app`:
      [::1]:52381 (localhost): dial error: connect: connection refused
      127.0.0.1:52381 (localhost): failed to receive message: invalid body length:
        expected at most 1073741822, but got 1414811691

`1414811691` is not a length. It is `0x5454502b` — the ASCII bytes **`TTP+`**. A
Postgres client had read someone else's bytes and taken four of them as an int32
message length. *(An earlier note in this repo decoded these as "TSEU". That was
wrong; the correct decode is above and it points at HTTP, which is what made the
mechanism findable.)*

### Reproduced

A harness started **168 Postgres containers** in waves of 12 and, for each,
dialled the published port and sent a Postgres `SSLRequest` — to which every
Postgres answers a single byte:

    RESULT started=168 nonPostgres=3 errors=0 distinctPorts=168 portsReused=0

**3 in 168 (~1.8%)** were answered by something that is not Postgres:

| port | answered | |
|---|---|---|
| 54042 | `48 54 54 50 2f` = `HTTP/` | an HTTP server |
| 54120 | `48 54 54 50 2f` = `HTTP/` | an HTTP server |
| 54167 | `01 00 00 00` | binary — identified below |

**`portsReused=0` is the load-bearing negative.** No port was ever handed to two
of our containers, so this is *not* testcontainers reuse, not a stale container,
and not a fixed port mapping — the three hypotheses that would have pointed at
our code.

### The squatter, named

    $ lsof -nP -iTCP:54167
    rapportd 622 hashir 10u IPv4 TCP *:54167 (LISTEN)
    rapportd 622 hashir 11u IPv6 TCP *:54167 (LISTEN)

    $ ps -o lstart -p 622
    Mon Aug 17 13:33:28 2026        # the run was Aug 25

`rapportd` is macOS Continuity/AirDrop. It had held that port **for eight days
before the run**. The container did not take a port from rapportd; the VM
published onto a port the host had already given away.

### Why the host lets that happen

Under colima the Docker daemon runs in a VM. It picks a port *inside the VM*, and
lima's hostagent then opens a matching host-side listener per published port —
**54 `ssh -L` listeners** were live during one run. The host port is drawn from
the same ephemeral range every other process uses
(`net.inet.ip.portrange` = **49152–65535**; the failing port 52381 is inside it)
and **nothing reserves it on the host**. When a host process already holds that
number, the forward loses and a connection to `127.0.0.1:<port>` reaches the
squatter.

That also explains the preserved error's shape: `[::1]` refused while `127.0.0.1`
answered garbage, because that squatter had bound IPv4 only.

### Scope: this is a developer-machine mechanism

CI runs on `ubuntu-latest` with native Docker, where `dockerd` `bind()`s the
published port directly and therefore reserves it. The VM-forward race does not
exist there. **So this explains local flakes and does NOT explain a CI failure.**

## Exposure is linear in container count, and the count is large

Measured with `docker events` during a real run: **127 containers for two
packages** (`reconcile` + `platform/db`). Every test that needs a database starts
its own. At ~1.8% per container, that is not a rare event — it is a coin flip
several times per full run.

## Done here

`testenv.RequirePostgresPeer` proves the published port is served by *that*
container's Postgres before any test uses it, and `CheckPostgresPeer` is split out
as a testable core **because a guard whose only entry point calls `t.Fatal` can be
asserted to stay quiet but never to fire** — the exact defect it exists to prevent
one level up. Wired into all three integration helpers.

It is a **diagnosis, not a retry**: it does not reconnect, restart, or paper over
anything. It converts a failure that reads like a Postgres protocol bug into one
that names the cause and runs `lsof` to name the process holding the port.

Regression-tested both ways, against both measured behaviours:

| case | result |
|---|---|
| squatter answering `HTTP/` (2 of 3 collisions) | refused, message names the cause |
| squatter accepting then silent | refused, message says so |
| a real Postgres container | accepted — the guard is inert |

## Still open — the structural fix

The guard makes the failure legible; it does not make it rarer. **Reducing the
container count is what reduces exposure**, and it is linear: a shared container
per package with per-test database isolation takes 127 containers per two packages
to ~2, a ~60× cut, and would also address the 250–400 s `internal/identity` runtime.

That refactor touches four packages and deserves its own review round rather than
riding along here.

## Q11 — kept open, and here is why it is NOT closed by this

`Q11`'s failure output **was not preserved**, and its `verify:` runs
`-count=20` on a single test in isolation — a shape that cannot produce this
collision, which needs many concurrent containers. This mechanism is a *candidate*
for Q11, not an explanation of it. Closing it on this evidence would be exactly the
"a citation is a claim" error the mistake bank records.

## Acceptance criteria

- [x] The mechanism is **named**, not guessed — reproduced, with the squatting
      process identified by `lsof` and its start time predating the run.
- [x] A verification mechanism exists and is proved to fire, not just to stay quiet.
- [x] Q11 kept open, with the reason it is not covered.
- [ ] The structural fix: shared container per package, per-test database isolation.
- [ ] A re-run is not evidence: any future occurrence is triaged against this
      diagnosis before the word "flake" is used.
