## The measurement

Every test needing a database calls `tcpostgres.Run` and gets its own container.
Counted with `docker events` during a real run of **two** packages
(`internal/reconcile` + `internal/platform/db`):

    127 create, 126 destroy

`internal/identity` alone runs 250–400 s, essentially all of it container startup
and migration. A full `go test ./...` on the api module is several hundred
containers.

## Why it is worth changing, with the evidence from O34

O34 reproduced a failure mode where a published host port is answered by a
*different process*: 3 of 168 containers (~1.8%), with the squatter named
(`rapportd`, holding `*:54167` since eight days before the run). The mechanism is
colima publishing onto a host port nothing reserved.

**Exposure to that is linear in container count.** O34's guard makes the failure
legible — it names the cause and the process — but it does not make it rarer.
Reducing 127 containers per two packages to ~2 is a ~60× cut in exposure, and the
same change is the only realistic way to move the runtime.

Two independent reasons, one change. Neither is a reason to rush it.

## Why this is NOT part of O34

O34 is a local-flake diagnosis: one new file, one guard, its tests. This is a
cross-cutting change to how four packages get a database, and it can break every
integration test in the repo if the isolation is wrong. Bundling them would have
made a small, verifiable fix unreviewable — and would have put an architectural
refactor inside a PR whose subject is a `t.Fatal` message.

## The design question this task must answer first

**What is the isolation boundary?** The options are not equivalent and the choice
determines whether this is safe:

- **Database per test** (`CREATE DATABASE` from a template) — strongest isolation,
  and migrations run once into the template rather than once per test, which is
  where most of the 400 s goes. Cost: connection strings differ per test, and
  anything caching a pool must not leak across them.
- **Schema per test** (`CREATE SCHEMA` + `search_path`) — cheaper, but every query
  that names a schema explicitly, and every migration that does, becomes a trap.
- **Truncate between tests** — cheapest, and wrong here: tests run in parallel
  within a package, so a shared mutable database is a race, not an optimisation.

Recommended: **database per test from a migrated template**, because it keeps the
current per-test guarantee exactly (a test sees only its own writes) while moving
migration cost out of the per-test path. The recommendation is not the ruling —
measure the template-clone cost before committing.

## Acceptance criteria

1. Container count for a full `go test ./...` on `services/api`, measured the same
   way (`docker events`), is reported **before and after** in the PR. A claim
   without both numbers is not evidence.
2. Runtime for `internal/identity` reported before and after.
3. **Isolation is proved, not assumed**: a test that writes a row and a sibling
   that asserts it cannot see it, running in parallel, and failing if the
   isolation boundary is removed. This is the one that matters — a shared
   container whose isolation silently leaks turns every downstream test into a
   flake with a new mechanism.
4. `testenv.RequirePostgresPeer` (O34) still runs against whatever container the
   suite ends up using — the guard must not be lost in the refactor.
5. No test loses coverage: the package list and test count are unchanged.

## Notes

is *how a test gets a database*, and nothing else.
