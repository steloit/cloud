## The defect

`invoice.Close` reads a rollup that a **late span edge can still change**. There
is no draft → grace → finalized state, so a closed invoice a customer has already
seen can move underneath them, and nothing records that it did.

## What the market does — grace period, then hard close

Every serious engine defines the same three states and disagrees only on the
window:

- **Stripe**: 1 hour default finalisation grace, 72h max. Beyond it, "any usage
  reported beyond the grace period isn't included". A documented sharp edge:
  under a mid-cycle price change, late usage appears on **neither** the current
  nor a subsequent invoice — it is silently lost.
- **Metronome**: draft "continuously updates to reflect real-time spend"; 24h
  grace; "once an invoice is finalized… no further changes can be made, even if
  additional usage is reported". Recovery is **void + regenerate**, not amend.
- **Lago**: late events land in the correct historical period by `timestamp`; if
  the invoice is finalized they are dropped for one-off meters and **carried
  forward** for recurring ones.
- **Orb** restates — and documents the limit: not recommended once a credit
  ledger has moved, "because Orb is not able to reflect changes to deductions as
  a result of backfilled events in issued invoices".

Consensus: **grace, then immutable.** Restatement exists and every vendor that
offers it says it stops being clean once money has moved.

## Acceptance criteria

1. An invoice has an explicit state: `draft` → `grace` → `final`. `final` is
   immutable, enforced in the database the way `usage_events` enforces
   append-only — not by convention in application code.
2. A usage event arriving after `final` is **not silently dropped**: it is
   recorded and either carried forward or surfaced. Which one is a decision to
   state, not to leave to whichever branch runs.
3. The grace window is a named constant with the reasoning beside it, not a
   literal.
4. A test finalizes an invoice, emits a late event, and asserts both that the
   invoice did not change and that the event was not lost.

## Notes

Model-independent, and a correctness problem under fixed pricing too. Depends on
O30 only because both touch the same rollup arithmetic and doing them in the
wrong order would mean writing the close twice.

## Outcome

### The defect was not what the task assumed, and the real one is worse

The task said "`invoice.Close` reads a rollup that a late span edge can still
change". Investigating found the invoice row is already immutable — `ON CONFLICT
(org_id, period) DO NOTHING`, and a re-close returns the frozen row unchanged.

**`quota_usage` was not.** `Rollup` upserts with `DO UPDATE SET used =
EXCLUDED.used`, and `GET /orgs/{org}/usage?month=…` takes a **caller-supplied
month** and calls `Rollup` on the **read path**. So a customer viewing last
month's usage rewrote the rollup their invoice was computed from. Measured before
the fix:

    closed:                              invoice total=8640000, rollup used=3600s
    after a late edge + one GET /usage:  invoice total=8640000, rollup used=14400s

10800 seconds billed by nobody, and two customer-facing surfaces permanently
contradicting each other. **Not a race — the normal read path**, reachable by a
GET.

### The boundary is the invoice, and the database enforces it

`quota_usage_no_write_after_close` refuses UPDATE and DELETE on any period with an
invoice. A `WHERE` clause would have been caller discipline — the next query, a
support script or a backfill silently bypasses it — and this table is the *input
to an invoice*, so its immutability must not depend on every future writer
remembering. Same idiom as `usage_events_append_only`, already proven here.

The application *also* checks (`PeriodIsClosed`) so the read path keeps working:
erroring inside `Rollup` would make viewing any past month a permanent 500 with a
remediation that cannot succeed — the blast radius O30 documented. **The app asks
politely; the database refuses regardless.**

### Late usage is carried forward, not dropped and not restated

The three answers in the market are not equivalent. Stripe drops past its grace
window — and documents that under a mid-cycle price change the late usage lands on
**neither** the current nor a later invoice. Metronome voids and regenerates. Lago
carries forward for recurring meters.

Carry-forward is the only one that neither loses money silently nor changes a
number the customer has already seen: **dropping is invisible under-billing, and
restating destroys what "closed" means.** `usage_carry_forward` records the delta
against the frozen figure with its origin period, and `invoice.Close` bills it as
a named line — *"late usage from 2026-07"*, with `usage_ref`
`carry:service_span_seconds:2026-07`.

Idempotency is **by construction, not by a guard**: the amount is a delta against
a frozen number, so recomputing it yields the same delta however many times the
period is re-read. Five recomputes produce one row of 10800s, not five or 54000s.

Rows are marked applied **only after** the invoice that carries them exists, so a
failure anywhere in the close leaves them unapplied and they land on the next one
rather than vanishing.

## Review round 1 — four money defects in my first design

Every one was reachable by ordinary usage, and three of them lost or froze money.

**1. A second late arrival was silently discarded.** The ledger was keyed
`(org, meter, origin)` and upserted `ON CONFLICT … WHERE applied_period IS NULL`.
Once the first carry was billed the `WHERE` failed, the `:exec` discarded the row
count, and nothing errored — 14,400 s on no invoice, ever. **Precisely the Stripe
failure mode this design was chosen to avoid.**

**2. The remainder was computed against the frozen row alone**, never against
`frozen + already-carried`, so even a working upsert would have re-carried the
first shortfall.

Both fixed by making the ledger **append-only, one row per detection**:

    remainder = recomputed − frozen − Σ(already carried for this origin)

A remainder of zero records nothing, so repeated recomputes are idempotent **by
construction** rather than by a conflict clause, and an nth late arrival appends
its own remainder. No unique key is needed, because no row is ever revised.

**3. A mixed-sign remainder poisoned every future invoice.** The guard was
`deltaSeconds <= 0 && deltaCents <= 0`, so a remainder positive on one axis and
negative on the other wrote `rate_cents < 0`; `Close` then refused to total it —
permanently, for that org, with no query able to repair the row. The trigger is a
late `close` for a span the frozen rollup credited to the period end, **the
commonest late shape there is**. The axes are independent now, and a negative
remainder becomes a `credit`.

Related: an over-bill previously returned `nil` with no row and no log, so
under-billing was carried forward with a WARN while over-billing — the customer's
money — vanished. **The asymmetry was the defect.** Credits are recorded and
surfaced but deliberately **not auto-applied**: issuing a refund is commercial, and
the engineering obligation is only that it cannot be invisible.

**4. The freeze covered two of the three ways a rollup can change.** The trigger
was `BEFORE UPDATE OR DELETE`, so **INSERT into a closed period succeeded** — a
meter with no row at close time could still gain one behind a frozen invoice — and
`TRUNCATE` succeeded too, because a `FOR EACH ROW` trigger never fires for it. The
`usage_events_append_only` idiom this copied is for a table where INSERT is
*legitimate*; that reasoning does not transfer to a freeze. Now
`BEFORE INSERT OR UPDATE OR DELETE` plus a statement-level `BEFORE TRUNCATE` arm.

### Majors

- **`MarkCarryForwardApplied` was a blanket `WHERE applied_period IS NULL`**, so
  every row unapplied *at mark time* was stamped billed — including ones created
  after the read, and ones skipped for a zero amount. `GET /usage?month=<closed>`
  calls `Rollup` on the read path, so any `billing.view` user could open that
  window. Now `id = ANY(...)`, and only ids that produced a line.
- **A carry-forward could land on an *earlier* invoice** — measured, a June
  invoice carrying "late usage from 2026-07". Now `origin_period < $2`.
- **`Close` accepted any period**, so closing early silently converted the rest of
  the month into "late usage". Now refused unless the period has ended.

### Two tests that did not discriminate

- `TestAnEdgeThatLandsBeforeClose…` **never called `Rollup` after `Close`**, so it
  never reached `carryForward`. Review mutation-verified: disabling carry-forward
  entirely left it PASS. Fixed — it now rolls up after close and asserts zero.
- `TestCarriedUsageIsBilledOnce…` proved "not on the *next* invoice", not "once".
  Duplicating `carried` inside `Close` left the **whole suite green**, because
  `strings.Contains` cannot see a duplicate. It now counts the `usage_ref` and
  asserts the exact total.

## My own adversarial pass — four more, found before re-review

The instruction was not to treat four RED mutations as sufficient. Hunting the
named failure modes turned up four more, three of them money.

**Two concurrent closes both billed the same carry.** `UnappliedCarryForward` and
the mark were separate statements with no transaction, so both closes read the
same rows, both wrote lines, and the loser's mark was a **silent no-op** — the
`:exec` discarded the row count. `Close` is now **one transaction**, and the mark
became `ClaimCarryForward`: a single atomic `UPDATE … RETURNING`, so only rows this
close actually **took** come back, and **only those are billed**. A failure after
the claim rolls it back rather than stranding money as billed-but-invoiceless.

**Deleting an invoice un-froze its period.** The freeze is defined by the
invoice's existence, so removing the evidence of the boundary removed the
boundary — and orphaned every carry referencing it as origin. `invoices` is now
append-only too: DELETE and TRUNCATE refused, and of the columns only `status` may
change (open → paid/void). Everything that decides the money is frozen.

**A meter `carryForward` cannot account for was silently skipped.** It handles
`service_span_seconds` only, while `quota_usage.meter` already names
`egress_bytes | build_minutes | events | ai_requests` and ADR-0018 ratifies an
expanded set. Carrying one meter and dropping another is the invisible
under-billing this whole task exists to prevent, so it now **refuses loudly** and
the error says what extending it requires.

**The sign matrix is stated exhaustively** rather than left to whichever branch
runs: zero, +/+, −/−, **+seconds/−money**, **−seconds/+money**. Each asserts the
row count, the kind, and — the part that matters — that **every later invoice
still closes**, because a mixed-sign remainder writing a negative *charge* was the
poison pill.

### Two of my own tests did not discriminate, and mutation testing said so

- The concurrency test **spawned two goroutines and counted lines**. They
  serialised, so the second close read nothing and the mutation survived. *A test
  whose outcome depends on scheduling proves nothing about the mechanism.*
  Replaced with a deterministic one: claim the row out from under `Close`, and
  assert a second claim of the same id returns zero rows.
- That replacement **still** did not catch "bill what was read, not what was
  claimed", because an externally-claimed row leaves `carried` empty. The case that
  discriminates is a carry **read but deliberately not claimed** — a zero-amount
  row — which under the mutation emits a phantom line *and* stays unapplied forever.

### Mutation protocol, tightened

A result counts only when the baseline is independently green, the mutation
**compiles**, and the expected test discriminates. Two runs were thrown out under
that rule: one where `grep -c "^--- FAIL"` read a non-compiling mutation as a
survivor, and one where a shared copy carried a broken restore between runs. Every
mutation below ran in its own fresh copy.

| mutation | result |
|---|---|
| claim reverts to a blind mark | **RED** |
| bill what was READ, not CLAIMED | **RED** (after the discriminating test was added) |
| sign guard back to `remSeconds < 0 && remCents < 0` | **RED** |
| unaccountable meter skipped | **RED** |
| invoice DELETE allowed | **RED** |
| trigger back to `BEFORE UPDATE OR DELETE` | **RED** |
| remainder ignores already-carried | **RED** (2 tests) |
| every carry billed twice on one invoice | **RED** |

Sixteen adversarial tests. `services/api` fully green.

### The trade I flagged for review, resolved rather than accepted

Refusing an unaccountable meter is fail-closed — but `GET /usage?month=…` calls
`Rollup` on the read path, so a second meter would turn viewing any closed month
into a permanent 500. **Neither outcome is acceptable**: silently dropping is
invisible under-billing, and a customer-facing 500 is the blast radius O30
documented.

So the tripwire moved to CI. `SpanMeter` is now the single owner of the name
(ADR-0014), and `TestRollupWritesOnlyTheMeterCarryForwardCanAccountFor` reads
`rollup.go` and fails if `Rollup` ever writes a meter `carryForward` cannot
handle — **before it ships, rather than on someone's billing page**. The runtime
refusal stays as the backstop it should be: correct, and in practice unreachable.

Mutation-verified: making `Rollup` write `egress_bytes` fails CI with a message
naming what to extend.
