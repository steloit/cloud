## Goal

`T3.4` (CNPG driver behind the provisioner interface) is `priority: critical` and
`status: ready`, so it sits at the **top of the ready queue** — the first thing
anyone picking up work would take. It shipped a month ago.

## What was actually true

- Merged as **PR #298** (`205aae1`, "T3.4: CNPG driver behind the provisioner interface").
- Every acceptance criterion in its enriched body is checked `[x]`.
- It has a full `## Outcome`.
- All **17** tests named in its `tests:` frontmatter exist and pass.
- `services/cell-agent` builds, vets and tests clean — its `verify:` block passes
  verbatim.

Two things kept it looking unstarted:

1. **The status flip never happened** (protocol step 6 asks for it in the same
   PR). Same class as O24's T1.3 and US-10.3 — but those were `in-progress`, so
   O24's sweep found them. This one was `ready`, which reads as "not started" and
   is invisible to that check.
2. **The spec-author enrichment left the original stub tail in place.** The file
   carried a SECOND `## Acceptance criteria` section near the end with one
   unchecked item and the marker *"**Stub** — run the spec-author skill to enrich
   to `ready` before starting"*. A reader scrolling to the bottom sees a stub;
   the top of the same file is a completed task.

## Why it matters more than one wrong field

The board is a generated view of these files. A `critical`/`ready` item is the
strongest signal the queue can emit, and this one pointed at finished work — so
the actual next MVP item (**US-3.3a**, nothing creates the env namespace or its
D7 default-deny policies) sat behind a phantom.

## Is it systemic?

Checked, and **no** — this is the only one. I swept every `ready` task with a
non-empty `tests:` list and compared it against the tests that actually exist in
the tree: T3.4 is the sole task where all named tests are already present. That
bounds the problem rather than leaving it open.

The check is worth keeping, though, and it is cheap: *a `ready` task whose every
named test already exists is either done or mis-specified.* Recorded as a
candidate for **O18**, which owns making `validate.mjs` notice this family of
drift.

## Outcome

`T3.4` → `done`, stub tail removed, and a dated note added to the file recording
what was corrected and what was verified first. `validate.mjs` OK; the ready
queue drops from 21 to 20 and its top entry is now real work.
