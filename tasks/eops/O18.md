## Goal

Make a duplicate work item detectable, so two reviewers cannot silently file the
same defect twice and have the queue carry both as `ready`.

## Why — Q10 and O14

Q10 (`tasks/eqa/Q10.md`) and O14 (`tasks/eops/O14.md`) described the **same
defect**: the same data race, in the same file
(`services/api/internal/reconcile/reconcile_test.go`), with the same fix
(one mutex over the shared map). Neither referenced the other.

They were filed a day apart by two different review sweeps — US-3.7's
architecture review filed Q10, US-3.8's filed O14, both on 2026-07-27 — and the
queue carried **both as `ready` for a month**. Whoever picked one up would have
done the work; whoever picked up the other second would have found it already
done and had to work out why.

Nothing catches this today:

- `validate.mjs` checks frontmatter, deps and caps across 215 tasks. It has no
  notion of two tasks pointing at the same defect.
- The `reviewer` and `qa` agent prompts say to file follow-up tasks for findings.
  Neither says to search the existing queue first.

This is cheap to make much less likely and expensive to keep rediscovering: the
same *defect class* was also found twice (see the mistake-bank entry in
`contexts/canon-testing.md`), which is the more costly version of the same gap.

## Approach

Smallest useful thing first — this is a `low` priority task and should not grow
into a similarity engine:

1. **A warning, not an error, in `validate.mjs`.** For tasks in a non-terminal
   status (`stub`/`ready`/`in-progress`), report any pair whose `files:` globs
   have a non-trivial intersection AND whose titles share enough distinctive
   terms to be worth a human glance. Warn — a false positive must not fail CI.
2. **One line in each reviewer prompt:** before filing a follow-up task, grep
   `tasks/` for the file you are about to name. That is where the cost is
   actually paid, and it costs one command.

**A second, cheaper check worth adding at the same time (from O27):** a task in
`ready` whose every named `tests:` entry ALREADY EXISTS in the tree is either
already done or mis-specified. T3.4 sat at `critical`/`ready` for a month with
all 17 of its named tests present and passing, having shipped in PR #298 — the
top of the ready queue pointing at finished work. The check is a grep, and unlike
title similarity it has no false-positive problem worth worrying about.

Do NOT attempt semantic dedupe. The Q10/O14 pair shares an exact file path,
which is the signal that would have caught it.
