## Goal

`fakeTrans` and `fakeQ` guard the SAME map with TWO different mutexes. Give the
map one owner, so `go test -race ./internal/reconcile/` is stable.

## Why

`fakeQ.services` is written by `fakeTrans.Transition` under `fakeTrans.mu`
(`reconcile_test.go:100,107`) and read by `fakeQ.GetService` under `fakeQ.mu`
(`reconcile_test.go:76`). Neither lock excludes the other, so
`TestConcurrentWritebackAppliesOnce` — which exists precisely to drive eight
concurrent writebacks — races on every run that schedules unluckily.

Reproduced at `-count=20`, three runs, three failures:

    WARNING: DATA RACE
    Write at 0x00c000410090 by goroutine 29:
        reconcile_test.go:107   (fakeTrans.Transition, holding fakeTrans.mu)
        reconcile.go:199
    Previous read at 0x00c000410090 by goroutine 35:
        reconcile_test.go:76    (fakeQ.GetService, holding fakeQ.mu)
        reconcile.go:164

The production code in `reconcile.go` is NOT implicated: both frames reach the
fixture through ordinary calls, and the conflicting accesses are both in the
test file.

**Why it has gone unnoticed.** CI runs `go test ./...` with no `-race`
(`ci.yml:96`), so the detector never runs there at all. Locally it needs
iteration or a loaded machine to schedule the interleaving — a single
`-run TestConcurrentWritebackAppliesOnce` passes.

**Why it matters more than a flaky test.** A data race is undefined behaviour,
so every OTHER test in this package that uses `newFixture()` is reading results
from a fixture with no defined state under concurrency. The package's job is
verifying that the reconciler applies an edge exactly once; a fixture that
cannot count reliably is not evidence for that. The observable symptom (a flake)
is much smaller than the epistemic one.

## Approach

Delete `fakeTrans.mu` and have `Transition` take `t.q.mu` instead — one mutex,
one owner, no lock-ordering question since nothing takes both. Confirm the fix
with `-count=20`, not a single run.
