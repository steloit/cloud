## Goal

Pin the composition root's background workers, so removing one fails a test.

## Why

`cmd/api` has no test files. Deleting either of these lines leaves
`go test ./...` fully green:

```go
go idemSvc.RunSweeper(ctx, time.Hour, logger)          // main.go:268
go prov.RunOverrideExpiry(ctx, 5*time.Minute, logger)  // main.go:272
```

Both were verified by mutation (US-3.8 QA, 2026-07-27, for the second one).

The behaviour of each worker is well covered — `TestAPinCreatedAfterBootStillExpires`
pins that the ticker sweeps, and the idempotency tests drive `RunSweeper`
directly. What nothing covers is that **anything ever calls them in
production**. Every test starts the goroutine itself. So the failure mode is the
whole feature dark in production with a green suite, which is exactly the shape
US-3.8 spent three review rounds removing from the code it could reach — the
composition root was simply outside every test's reach.

Consequences if it happens: manual pins never expire (capacity provisioned
indefinitely, priced but "temporary"), and idempotency records outlive their 24h
window and grow without bound.

This is a repo-wide gap, not US-3.8's: the idempotency sweeper has identical
exposure and predates it. The middleware chain by contrast IS pinned —
`identity_integration_test.go`'s world asserts "a middleware dropped from
production fails here" — so the precedent for covering the composition root
exists; it just does not extend to background goroutines.

## Approach

Do NOT assert on source text. Extract the workers into a value the wiring
returns and the test can enumerate:

```go
// backgroundWorkers is every long-lived goroutine the API starts. Adding one
// here and starting it below is the whole registration; a worker that is not
// in this list is not running in production.
func backgroundWorkers(...) map[string]func(context.Context) { … }
```

`main` ranges over it and starts each; the test asserts the expected names are
present and that each is non-nil. That makes deletion a compile-or-assert
failure rather than a silent no-op, without pinning the literal text of `main`.

Consider whether `newWorld` in `identity_integration_test.go` should start the
same registry, so integration tests exercise production's worker set rather than
a hand-assembled one.

## Outcome

**The gap was three times wider than the task states.** O15 names two workers —
`idemSvc.RunSweeper` and `prov.RunOverrideExpiry`. `main` was starting **six**
bare `go x.Run(ctx, …)` goroutines, and deleting any of them left
`go test ./...` fully green:

| worker | what goes dark if the line is deleted |
|---|---|
| `mailer.outbox` | no transactional email is ever sent |
| `subscription.lifecycle` | dunning and billing-anchor progression stop |
| `notify.outbox` | webhooks are recorded and never delivered |
| `notify.bell` | spine events never reach anyone's bell |
| `idempotency.sweeper` | the 24h window is a lie; the table grows unbounded |
| `provisioning.override-expiry` | pins never expire — capacity provisioned indefinitely, priced as "temporary" |

The two the task names are the two a prior sweep happened to mutate. The other
four have identical exposure, and two of them (`notify.*`) postdate the filing.

**The fix is the registry the task's Approach specifies.** `backgroundWorkers`
returns `map[string]func(context.Context)`; `main` ranges over it and starts
each, logging the name. Adding a worker there IS the registration — a worker not
in the map does not run. `main_test.go` asserts the map by name, in both
directions, so a deletion fails a test instead of being a silent no-op.

Two details worth stating:

- **The expectation is spelled out, not derived from the map under test.**
  Deriving it would assert the function against itself, which this repo has a
  mistake-bank entry for.
- **The test passes `nil` for every component.** The registry closes over them
  and the test never calls the closures; constructing real ones would need a
  database and would test the constructors rather than the wiring.

`idemSvc` moved earlier in `main` so every worker exists before the registry is
built. Nothing else about the composition root changed.

**Negative evidence**, in a `cp -R` copy under the scratchpad, deleted after:

- Delete `provisioning.override-expiry` from the registry → FAIL, twice: *"is not
  registered — it does not run in production"* and *"the registry holds 5 workers
  but this test knows 6"*.
- Set `idempotency.sweeper` to `nil` (the registered-but-does-nothing shape) →
  FAIL: *"registered but nil — main would start a goroutine that does nothing"*.

**Deliberately not done.** The task says to *consider* whether `newWorld` in
`identity_integration_test.go` should start the same registry. It should not:
starting six real ticking workers in every integration world buys coverage of
behaviour that is already covered directly, and pays for it in nondeterminism
across a suite that already runs 400+ seconds. The gap was registration, and
registration is what this closes.

**Evidence** (`DOCKER_HOST=unix://$HOME/.colima/default/docker.sock
TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
TESTCONTAINERS_RYUK_DISABLED=true`): `go build`, `go vet` clean;
`go test -count=1 -timeout 30m ./...` → **24/24 packages ok, 0 failures, 0
skips**, now including `cmd/api` (0.401s), which had no test files before.

Go's default per-package timeout is 600s, so the explicit `-timeout` O13 adds is
not theoretical headroom.
