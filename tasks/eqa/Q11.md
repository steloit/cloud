## The observation — and it is only an observation

`TestIdempotentCreateWebhookReplaysTheRevealOnceSecret` **failed once** during a
full `go test -race ./...` run on 2026-08-23. It passed in isolation, and passed
on a full-package re-run (293s).

**The failure output was not preserved.** So this task exists to reproduce and
diagnose, not to fix a known defect. Timing, container contention under `-race`,
and a real intermittent defect are all still live hypotheses, and the honest
statement is that nobody knows which.

## Why it gets a task rather than a shrug

It is a **reveal-once / idempotency** test, which is a load-bearing security
property: the guarantee is that a replayed create returns the ORIGINAL response
bytes including a secret that is shown exactly once. An intermittent failure
there is either a flaky test (a defect by the founder standard) or a real
concurrency bug in the reveal-once path. Both need an answer; neither is safe to
assume.

It is also the *third* concurrency-adjacent finding in `internal/identity`'s
neighbourhood in one week (Q10/O14's fixture race, and this), and that package is
the largest suite in the repo — a per-run failure rate low enough to look like
noise is exactly what nobody chases.

## Approach

1. **Reproduce with output preserved.** `-race -count=20` on the single test,
   then `-count=5` on the whole package under `-race`, capturing full output
   (`-v`, redirected, not piped through `tail`). If it will not reproduce in 50
   runs, say so and record the negative result — that is a finding too.
2. If it reproduces, decide which of the three it is before changing anything.
3. If it is contention rather than a defect, the fix is likely the same shape as
   Q10's: make the test deterministic rather than probabilistic.

Do NOT weaken the assertion to make it stable. The founder standard is that a
flaky test is a defect, and the property here is a security one.
