## The defect

`go test -race ./internal/reconcile/` fails:

```
WARNING: DATA RACE
--- FAIL: TestConcurrentWritebackAppliesOnce
```

The race is in the test's own doubles, not in `reconcile`: `fakeQ.GetService`
reads a map while `fakeTrans.Transition` writes one, both from the goroutines
the test spawns to exercise concurrent writeback. The doubles have no mutex.

Introduced by **US-3.6 (#300)** — mine — and already on the base branch.
`internal/reconcile` imports only `identity/store`, so nothing else reaches it.

## Why it matters

The test exists to prove that concurrent writebacks apply exactly once. Under
`-race` it does not run to completion, so the property it asserts is unproven
whenever the race detector is on — and the founder standard is explicit that a
flaky test is a defect, not a nuisance.

It also makes `go test -race ./...` unusable for `services/api`, which is the
invocation most likely to catch a real concurrency defect in the reconciler —
the component whose whole job is concurrent convergence.

## Fix

Guard the doubles' maps with a mutex (the pattern `internal/platform/idempotency`'s
`fakeStore` already uses after the same finding there), or give each goroutine
its own service id so the doubles are never shared.

Prefer the mutex: the shared-row case is the one the test is about.

## Acceptance criteria

- [x] `go test -race -run TestConcurrentWritebackAppliesOnce ./internal/reconcile/` passes.
- [x] `go test -race ./...` is clean for `services/api`.
- [x] The test still asserts exactly-once application (it must not be weakened
  to dodge the race — check it still fails if the writeback guard is removed).
- [x] Any other test double in the package sharing state across goroutines is
  audited at the same time.

## Outcome

**O14 filed the same defect** — same file, same two-mutex cause, same fix. Both
are closed here; O14's task file is in this task's `files:` for that reason.
Recorded as a finding rather than resolved silently (protocol §7). The two were
written from different sweeps (O14 from US-3.8's architecture review, Q10 from
US-3.7's) and neither cross-referenced the other, which is the more useful
observation: two independent reviewers each filed a task, and the queue carried
both as `ready` for a month.

**The fix.** `fakeTrans` guarded `calls`/`edges` with its own mutex while
read-modify-writing `fakeQ.services`, which `GetService` and `MarkObserved`
guard with `fakeQ.mu`. Two mutexes each covering half the accesses to one map
exclude nothing. `fakeTrans.mu` is deleted and `Transition` takes `q.mu`, so the
map has exactly one owner. No `fakeQ` *method* is called from `Transition`, so
there is no lock-ordering question — the comment on the struct says so, because
the next person to add a mutex here is the one who needs to know.

**Negative evidence.** Two mutations, in a `cp -R` copy under the scratchpad:

- Remove the fixture's exactly-once FROM-guard → `TestConcurrentWritebackAppliesOnce`
  FAILS at `-count=50`: *"concurrent writebacks applied the edge 2 times, want
  exactly 1"*. The test was not weakened to dodge the race (AC 3).
- Remove `Writeback`'s `rep.Status != svc.Status` pre-check → that test stays
  green, but `TestStatusWritebackIsIdempotent` FAILS: *"repeating an identical
  writeback must be a no-op, got illegal transition (already there)"*. Checked
  because a mutation nothing catches is a coverage gap; this one is covered.

**Audit (AC 4).** The package's two other concurrent tests need no change:
`TestConcurrentWritebackAppliesOnceAgainstRealPostgres` uses `realDB` and no
in-memory double, and `TestIdempotencyConcurrentDoubleSubmitHasOneWinner`
already guards its counters. `fakeQ.cells`/`rows` are read unlocked but never
written after construction.

**Evidence** (`DOCKER_HOST=unix://$HOME/.colima/default/docker.sock
TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
TESTCONTAINERS_RYUK_DISABLED=true`):

- Before: `-race -count=10 -run TestConcurrentWritebackAppliesOnce` → 3 DATA RACE
  reports (`reconcile_test.go:62, :76, :100, :107`), FAIL.
- After: same command at `-count=20` → `ok  ...internal/reconcile  1.807s`.
- `go test -race -count=1 -timeout 40m ./...` → **23/23 packages ok, 0 failures,
  0 skips** (`identity` 274s, `reconcile` 113s).
