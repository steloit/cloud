Invite emails + renew/decline endpoints wired: S3 yaml fixes implemented; renew
notifies inviter; decline invalidates the link.

## Summary

## Read-first

- services/api/internal/mailer — the T10.4 event/outbox dispatcher + registry
- services/api/internal/identity/invites.go — Decline/Renew service methods

## Acceptance criteria

- [x] S3 yaml fixes implemented (already applied: `/invites/{invite}/renew` has
  its path param; `DELETE /invites/{invite}` (decline) + `DELETE
  /orgs/{org}/invites/{invite}` (revoke) both exist).
- [x] renew notifies inviter (invite.renewal_requested → email to the inviter).
- [x] decline invalidates the link (status → declined; public view 410, accept

## Outcome

Most of T7.5 was already in place: **invite emails** ride the T10.4 pipeline
(`invite.created` → org-invite email, built as that task's V1 rule), the
**renew/decline endpoints** are wired handlers, **decline invalidates the link**
(status → declined; a declined invite's public view is 410 and re-decline is
refused), and the **S3 yaml fixes** (the `/invites/{invite}/renew` path param and
the DELETE invite endpoints) were already applied in an earlier pass.

The delivered delta is the **renewal notification**: when an expired invite's
holder requests a fresh link (`POST /invites/{invite}/renew`, public, 202), the
existing `invite.renewal_requested` spine event now drives an email **to the
inviter** (org-scoped, so it flows through the org-event outbox) — a new
versioned template + registry rule + a `MailDirectory` resolver that looks up
the inviter's address and the invitee/org context (HTML-escaped). Verified
end-to-end against real Postgres: create → expire → renew → the inviter receives
the renewal email alongside the invitee's original invite; and a decline 410s
the public link.

Note (founder-ruled): password-reset-style account-level events stay on their
own durable facts (ADR-0011 defers a principal-scoped audit spine); invite
renewal is org-scoped, so it uses the org spine directly — no AccountSource.
