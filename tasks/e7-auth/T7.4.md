## Goal

Org API keys with explicit scopes

## Summary

Incl. the Token.scope enum widening (spec-change §3) and DELETE /orgs/{org}/api-keys/{key}.

## Acceptance criteria

- [x] reveal-once holds (unchanged from T2.7); the secret shows once, list is hash-only.
- [x] least-privilege scopes ENFORCED per ADR-0007: an org key authorizes against its
      explicit matrix-permission subset (no role, no membership); granted perms allow,
      ungranted deny naming the key, foreign-org scope denies, delegated/unknown perms
      are unbuildable and unauthorizable, and policies still narrow — all integration-
      proven end to end.

## Outcome

- **Founder decision ratified as ADR-0007** (docs/adr/): one canonical permission
  language, multiple principal types, no duplicated authorization systems.
- `Principal.IsOrgKey()` + `OrgID`/`Permissions`; `ResolveBearer` loads them.
- `Authorizer.Require` branches: users → membership→role→matrix→policy (unchanged);
  org keys → `requireOrgKey` (org-scope match · not-delegated · registered · in the
  granted subset · then policies narrow). Denials audited, naming the key.
- Spec-change §3 done: `TokenInput.permissions` (required non-empty for createApiKey,
  each a grantable matrix permission) + `Token.permissions` on reads + `DELETE
  /orgs/{org}/api-keys/{key}` (revokeApiKey). All clients regenerated.
- CLI `key create/list/revoke` shipped (the T5.3 deferral — resolved); SDK via core.
- Closes the standing T2.7 finding: org keys now have a first-class authorization path.
