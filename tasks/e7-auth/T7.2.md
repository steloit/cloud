## Goal

Recovery codes + password reset emails: codes single-use; reset flow matches the
console's /forgot-password, /reset-password routes.

## Summary

## Outcome

Password reset over the T10.4 email pipeline. `POST /auth/password:reset-request`
always returns **202** (unknown email is a silent no-op — no account
enumeration); it mints a single-use, 1-hour token whose plaintext is
**envelope-sealed** (so the async dispatcher can build the reset link) and
sha256-hashed (constant-time lookup+verify) — the TOTP-secret pattern (T7.1).
`POST /auth/password:reset` verifies the token, sets the new password, and
**revokes every session** in one transaction; the token is single-use (a replay,
an unknown token, and an expired token are one indistinguishable 422). Recovery
codes were built single-use in T7.1 and are unchanged.

The reset email is **event-driven** but account-level: the console link is
`{console}/reset-password?token=…`, built by the mailer `Directory` unsealing
the token by id. Verified end-to-end against real Postgres (request → outbox →
token in email → reset → old password dead, new works, sessions revoked,
single-use).

**Architectural finding (recorded):** the events spine is org-scoped
(`events.org_id NOT NULL`), but a password reset is account-level with no org —
the account-deletion "fan into the user's orgs" pattern doesn't fit (a new user
has no org, and a personal reset isn't org business). Resolved without touching
the spine: account emails dispatch from their own durable fact (the reset-token
row) via a new `mailer.AccountSource` seam, reusing the same idempotent
`Dispatch` + `email_deliveries` ledger. Open question surfaced to the founder:
should the spine gain account-scoped events for a first-class personal
security-audit trail (currently reset request/complete are not audited).
