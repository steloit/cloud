## Goal

Secrets service (versioned, scoped, KMS envelope)

## Summary

D5: OpenBao/KMS envelope, never invent crypto. Internal-only in v1 (no CRUD API in the yaml — carried as a finding).

## Acceptance criteria

- [x] plaintext never at rest: integration test scans every stored row for the plaintext
      (and its distinctive substring) — ciphertext + wrapped DEK only; tamper and
      cross-scope moves fail AEAD authentication.
- [x] the vault is wired into the provisioning service — bindings (T3.6) and deploys
      consume it in-process; first consumer lands next task.

## Outcome

- `internal/secrets`: envelope encryption per D5 with stdlib AES-256-GCM ONLY (never
  invent crypto) — per-secret DEK, KEK-wrapped, `kek_id` on every row for rotation.
- The KEK is a seam: `EnvKEK` (32-byte key from `SECRETS_KEK`, required at boot) now;
  GCP KMS implements the same interface at P1 — same table, lazy re-wrap.
- AAD binds ciphertext to scope+name: a row copied to another scope FAILS authentication
  instead of decrypting (integration-proven by moving a row in SQL).
- Versioned (rotation = Put again; latest wins) and scoped (org / project / env are
  distinct namespaces; NULLS NOT DISTINCT unique).
- Standing finding (from the stub, confirmed): secrets are internal-only in v1 — the
  contract has no CRUD API; customer-facing secret management needs an owner ruling.
