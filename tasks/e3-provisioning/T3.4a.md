## Goal

`SnapshotBranch`/`PITRBranch` render the branch/PITR cluster with a hardcoded
`storage.size: 10Gi`. Thread the SOURCE's storage size through `BranchSource` so
a branch/PITR off a `standard`/`pro` database is not silently undersized.

## Why — a real T3.4-review finding (non-blocking, recorded)

For a snapshot branch the CoW clone restores to the snapshot's size, so 10Gi is
mostly cosmetic there. But a **PITR off a standard (32Gi) or pro (128Gi) source**
has no snapshot to size from and would render a 10Gi target PVC — potentially too
small to recover into. `BranchSource` should carry `StorageSize` (or the driver
should derive it from the source), and the branch/PITR templates render it.

## Acceptance criteria

- [ ] `BranchSource` carries the source storage size; branch/PITR render it.
- [ ] A PITR off a 128Gi source renders a 128Gi target (test).
- [ ] The spike parity tests still pass (10Gi in the spike fixtures is the dev size).

## Outcome — SUPERSEDED BY T3.4d (#329), not implemented again

T3.4d landed exactly this: `SnapshotBranch` and `PITRBranch` size their volume
from the **source service's shape**, through the same `storageForShape` that
sizes a create. All three ACs are satisfied, and the parity fixtures still pass
because they are `dev` (10Gi).

Closed as a duplicate rather than re-implemented. The two were filed from
different reviews of the same defect and neither referenced the other — which is
the detection gap **O18** exists for.

**One correction worth keeping, because this task's reasoning was wrong in the
direction that matters.** T3.4a says:

> For a snapshot branch the CoW clone restores to the snapshot's size, so 10Gi is
> mostly cosmetic there.

It is not cosmetic, and it is not a clone-time question.
`.spec.resources.requests.storage` is what the PVC **asks for**, and
external-provisioner refuses a request below the source snapshot's
`status.restoreSize` outright — *"requested volume size %d is less than the size
%d for the source snapshot %s"*. [external-provisioner#727](https://github.com/kubernetes-csi/external-provisioner/issues/727)
asked for the request to be treated as a minimum and was closed **not planned**,
so the behaviour is durable and not GKE-specific. The snapshot branch does not
come up undersized — **it does not come up at all.**

The PITR half of T3.4a's reasoning was right, and is in fact the worse case: no
snapshot data source means no `restoreSize` to check against, so nothing refuses
it and the undersized volume fills mid-restore.

`pro (128Gi)` named here is not in `pricing.json`; the catalog is
dev/standard/performance, and T3.4d sweeps every size the catalog actually sells.
