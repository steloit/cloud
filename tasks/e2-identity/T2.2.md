## Goal

Token mint/verify middleware (personal tokens + org API keys)

## Summary

Shared `tokens` table; `stp_` prefix; hash-stored, reveal-once contract.

## Acceptance criteria

- [ ] bearer auth works for both credential kinds.

## Outcome

Delivered 2026-07-19. Shared `tokens` table (timestamped migration via the migrate CLI):
kind personal|org with check constraints, nullable org_id (FK deferred to the orgs
migration — documented forward reference), sha256 hash UNIQUE + display prefix, expiry,
last_used, revocation. Personal tokens: `stp_` secrets minted reveal-once (plaintext exists
in exactly one response; hash-only storage DB-asserted), scope full|read_only, 30–365d
expiry per contract. Bearer middleware resolves EITHER credential kind through one
hash lookup (org keys proven at store level — last_used_at moves; endpoints land with the
org tasks); read_only tokens are denied mutating token ops (403 with remediation); owner
scoping makes foreign revocation indistinguishable from 404. Strict server grew by three
ops via include-operation-ids. Full-stack tests: reveal-once contract, secret-leak greps
on list, both-kinds bearer auth, scope denial, revocation kill, expiry — CI-enforced.
