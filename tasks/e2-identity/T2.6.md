## Goal

`platform/problem`: one package where every API error is born — RFC 9457 problem+json, `remediation` required by construction, the full x-error-catalog as typed constructors, panic recovery with `event_id`.

## Why

"Errors always carry remediation" is a hard rule (AGENTS.md); it only holds if there is exactly one way to produce an error and that way makes remediation unforgeable. Every handler task (T2.1 onward) builds on this.

## Read first

- `docs/product/08-api/openapi.yaml` x-error-catalog + `x-conventions.errors` — the catalog this package types
- `docs/architecture.md` §16 (error handling: one platform/problem package, catalog-registered, logged once at the boundary with the event id the 5xx body carries) + §17 (slog conventions)
- `contexts/api-conventions.md`
- Don't read: console code.

## Approach

1. `Problem` struct: `type,title,status,detail,remediation` + typed extensions (`errors[]` field errors, `reasons[]`, `required_plan`, `overage_price_cents`, `event_id`, `retry_after_s`); JSON marshals with omitempty on extensions, never on remediation.
2. One constructor per catalog entry (422 validation, 403 permission naming role|policy, 402 plan-gated / quota soft+hard, 409 conflict with reasons, 404, 429 with Retry-After, 502 provider with event id, 500 internal with event id). Constructors demand remediation (or derive the canonical one); no public way to build a Problem without it.
3. `Write(w, r, p)`: `application/problem+json`, status from p, Retry-After header when set; 5xx logs once at this boundary (slog, event_id + request context keys per §17).
4. `Recover` middleware: panic → 500 problem with fresh event_id; wired in main's middleware chain now.
5. Table-driven golden tests: one per catalog entry asserting exact JSON shape, remediation non-empty, headers; a compile-time/or-test guarantee that every constructor sets remediation.
6. CI go job gains `go test ./...`.

## Edge cases

- Double-write (handler wrote, then errors) → Write is terminal; document the one-write discipline.
- Panics after partial body → recovery logs; body best-effort (documented limitation until real handlers exist).
- 429 must set BOTH the header and `retry_after_s` (clients honor the header; the body is for humans).

## Security & performance

Error bodies never leak internals: 5xx detail is generic + event_id (the log carries the truth). No stack traces in any body.

## Acceptance criteria

- [ ] WHEN any catalog constructor runs THEN the body carries non-empty `remediation` (test-enforced for every constructor)
- [ ] WHEN each golden test runs THEN the JSON matches the catalog shape exactly (422 errors[], 409 reasons[], 402 required_plan/overage_price_cents, 429 Retry-After header+field, 5xx event_id)
- [ ] WHEN a handler panics THEN the response is a 500 problem with event_id and the panic is logged once with that id
- [ ] CI runs the tests on every PR

## Validation

`verify:` block. PR evidence: test output listing the per-catalog golden cases.

## Common mistakes

- An exported Problem literal path that skips remediation (keep fields unexported or constructor-only).
- Logging the error at every layer (once, at the boundary — §16).
- Inventing catalog entries — the yaml's x-error-catalog is the closed set; a new class is an S-process change.
