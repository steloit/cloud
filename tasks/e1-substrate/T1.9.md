## Goal

Make `docs/founder-config.md` §2 describe the project that exists.

## Why

§2 says *"The **dev** foundation is bootstrapped; identifiers below are live."*
Most of it is not. Measured against `steloit-dev` on 2026-08-25, read-only:

| §2 row | says | live |
|---|---|---|
| Terraform state `gs://steloit-dev-tfstate` | ✅ **created** | **exists** |
| KMS key ring + `secrets` key | ✅ **created** | ring `cell-dev-core` **exists** |
| Artifact Registry `images` repo | ✅ **created** | **no repositories in the project** |
| WAL buckets `-wal-customer`, `-wal-control` | ✅ **created** | **absent** |
| Artifacts bucket `steloit-dev-artifacts` | ✅ **created** | **absent** |
| WIF pool `github-ci` + provider `github-oidc` | ✅ **created** | only the GKE-managed `steloit-dev.svc.id.goog` pool |
| SAs `ci-terraform-plan`, `ci-image-push` | ✅ **created** | only the default compute SA |

Commands, so this is re-runnable rather than a claim:

    gcloud storage buckets list --format="value(name)"        # steloit-dev-tfstate, and nothing else
    gcloud artifacts repositories list                        # empty
    gcloud iam service-accounts list --format="value(email)"  # 850447601666-compute@... only
    gcloud iam workload-identity-pools list --location=global # only GKE's steloit-dev.svc.id.goog
    # Added after review: the three measurements that were NEW in this task had no
    # recorded command, and two of them carried the whole causal conclusion.
    gcloud kms keyrings list --location=us-central1           # cell-dev-core
    gcloud kms keys list --location=us-central1 --keyring=cell-dev-core   # NOT RUN — see AC 1
    gcloud storage cat gs://steloit-dev-tfstate/dev/default.tfstate | jq '.resources[].type'
    gcloud services list --enabled --format="value(config.name)" | wc -l  # 42

This is the same defect class the mistake bank calls *rendered / stored /
enforced are three representations* — here it is **declared vs live**, and the
declared side is a founder-owned file that other tasks cite as fact. Two have
already leaned on it: T1.7's option (b) is priced partly against the "zero static
keys (D5)" CI identity, which does not exist; and it explains why T1.7's missing
API went unnoticed through bootstrap — `ci_plan_viewer`, the first consumer, was
never applied.

## What is proven and what is not

**Proven:** the resources above are absent from `steloit-dev` today.

**Not established, and the task should not assume it:** *why*. Three candidates,
distinguishable by evidence the implementer should gather before editing —
(i) `project_base` was only ever partially applied (the bootstrap `-target` step
stopped after the state bucket); (ii) it was applied and later destroyed;
(iii) the rows were written from the *plan* rather than from the result. The KMS
ring exists while the buckets do not, which is not obviously consistent with any
single story, so look before writing.

### What was NOT done, on purpose

- **No history erased.** Every restaked row says what it used to claim and when
  that changed. A row that reads "was ✅ created until 2026-08-25" is recoverable;
  a deleted row is not.
- **No intent changed.** The WIF row still states "zero static keys (D5)" and now
  says explicitly that D5 remains the standing rule — the row records that the
  mechanism is unbuilt, never that keyless CI was abandoned. Same for the WAL
  buckets' separation requirement (INF-001 #10), which is unaffected by the
  buckets not existing yet.
- **Current state and historical evidence are kept apart.** The bootstrap
  paragraph now points at `infra/README.md` §Bootstrap as the contract, and keeps
  the procedure actually *used* below it, marked historical — because that
  paragraph is the evidence for T1.7's defect and deleting it would delete the
  explanation.

### The cause — a leading inference, NOT established

The task listed three candidates and said to look before writing. I wrote
"established: (i)" and that over-reached; review was right to block it.

**What is measured:** `gs://steloit-dev-tfstate/dev/default.tfstate` holds exactly
one resource, `google_storage_bucket.state`.

**The leading inference:** `apply -target=module.project_base` was only ever run far
enough to create the state bucket, so the absent rows were never applied rather than
destroyed.

**What it does not explain, and I did not resolve:** the KMS ring exists while not
being in that state file. My first write-up called that "the exception that confirms
it" — rescuing an inference with a second unevidenced claim (that the ring was
created out of band), which is not evidence, it is a story. And the absent resources
depend only on `google_project_service`, so a partial apply at default parallelism
would not plausibly stop at exactly one bucket plus a ring.

**Open, and it has an operational consequence** (recorded in §2): if the ring really
is out of band, `apply -target=module.project_base` fails on
`google_kms_key_ring.core` with an already-exists error until it is imported. Exactly
one of "the ring is out of band" and "the partial-apply story is right" can be true,
and a single `terraform state list` against the real backend settles it. That needs
credentials this session no longer has.

### Why this row-set is the one that mattered

`ci_plan_viewer` — the first consumer of the API T1.7 was about — lives in the
same never-applied set. That is why a module unable to complete its own bootstrap
step went unnoticed: the step was never run past its first resource.

### A ✅ still has no expiry

The `last verified` line is a date, not a mechanism. Nothing re-checks it, so it
will go stale again. Making drift detectable rather than merely dated is
**T1.10**.
