## The defect T1.9 left behind

T1.9 corrected seven rows in `docs/founder-config.md` §2 that claimed resources
existed when they did not, and added a **last verified** date. A date is not a
mechanism. Nothing re-checks it, so the table will go stale again exactly the way
it did the first time — silently, for weeks, while other tasks cite it as fact.

It was cited as fact: T1.7 priced an option partly against the "zero static keys
(D5)" CI identity, which does not exist.

## Why the obvious fix is wrong

"Run `gcloud` in CI and diff against the table" fails on three counts, and the
task should not start by trying it:

1. **CI has no credentials for `steloit-dev`,** by design — D5, keyless, and the
   plan-only SA in that row is itself unbuilt. Granting CI read access to the live
   project to check a doc is a real security decision, not a chore.
2. **The table is prose.** `iam(+creds)` is not a machine-readable list, and the
   APIs row deliberately stopped enumerating (T1.9) precisely so there would be
   one list, in code.
3. **Drift is expected and correct here.** Most ⏳ rows are things not built yet.
   A checker that fails CI because the future has not arrived teaches people to
   ignore it.

## What would actually help

Prefer the smallest thing that makes staleness *visible* rather than *detected*:

- A `verified: YYYY-MM-DD` marker parsed by `validate.mjs`, warning when a ✅ row's
  date is older than some window. Not a hard failure — an unresolvable claim about
  live state must not block a merge that has nothing to do with it.
- A committed, re-runnable script (`scripts/infra/verify-live.sh`) that a human
  with credentials runs, printing a table diff. T1.9's commands already exist in
  its body; lifting them into a script is most of the work, and it makes the next
  verification a minute rather than an investigation.

The second is worth doing regardless of the first.

## Acceptance criteria

1. Re-verifying §2 against live is **one command**, committed, with its output
   pasted into the PR that runs it.
2. Staleness is surfaced somewhere a reader will see it without going looking.
3. The mechanism does **not** require CI credentials for the live project, or the
   ADR that granting them would need is written first and this task waits.
4. A row that is legitimately ⏳ (not built yet) never fails a build.
