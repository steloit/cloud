## The defect T1.9 left behind

T1.9 restaked four rows in `docs/founder-config.md` §2 — eight resources — that
claimed to exist when they did not, corrected three more, and added a **last
verified** date. A date is not a
mechanism. Nothing re-checks it, so the table will go stale again exactly the way
it did the first time — silently, for weeks, while other tasks cite it as fact.

It was cited as fact: T1.7 priced an option partly against the "zero static keys
(D5)" CI identity, which does not exist.

## Why the obvious fix is wrong

"Run `gcloud` in CI and diff against the table" fails on three counts, and the
task should not start by trying it:

1. **The keyless read path is DECLARED but UNAPPLIED — so this task must not
   depend on it.** An earlier revision of this task said "CI has no credentials for
   `steloit-dev`, by design", and that was **false**: `.github/workflows/image.yml`
   already authenticates with `google-github-actions/auth@v2` via
   `workload_identity_provider`, and `project-base` declares `ci-terraform-plan`
   with `roles/viewer`, commented *"read-only; apply is founder-run"*. **D5 forbids
   static keys, not credentials.** The read grant a checker would need is already a
   decision the repo made in code — it has simply never been applied (T1.9). So the
   obstacle is availability, not authority, and a checker that assumes those
   credentials exist will silently do nothing until `project-base` is applied.
2. **The table is prose.** `iam(+creds)` in the APIs row expands to two service
   names; statuses are English. A checker has to parse founder-written text, and
   review of T1.9 kept that row's enumeration deliberately (T1.7 option (a)), so
   the duplication it introduces is a thing to CHECK, not to remove.
3. **Drift is expected and correct here.** Most ⏳ rows are things not built yet.
   A checker that fails CI because the future has not arrived teaches people to
   ignore it.

## What would actually help

Prefer the smallest thing that makes staleness *visible* rather than *detected*:

- A `verified: YYYY-MM-DD` marker parsed by `validate.mjs`, warning when a ✅ row's
  date is older than some window. Not a hard failure — an unresolvable claim about
  live state must not block a merge that has nothing to do with it.
- ~~A committed, re-runnable script (`scripts/infra/verify-live.sh`)~~ — **done in
  T1.9.** It was worth doing regardless of the rest, and it immediately paid: running
  it settled the KMS question that had been blocking T1.9's cause section.

What remains is only the *surfacing* half: nothing yet tells a reader that a ✅ is
old, and nothing compares the script's output to §2 automatically.

## Acceptance criteria

1. [x] Re-verifying §2 against live is **one command**, committed, with its output
   pasted into the PR that runs it — `scripts/infra/verify-live.sh` (T1.9). It is
   read-only, it prints Terraform's tracked-resource set alongside what exists (so
   an untracked resource that would re-apply as `already exists` is visible), and it
   **exits 2 rather than reporting an empty project** when credentials are unusable:
   a checker that silently reports "nothing there" is worse than no checker.
2. Staleness is surfaced somewhere a reader will see it without going looking.
3. The mechanism does not silently no-op when the CI identity is absent — today it
   is (T1.9), so anything built on it must fail loudly or skip visibly, never pass.
   An ADR is required only for a grant **beyond** the `roles/viewer` already
   declared on `ci-terraform-plan`; that existing grant needs no new decision, and
   this task must not stall on an ADR for something the repo already decided.
4. A row that is legitimately ⏳ (not built yet) never fails a build.
