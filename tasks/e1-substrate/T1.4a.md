## Goal

`terraform apply` on a fresh cell must succeed in ONE pass. Today it cannot:
`module.cnpg` mixes the operator's Helm install with `kubernetes_manifest`
resources for CNPG CRs, and the Kubernetes provider requires a CRD to exist at
**plan** time — so the very apply that installs the CRDs cannot plan the objects
that need them.

## Why — found standing up the cell for US-3.3 (reproducible)

```
$ terraform apply -var project_id=steloit-dev ...
Plan: 8 to add, 0 to change, 0 to destroy.
Error: API did not recognize GroupVersionKind from manifest (CRD may not be installed)
```

The failing resources are `module.cnpg.kubernetes_manifest.control_plane_cluster`
and `.control_plane_backup_schedule` (kind `Cluster`/`ScheduledBackup` in
`postgresql.cnpg.io/v1`). The Helm release that installs those CRDs is in the
same apply, but `kubernetes_manifest` resolves its GVK during **plan**, before
anything is created. This is a known limitation of
`hashicorp/kubernetes`'s `kubernetes_manifest`, not a transient error — it
reproduces on every from-zero apply.

The workaround used for US-3.3 was a targeted apply
(`-target=module.gke_cell` → `-target=module.cnpg.helm_release.cnpg_operator` →
full apply). **That is exactly the "exceptional situations only" use Terraform
warns about**, so it must not become the documented path for standing up a cell.

## Options

1. **Split the operator into its own root/stage** (`envs/dev-operator` or a
   documented two-stage apply with `depends_on`) — honest about the ordering,
   but two states to manage.
2. **Replace the CR `kubernetes_manifest`s with `helm_release`/`kubectl_manifest`**
   (a provider that defers GVK resolution to apply time), keeping one pass.
3. **Move the control-plane CNPG cluster out of terraform** into the same
   apply path the cell-agent uses (it is, after all, a CNPG cluster like any
   other) — arguably the most consistent with D9.

Decide with evidence; option 2 is the smallest change, option 3 the most
architecturally consistent.

## Outcome

**One resource type was the whole problem.** `kubernetes_manifest` resolves its
GroupVersionKind against the live API at PLAN time; on a from-zero apply there is
no API yet, and for a CR no CRD yet. `depends_on` cannot help — validation runs
before dependency resolution — and it is acknowledged and still open upstream
(#1367, #2597). Every raw manifest now uses `kubectl_manifest` (`alekc/kubectl`),
which applies YAML the way `kubectl apply` does and resolves nothing at plan.

**All four had to move, not just the two that were reported.** The original error
named only the CNPG custom resources, but that apply had already run
`-target=module.gke_cell`, so a cluster existed. A `kubernetes_manifest` needs
the API at plan time whatever its kind — so the two storage classes fail too on a
genuine from-zero apply, and leaving them would have kept the `-target` sequence
while appearing to fix it.

**Option 3 in this task is a bootstrap cycle, and that is checkable.** "Move the
control-plane CNPG cluster out of terraform into the agent's path" was described
here as the most architecturally consistent option. The agent gets desired state
by polling the control-plane API, and the API refuses to start without its
database. The control-plane database cannot be provisioned by the thing that
needs it to exist. Rejected on evidence.

**Nothing else about a one-pass apply was broken**, which is why the fix is this
small: creating a cluster and deploying into it in a single apply is supported —
the Kubernetes and Helm providers are simply not initialised until apply, and
HashiCorp's own GKE example does exactly this.

**`~> 2.4`, not the `~> 3.0` the provider's README gives.** The registry
publishes 3.0.0 only as `beta2`/`beta3`, so that constraint resolves to nothing —
`terraform init` failed on it. Verified against `registry.terraform.io`.

**The guard is a text check and says so.** `TestInfraNeverUsesKubernetesManifest`
walks `infra/` and fails on a reintroduced `resource "kubernetes_manifest"`
anywhere — measured RED for the cnpg module, another module, and an env root,
with a `kubectl_manifest` control staying green. No terraform test can assert
"this resource type is absent" about a configuration that would fail to plan.

**The first version of this fix did not work, and review caught it.** Replacing
`kubernetes_manifest` removes the plan-time API call, but `alekc/kubectl`
CONFIGURES at plan time and errors when host/CA are unknown — the from-zero case
exactly. Reproduced: `Plan: 1 to add` then *"invalid provider configuration:
default cluster has no server defined"*; with `lazy_load = true`, a clean plan.
So one plan-time failure had been swapped for another, and **nothing in the repo
could see it**: `terraform validate` never configures providers, and the env
`terraform test` suites mock this provider wholesale, which is what makes them
pass. `TestTheKubectlProviderLoadsLazily` now guards `lazy_load` and
`apply_retry_count` — five mutations measured RED, including flipping lazy_load
to false and removing it from either env.

Decision recorded as **ADR-0017**, with the four rejected alternatives and why.
