## Goal

`terraform apply` on a fresh cell must succeed in ONE pass. Today it cannot:
`module.cnpg` mixes the operator's Helm install with `kubernetes_manifest`
resources for CNPG CRs, and the Kubernetes provider requires a CRD to exist at
**plan** time — so the very apply that installs the CRDs cannot plan the objects
that need them.

## Why — found standing up the cell for US-3.3 (reproducible)

```
$ terraform apply -var project_id=steloit-dev ...
Plan: 8 to add, 0 to change, 0 to destroy.
Error: API did not recognize GroupVersionKind from manifest (CRD may not be installed)
```

The failing resources are `module.cnpg.kubernetes_manifest.control_plane_cluster`
and `.control_plane_backup_schedule` (kind `Cluster`/`ScheduledBackup` in
`postgresql.cnpg.io/v1`). The Helm release that installs those CRDs is in the
same apply, but `kubernetes_manifest` resolves its GVK during **plan**, before
anything is created. This is a known limitation of
`hashicorp/kubernetes`'s `kubernetes_manifest`, not a transient error — it
reproduces on every from-zero apply.

The workaround used for US-3.3 was a targeted apply
(`-target=module.gke_cell` → `-target=module.cnpg.helm_release.cnpg_operator` →
full apply). **That is exactly the "exceptional situations only" use Terraform
warns about**, so it must not become the documented path for standing up a cell.

## Options

1. **Split the operator into its own root/stage** (`envs/dev-operator` or a
   documented two-stage apply with `depends_on`) — honest about the ordering,
   but two states to manage.
2. **Replace the CR `kubernetes_manifest`s with `helm_release`/`kubectl_manifest`**
   (a provider that defers GVK resolution to apply time), keeping one pass.
3. **Move the control-plane CNPG cluster out of terraform** into the same
   apply path the cell-agent uses (it is, after all, a CNPG cluster like any
   other) — arguably the most consistent with D9.

Decide with evidence; option 2 is the smallest change, option 3 the most
architecturally consistent.

## Acceptance criteria

- [ ] From zero (no cluster, empty state) a single `terraform apply` stands up a
  complete cell — GKE + operator + storage classes + control-plane DB — with no
  `-target`.
- [ ] Verified by actually destroying and re-applying, not by reasoning.
- [ ] `infra/README.md` documents the real bootstrap, and any remaining ordering
  constraint is stated rather than discovered.
