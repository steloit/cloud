## Goal

Decide whether `cloudresourcemanager.googleapis.com` joins the project's
authoritative API list, and if so add it to **both** representations.

## Why this is blocked on the owner, not on engineering

The one-line change is trivial. What is not trivial is *whose* list it is. The
service set exists in two places that currently agree:

- `infra/modules/project-base/main.tf:6-21` — 14 services in `local.services`.
- `docs/founder-config.md` §2 "APIs enabled" — the same 14, recorded as the
  founder's bootstrap record, together with a procedure that says
  "`gcloud services enable` **the 14 APIs**".

Because they agree, the omission is **a gap in the authoritative configuration,
not drift in the implementation**. Editing `local.services` alone would silently
fork the two and quietly move an owner decision into a feature PR. Founder
instruction, 2026-08-25: *"Treat the `project_base` service list as an
owner-level configuration decision. Do not silently modify it merely to make the
current environment work."*

## What is proven

1. **The dependency is real, measured on the wire — not inferred from provider
   docs.** `gke-cell` grants its dedicated least-privilege node service account
   five roles via `google_project_iam_member.node_roles`
   (`infra/modules/gke-cell/main.tf:18`). That resource is implemented as
   project `getIamPolicy` + `setIamPolicy`, and those are served by Cloud
   Resource Manager:

       $ gcloud projects get-iam-policy steloit-dev --log-http
       uri: https://cloudresourcemanager.googleapis.com/v1/projects/steloit-dev:getIamPolicy?alt=json

   It is the only consumer in `infra/` — every other module's API needs are
   already in the list.

2. **It is absent from both declared representations.** Verified by reading
   both, above.

3. **It is not reliably enabled by default.** `steloit-dev` did not have it
   until US-3.3c enabled it by hand (`docs/dev/us33c-live-evidence.md:106`) so
   the live cell could be built.

## What is inferred, and stated as inference

That a *genuinely clean* project would fail here. No fresh project was created
to test it — doing so would have created infrastructure outside the authorized
scope. The support for the inference is (3): the one project we have did not
have it on. GCP enables a default set at project creation that varies by
creation path (console / gcloud / org policy), so "clean project" is not one
fixed baseline.

## Disclosure

`steloit-dev` has the API enabled **right now**, by this agent's hand, and that
is undeclared. The running project is therefore a third representation that
disagrees with both declared ones. It was left enabled rather than disabled
again because disabling it would have broken the very apply it was enabling, and
because the API is free. Ratifying this task reconciles all three; declining it
should be paired with `gcloud services disable cloudresourcemanager.googleapis.com`
on `steloit-dev` and with removing `google_project_iam_member.node_roles` or
moving the grants to a mechanism that does not use project IAM.

## Options

- **(a) Add it — recommended.** Fifteen entries in `local.services`, fifteen in
  the founder-config row, "the 14 APIs" becomes "the 15 APIs". The API is free;
  its scope is the project's own IAM policy, which Terraform already reads and
  writes today with the founder's credentials. Nothing new is exposed.
- **(b) Decline, and remove the project-IAM grant.** The node SA would carry no
  project roles; logging/monitoring/AR-read would have to come from elsewhere.
  This weakens the D5 posture that motivated the dedicated SA in the first place
  (the review finding recorded in `gke-cell/main.tf:8-11`), and there is no
  cheaper mechanism for project-level role binding.
- **(c) Decline, and enable the API out-of-band per project.** Keeps the
  declared list at 14 but makes the bootstrap procedure lie about being
  repeatable, and re-introduces the exact by-hand step that produced this
  finding.

## Acceptance criteria

1. A founder ruling recorded in `docs/founder-config.md`, replacing the
   `❓ NEEDS FOUNDER INPUT` row with an attributed decision.
2. If (a): `local.services` and the founder-config row list the same set, and a
   check asserts they cannot diverge again — the two-representations rule
   (`contexts/provisioning.md`) applies to this pair exactly as it does to code.
3. The bootstrap procedure's API count matches the list it points at.

## Notes

**T1.8 is the other half and does not need this ruling.** Adding the API to the
list is necessary but *not sufficient* for a from-zero apply:
`module.project_base.google_project_service.enabled` has **zero outgoing edges**
in `envs/dev`'s graph, so nothing waits for API enablement. See T1.8.
