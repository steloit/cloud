## Goal

Decide whether `cloudresourcemanager.googleapis.com` joins the project's
authoritative API list, and if so add it to **both** representations.

## RESOLVED by the repository — the ownership question answered the list question

Filed as owner-level, on the reading that the service list is a configuration
choice. It is not, and the evidence that settles it was in the repo the whole
time:

1. **`infra/README.md` §Bootstrap is the clean-project contract, and it is
   Terraform-first.** Step 2 on a fresh project is
   `terraform apply -target=module.project_base`. There is **no**
   `gcloud services enable` anywhere in that file.
2. **`project-base` is the sole declarer of `google_project_service`** — one
   occurrence in the entire tree, verified by grep.

Together those make API enablement unambiguously this module's job, which means
its list must be sufficient for **its own resources** to apply. It was not:
`google_project_iam_member.ci_plan_viewer` is declared in `project-base` and is
served by Cloud Resource Manager. **The module could not complete its own
documented bootstrap step** — an internal inconsistency, not a preference between
defensible options, so it is fixed here rather than escalated.

Why nobody noticed: `docs/founder-config.md` §2 records the procedure actually
*used*, which inserted a manual `gcloud services enable` of "the 14 APIs" before
the Terraform step. That manual step is not in the normative contract and it
masked the gap. `ci_plan_viewer` was also never applied to `steloit-dev` at all
(**T1.9**), so the second consumer never ran either.

### Enforced, not just fixed

`scripts/infra/required-apis.mjs` maps every `google_*` resource type in `infra/`
to the API that serves it and asserts each one is in `local.services`. It runs in
CI's infra job. **An unclassified resource type is a FAILURE, never a skip** —
`contexts/provisioning.md` records that widening a lookup table without widening
its consumer turns a loud error into a silent success, and an API-classification
table that quietly ignores what it does not recognise is precisely how this gap
arrived.

Proved both ways, in a copy:

| state | result |
|---|---|
| the API present (as shipped) | `OK — 10 APIs required by infra/, all declared` |
| the API removed | **FAIL**, naming `google_project_iam_member` as the requirer |
| a new unclassified `google_pubsub_topic` added | **FAIL**, exit 1, demanding it be classified |

The first two are the two-sided proof: it goes green with the fix and red without
it. The third is the one that matters in a year.

### What is NOT resolved here

The `❓` row in `docs/founder-config.md` is replaced with a record of this
reasoning, not with a ruling — the founder can still decide the list should be
smaller and remove the grants instead (old option (b)). What changed is that
"leave it out and do nothing" is no longer available: the bootstrap contract and
the module disagreed, and one of them had to move.

Also unresolved and deliberately left: §2's `APIs enabled` ✅ row and its "the 14
APIs" prose are now stale. Reconciling §2 with live state is **T1.9**.

## Why this was filed as blocked on the owner

The one-line change is trivial. What is not trivial is *whose* list it is. The
service set exists in two places that currently agree:

- `infra/modules/project-base/main.tf:6-21` — 14 services in `local.services`.
- `docs/founder-config.md` §2 "APIs enabled" — the same 14, recorded as the
  founder's bootstrap record, together with a procedure that says
  "`gcloud services enable` **the 14 APIs**".

Because they agree, the omission is **a gap in the authoritative configuration,
not drift in the implementation**. Editing `local.services` alone would silently
fork the two and quietly move an owner decision into a feature PR. Founder
instruction, 2026-08-25: *"Treat the `project_base` service list as an
owner-level configuration decision. Do not silently modify it merely to make the
current environment work."*

## What is proven

1. **The dependency is real, measured on the wire — not inferred from provider
   docs.** A `google_project_iam_member` is implemented as project
   `getIamPolicy` + `setIamPolicy`, and those are served by Cloud Resource
   Manager:

       $ gcloud projects get-iam-policy steloit-dev --log-http
       uri: https://cloudresourcemanager.googleapis.com/v1/projects/steloit-dev:getIamPolicy?alt=json

   **There are TWO consumers, and the first one is inside `project-base`
   itself:**

   - `project-base/main.tf:139` — `google_project_iam_member.ci_plan_viewer`,
     the `roles/viewer` grant to the plan-only CI service account.
   - `gke-cell/main.tf:18` — `google_project_iam_member.node_roles`, five roles
     on the dedicated least-privilege node SA.

   That first one relocates the failure. The documented bootstrap step is
   `terraform apply -target=module.project_base` (`docs/founder-config.md` §2),
   and **that** is what cannot complete on a clean project — `gke-cell` is never
   reached. An earlier revision of this task said "the only consumer in
   `infra/`" and located the failure at `gke-cell`; both were wrong, and the
   error mattered because it is what option (b) is priced against.

2. **It is absent from both declared representations.** Verified by reading
   both, above.

3. **It is not reliably enabled by default.** `steloit-dev` did not have it
   until US-3.3c enabled it by hand (`docs/dev/us33c-live-evidence.md:106`) so
   the live cell could be built.

## What is inferred, and stated as inference

That a *genuinely clean* project would fail here. No fresh project was created
to test it — doing so would have created infrastructure outside the authorized
scope. The support for the inference is (3): the one project we have did not
have it on. GCP enables a default set at project creation that varies by
creation path (console / gcloud / org policy), so "clean project" is not one
fixed baseline.

## Disclosure

`steloit-dev` has the API enabled **right now**, by this agent's hand, and that
is undeclared. On this one API, the running project is therefore a third
representation that disagrees with both declared ones.

**This is not a complete accounting of live divergence, and must not be read as
one.** Live state diverges from `docs/founder-config.md` §2 much more broadly —
most of the resources that row marks ✅ **created** do not exist. Measured
directly (`gcloud storage buckets list`, `artifacts repositories list`,
`iam service-accounts list`, `iam workload-identity-pools list`): the only bucket
is `steloit-dev-tfstate`; there is no Artifact Registry repository, no `github-ci`
WIF pool, and neither CI service account. That is filed separately as **T1.9**,
per protocol §7. It is also why the missing API went unnoticed through bootstrap:
`ci_plan_viewer` was never applied. It was left enabled rather than disabled
again because disabling it would have broken the very apply it was enabling, and
because the API is free. Ratifying this task reconciles all three on this API; declining it should be
paired with `gcloud services disable cloudresourcemanager.googleapis.com` on
`steloit-dev` and with removing **both** `node_roles` and `ci_plan_viewer`, or
moving those grants to a mechanism that does not use project IAM.

## Options

- **(a) Add it — recommended.** Fifteen entries in `local.services`, fifteen in
  the founder-config row, "the 14 APIs" becomes "the 15 APIs". The API is free;
  its scope is the project's own IAM policy, which Terraform already reads and
  writes today with the founder's credentials. Nothing new is exposed.
- **(b) Decline, and remove BOTH project-IAM grants.** Not one — two. The node SA
  would carry no project roles (logging/monitoring/AR-read would need another
  home), which weakens the D5 posture that motivated the dedicated SA in the
  first place (`gke-cell/main.tf:8-11`); **and** `ci_plan_viewer` would go, which
  is the read side of the plan-only CI identity that `docs/founder-config.md` §2
  records as ✅ under "zero static keys (D5)". A ruling on (b) made without
  knowing the second half would be made on bad information. Four of the five node
  roles (`logging.logWriter`, `monitoring.metricWriter`, `monitoring.viewer`,
  `stackdriver.resourceMetadata.writer`) have no narrower scope; see (d) for the
  fifth.
- **(c) Decline, and enable the API out-of-band per project.** Keeps the
  declared list at 14 but makes the bootstrap procedure lie about being
  repeatable, and re-introduces the exact by-hand step that produced this
  finding.
- **(d) Narrow `artifactregistry.reader` to the repository — worth doing whichever
  way (a)-(c) go.** It is the one node role with a narrower scope, and the repo
  already uses that scope for the same purpose one resource over:
  `google_artifact_registry_repository_iam_member.ci_image_writer`
  (`project-base/main.tf:158`). That path goes through
  `artifactregistry.googleapis.com`, not Cloud Resource Manager. This does **not**
  remove the dependency — the other four roles and `ci_plan_viewer` still need it
  — so it is not an alternative to (a). It is a D5 improvement on its own merits
  and should not wait on this ruling.

## Acceptance criteria

1. A founder ruling recorded in `docs/founder-config.md`, replacing the
   `❓ NEEDS FOUNDER INPUT` row with an attributed decision.
2. If (a): `local.services` and the founder-config row list the same set, and a
   check asserts they cannot diverge again — the two-representations rule
   (`contexts/provisioning.md`) applies to this pair exactly as it does to code.
3. The bootstrap procedure's API count matches the list it points at.
