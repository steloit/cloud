## Goal

Make API enablement a *predecessor* of the resources that need those APIs, so
`terraform apply` from zero is ordered rather than lucky.

## Why

`module.project_base` enables 14 services. **Nothing in either env depends on
that resource.** Measured, not read — the plan graph, built in a throwaway copy
of `infra/` (`terraform init -backend=false`, backend block neutralized in the
copy only).

**Mind the direction.** A Terraform graph edge runs *dependent → dependency*, so
the load-bearing measurement is edges whose TARGET is the node — what depends on
API enablement — not edges whose source it is. An earlier revision of this task
grepped the source side, which asks "what does `enabled` itself depend on"; that
is trivially nothing (the resource references only `var.project_id` and
`each.value`) and can never be non-empty, so the check would have stayed
"passing" after the fix landed. The correct measurement:

    $ terraform graph | grep -- '-> "module.project_base.google_project_service.enabled"'
    (no output)

| env | total edges | incoming to `enabled` | outgoing from it |
|---|---|---|---|
| `dev` | 42 | **0** | 0 |
| `cell0` | 40 | **0** | 0 |

The node is present in both graphs and fully isolated — so the grep is not empty
because the graph is. Every consumer is unordered with respect to it: the cluster
(`container`), the subnetwork (`compute`), four buckets (`storage`), the KMS ring
(`cloudkms`), the WIF pool (`iam`), the scheduler jobs, the budget. The only
edges out of `project_base` at all are its own internal ones plus two into
`module.cnpg`, which exist because cnpg *consumes a bucket output* — an accident
of data flow, not an ordering decision.

Today this is masked: the project was bootstrapped by a documented one-time
`gcloud services enable` **before** the first apply
(`docs/founder-config.md` §2), so by the time Terraform runs, the APIs are on.
That makes the bootstrap procedure load-bearing in a way nothing enforces.

*(An earlier revision blamed this ordering for how T1.7's missing API surfaced in
US-3.3c. That was wrong twice: `module.project_base` was omitted from that
temporary root entirely — `docs/dev/us33c-live-evidence.md:104` — so no edge could
have existed or helped; and `terraform plan` does not check API enablement for
resources being created, so `SERVICE_DISABLED` is apply-time regardless of
ordering. The ordering gap stands on its own; it does not need that story.)*

## Approach

**Prefer an explicit `apis_ready` output** from `project-base`, threaded into the
consuming modules. Not for elegance — because it is the only variant AC 2 can
assert. A graph edge is not an observable value in plan output, so under
`depends_on = [module.project_base]` no `.tftest.hcl` assertion can see it;
under `apis_ready` the dependency becomes ordinary data flow and an output
assertion covers it. The existing mocked suite already runs credential-free and
green, which is the harness this would join.

`depends_on = [module.project_base]` is the blunt alternative. Measured: adding it
to `module.gke_cell` takes `dev` from 42 edges to 63 and creates exactly the two
edges you want (`cell` and `node` → `enabled`). It is coarse — it also orders
against buckets and WIF — but API enablement genuinely is a project-wide
precondition, so that is defensible. Its only real cost is the untestability
above.

If the CI-grep fallback is taken instead, note the obstacle: **`terraform graph`
refuses to run under `init -backend=false`** (measured: *"Backend initialization
required"*), which is how CI initializes today, so it cannot be dropped into the
existing infra job as-is.

## Acceptance criteria

1. `terraform graph` for **both** envs shows at least one **incoming** edge to
   `module.project_base.google_project_service.enabled` (or to an output derived
   from it) **from** `module.gke_cell` and from `module.network` — i.e. matching
   `-> "module.project_base.google_project_service.enabled"`. The direction is
   part of the AC: the source-side form is satisfiable only by an inverted
   dependency, which would be worse than the bug.
2. `project-base`'s OWN resources are ordered against `enabled` too. Five of the
   consumers named above live inside that module — the four buckets (`storage`),
   the KMS ring (`cloudkms`), the WIF pool (`iam`), the AR repo
   (`artifactregistry`) and `ci_plan_viewer` (`cloudresourcemanager`) — and a
   `depends_on` on *consuming modules* does nothing for them. Without this AC the
   task is verifiably "done" with most of the documented gap still open, and the
   documented bootstrap step (`-target=module.project_base`) still races.
3. A `.tftest.hcl` assertion that is **green with the ordering present AND red
   with it removed**. Both halves, stated explicitly: a check built from the
   inverted grep in the Why section would be red *always* and would satisfy a
   one-sided "prove it goes red" obligation while never going green. A check that
   cannot pass is no better than one that cannot fail
   (`contexts/provisioning.md`). If `terraform test` cannot express it, a CI grep
   is acceptable under the same two-sided proof, subject to the backend
   constraint above.
4. The evidence in the PR is the measured edge counts before and after, in the
   correct direction, not an assertion that the edge exists.

## Notes

Scope is ordering only. Whether the *list* is correct is T1.7 and is the
owner's call; this task must not change `local.services`.

**Do not oversell the fix when it lands.** `google_project_service` returning
success does not mean the API is immediately usable — GCP enablement propagation
lag is real, and `depends_on` narrows the race without closing it. The PR should
say so rather than let a later reader assume ordering is a total guarantee.
