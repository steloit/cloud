## Goal

Make API enablement a *predecessor* of the resources that need those APIs, so
`terraform apply` from zero is ordered rather than lucky.

## Why

`module.project_base` enables 14 services. **Nothing in either env depends on
that resource.** Measured, not read — the plan graph, built in a throwaway copy
of `infra/` (`terraform init -backend=false`, backend block neutralized in the
copy only):

    $ terraform graph | grep '"module.project_base.google_project_service.enabled" ->'
    (no output)

Zero outgoing edges — in **both** envs, and not because the grep found an empty
graph: `dev` has 42 edges and `cell0` 40. Every consumer is unordered with respect to it: the cluster
(`container`), the subnetwork (`compute`), four buckets (`storage`), the KMS ring
(`cloudkms`), the WIF pool (`iam`), the scheduler jobs, the budget. The only
edges out of `project_base` at all are its own internal ones plus two into
`module.cnpg`, which exist because cnpg *consumes a bucket output* — an accident
of data flow, not an ordering decision.

Today this is masked: the project was bootstrapped by a documented one-time
`gcloud services enable` **before** the first apply
(`docs/founder-config.md` §2), so by the time Terraform runs, the APIs are on.
That makes the bootstrap procedure load-bearing in a way nothing enforces, and
it is exactly why the missing 15th API (T1.7) surfaced as a runtime failure in
US-3.3c rather than as a plan error.

## Approach

`depends_on = [module.project_base]` on the consuming modules is the blunt fix
and is probably right; it is coarse (it also orders against buckets and WIF) but
API enablement genuinely is a project-wide precondition. Consider instead an
explicit `apis_ready` output from `project-base` threaded into the modules, which
documents the edge at the call site and keeps the graph readable. Whichever is
chosen, the change must not be justified by taste — assert it.

## Acceptance criteria

1. `terraform graph` for **both** envs shows at least one edge from
   `module.project_base.google_project_service.enabled` (or an output derived
   from it) into `module.gke_cell` and `module.network`.
2. A `.tftest.hcl` assertion that fails if the edge is removed — a graph
   property is otherwise invisible to the existing suites, which is how it got
   here. If `terraform test` cannot express it, a CI step that greps the graph
   is acceptable **only** with a proof that the step goes red when the
   `depends_on` is deleted; a check that cannot fail is not a check
   (`contexts/provisioning.md`).
3. The evidence in the PR is the graph output before and after, not an assertion
   that the edge exists.
