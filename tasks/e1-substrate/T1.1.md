## Goal

The complete Terraform layout for both GCP projects — authored, validated, and reviewable now; applied the moment P1 (GCP project) lands.

## Why

Everything in E1 (spike, operator, control plane, observability) deploys onto this substrate; INF-001's "cheap on capacity, never on shape" only holds if shape is expressed once, in modules, from day one.

## Read first

- `docs/plan/e1-substrate-design.md` §1 — the module/env layout this task implements verbatim
- `docs/architecture.md` §14 — deployment decisions (zonal GKE Standard, pools, workload identity, Secret Manager+KMS)

## Approach

1. `infra/modules/project-base`: API enablement, GCS state+artifact buckets (uniform access, versioned), KMS keyring, workload-identity pool + GitHub-Actions provider binding. Providers pinned (`google` ~> 6.x); `required_version` pinned.
2. `infra/modules/network`: one VPC, per-cell subnet, Cloud NAT, external LB IP + managed cert placeholders; a DNS zone variable for the content eTLD+1 (A2.4 — zone created only when the P2 domain exists; guarded by `var.content_domain != ""`).
3. `infra/modules/gke-cell`: zonal GKE Standard; three pools — `core` (floor 1, A1.6), `zfs-storage` (local-SSD machine type, tainted for storage workloads), `workload` (gVisor `sandbox_config`, `min_node_count = 0`). Workload identity on; no client cert, no basic auth; release channel REGULAR.
4. `infra/modules/observability` + `infra/modules/cnpg`: stub module shells with variables + versions only (implemented by T1.5/T1.2 — see Out of scope); included so envs compose the full shape from day one.
5. `infra/modules/duty-cycle` (dev only): shell for the T1.6 mechanism (scheduled node-pool resize).
6. `infra/envs/dev` (us-central1) and `infra/envs/cell0` (asia-south1): compose all modules; ONLY size/count/region variables differ. GCS backend blocks parameterized (`backend "gcs" {}` + `-backend-config` documented in infra/README.md) so `init -backend=false` validates locally.
7. Every resource that supports labels carries `labels = { cell_id = var.cell_id, managed_by = "steloit-terraform" }` (US-1.1 / invariant 1).
8. `infra/README.md`: apply order, backend bootstrap (state bucket chicken-and-egg: one-time `-backend=false` apply of project-base), CI wiring note (plan on PR, founder applies).

## Edge cases

- P1 not yet available → everything must validate with `-backend=false` and no credentials (verify proves it).
- Content domain (P2) absent → DNS zone conditional on `var.content_domain`; `terraform validate` type-checks both branches.
- State-bucket bootstrap → documented one-time procedure in README; never auto-created by the env that uses it.

## Security & performance

- Zero static keys anywhere: workload-identity federation for CI, GKE workload identity for pods (D5). No `google_service_account_key` resources — grep-clean.
- gVisor on the workload pool only; core pool untainted for system + api (D7).
- Buckets: uniform bucket-level access, public access prevention enforced.

## Acceptance criteria

- [ ] WHEN `terraform validate` runs in both envs with `-backend=false` THEN it passes with no credentials
- [ ] WHEN modules are diffed THEN no capacity literal (node counts, machine types, disk sizes) appears in `modules/` — all flow from env variables (shape/capacity law)
- [ ] WHEN any taggable resource is inspected THEN it carries the `cell_id` label
- [ ] WHEN the repo is grepped for `google_service_account_key` THEN there are zero matches
- [ ] infra/README.md documents bootstrap, apply order, and the P1/P2 gates

## Validation

The `verify:` block (fmt + validate both envs) runs locally and in CI on the PR. PR evidence: verify output + `grep -rn google_service_account_key infra/ || true` showing empty.

## Common mistakes

- Hardcoding project ids — both are variables until P1 supplies real ids.
- Putting machine types / node counts in modules (capacity belongs to envs; shape to modules).
- Creating the DNS zone unconditionally (P2 gate).
- A `backend "gcs"` block with a hardcoded bucket — breaks `-backend=false` local validation.
