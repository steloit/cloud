## The defect

`cnpg.SnapshotBranch` and `cnpg.PITRBranch` hardcode `StorageSize: "10Gi"`
(`cnpg.go:201`, `cnpg.go:233`) instead of sizing from the source cluster's shape.

A branch of a `standard` therefore asks for a **10Gi** volume from a snapshot
whose `restoreSize` is **50Gi**. Kubernetes supports volume EXPANSION only — a PVC cannot shrink, and a request
below `.status.capacity` is rejected
([k8s.io storage docs](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)).
A restore into a PVC smaller than the snapshot's `restoreSize` is therefore
refused, so the branch does not come up small — it does not come up at all.
**Verify this against the GKE PD-CSI driver before implementing**; the general
no-shrink rule is documented, the specific snapshot-restore error is asserted
here by inference and should be measured.

## Why now

T3.4c fixed the same class in `Render` and, in doing so, **widened this gap**:
`standard` went from 32Gi to 50Gi, so the mismatch grew from 32→10 to 50→10.
Found by T3.4c's architecture review.

Neither entry point is wired to a caller yet, which is why this is a follow-up
rather than a blocker — but the AC T3.4c claims ("the PVC is sized from the priced
`storage_gb`") is only true of `Render` until this lands.

## Acceptance criteria

1. A branch and a PITR restore size their volume from the **source service's**
   resolved `storage_gb`, never a constant.
2. A test asserts, for every size in `pricing.json`, that a branch of that size
   renders a volume at least as large as the source — reading the catalog, not a
   retyped list (the T3.4c pattern).
3. Mutation-verified: reinstating a hardcoded size is RED. Run the sweep on a
   harness whose no-mutation baseline is asserted GREEN — a module-only `cp -R`
   of `services/cell-agent` is red on arrival (three `parity_test.go` cases need
   the repo root).

## Outcome

`SnapshotBranch` and `PITRBranch` size their volume from the **source service's
shape**, through the same `storageForShape` that sizes a create — so the three
paths cannot drift again. `driver.BranchSource` gained a `Shape` field to carry
it.

**The shape, not a resolved size string.** A `StorageSize string` on
`BranchSource` would let each caller compute its own answer, which is exactly how
the two branch paths came to hardcode `10Gi` while `Render` was reading the
catalog.

### The two failure modes are NOT the same, and the task treated them as one

The comment on the constant said *"CoW clone; sizing follows the source PVC"*. It
does not — `.spec.resources.requests.storage` is what the PVC asks for — and the
two paths fail differently:

- **A snapshot restore is REFUSED outright**, above the CSI driver, by
  external-provisioner: *"requested volume size %d is less than the size %d for
  the source snapshot %s"*. [kubernetes-csi/external-provisioner#727](https://github.com/kubernetes-csi/external-provisioner/issues/727)
  asked for the request to be treated as a minimum and was closed **not
  planned**, so this is durable behaviour and **not GKE-specific**. A branch of a
  `standard` (50Gi) asking for 10Gi does not come up small — it does not come up.
  The task's inferred claim is CONFIRMED, with a named enforcement point.
- **A PITR restore is NOT refused, and that is worse.** There is no snapshot data
  source, so no `restoreSize` to compare against, and CNPG documents no size
  requirement of its own — it passes `storage.size` straight through. The 10Gi
  volume is created happily and the base backup + WAL replay fills it until it is
  full. The failure lands mid-restore and only when the source actually holds
  more than 10Gi, so a large-but-empty source hides it indefinitely. **Here the
  rendered manifest is the only line of defence**, which the task did not
  distinguish.

### A missing shape is refused, not defaulted

`storageForShape` reads an absent size as `dev` (the API's closed schema defaults
it) — correct for a create, and it would have silently re-rendered `10Gi` here.
So a nil `Shape` is an error, while an empty-but-present one stays legal (a dev
postgres names no size). Mutation M3 confirms the guard is load-bearing.

### Review round 2: the same "two representations, one covered" hole, again

QA found a **blocking** gap: the PITR path was never tested with a priced
`storage_gb`. A mutation stripping it from PITR alone stayed green —
`{size: performance, storage_gb: 2000}` rendered create=2000Gi,
snapshot=2000Gi, **pitr=50Gi**. That is the path with no `restoreSize` refusal in
front of it, i.e. the one this task calls the only line of defence. The sibling
mutation on the snapshot path died, which is exactly why it looked closed.

Fixed by making the sweep **two-dimensional**: every catalog size × every
storage relation to the included floor (unset, zero, exactly included, well
above, one below) × **both** entry points, all bound to what `Render` produces
for the same shape. One table closes the blocking gap and both below-floor gaps
together. The storage dimension matters on its own: shapes of the form
`{"size": X}` with no `storage_gb` are shapes the API never emits, so the
original size-only sweep tested the one shape that does not occur.

**The size assertion was positional, not structural.** `renderedStorageGB` took
the *first* `size:` in the document, correct only by accident of field order.
Measured: adding a `spec.walStorage` block above `spec.storage` and regressing
`spec.storage.size` to a literal `10Gi` left the entire module green — every
assertion measured the WAL volume while the data volume was the old constant,
and `-update` regenerated the goldens without complaint. It reads
`spec.storage.size` **by path** now, and that mutation is RED.

**The Shape contract has one owner.** The nil check moved to
`driver.BranchSource.RequireShape`, next to the field it guards, so a second
`BranchingDriver` does not have to re-derive it (ADR-0014). It cannot be a
compile-time guarantee while `BranchSource` is a struct literal, so it fails
closed at render.

**Two error-path assertions were weakened by my own diff** — both passed a nil
`Shape`, so each had two independent reasons to fail and neither checked the
message, leaving guard ORDER silently load-bearing for a test that never
mentioned it. They supply a shape and check the message now, which removes the
dependency rather than pinning it.

### Evidence

Every catalog size is bound to what `Render` produces for the same shape —
reading `pricing.json`, not a retyped list (the T3.4c pattern), and by
**equality** rather than `>=` for the reason T3.4c recorded: an inequality binds
one direction only. Equality satisfies AC 1's "at least as large" a fortiori.
Priced `storage_gb` above the included floor is covered separately, since a
floor-only fix would be short by exactly what the customer bought.

Four mutations RED on a baseline asserted green **before and after**, in a
scaffolded `cp -R` sandbox:

| mutation | |
|---|---|
| snapshot branch back to a hardcoded `10Gi` | RED |
| PITR back to a hardcoded `10Gi` | RED |
| the nil-`Shape` guard removed (silently defaults to dev) | RED |
| the branch ignores the source shape entirely | RED |
| **PITR ignores the priced `storage_gb`** (QA's blocker) | RED |
| the branch bypasses the included floor | RED |
| the branch drops `size` when `storage_gb` is present | RED |
| `walStorage` added above `storage`, data volume back to `10Gi` | RED |

One mutation is a genuine **equivalent**: hoisting `branchStorage` above the
name/Target guards changes no outcome now, because the error-path tests were
given a shape and no longer depend on that order. Recorded rather than pinned —
inventing a test for a difference nothing can observe is the pattern this repo
already rejects.

### Recorded, not fixed here

- **What a branch deliberately does NOT inherit.** The branch templates hardcode
  `instances: 1` and carry no `backup.barmanObjectStore` or `ScheduledBackup`, so
  a branch of an HA source comes up single-instance and is not itself restorable.
  Both pre-existing; but this diff now plumbs the *whole* shape (which carries
  `ha`) while consuming only its storage dimension, so which dimensions a branch
  declines to inherit deserves an explicit decision.
- **PITR replays WAL into `pg_wal` on the same PVC** — no template declares
  `walStorage` — so a source running near-full can still fill its restore at the
  source's own size. No render-time input fixes that, and over-provisioning would
  misprice.
- The sizing is from the SHAPE, which equals the source's PVC only while nothing
  resizes it out of band. Reconciling a shape against an actual PVC is beyond a
  cluster-free renderer.
- `tenancy.go`'s justification block for withdrawing `requests.storage` still
  cites numbers T3.4c falsified (`storage_gb: 0` for all sizes; 10/32/128Gi). It
  is the standing record for a withdrawn enforcement and now misdescribes both
  planes — pre-existing, and a follow-up on **US-3.3i**.

Neither entry point has a production caller yet, so this closes the rendering
defect but nothing exercises it end to end. Whatever wires the branch API (D2)
owns plumbing the source service's shape into `BranchSource` — the nil guard is
what makes forgetting it loud rather than a 10Gi volume.
