## The defect

`cnpg.SnapshotBranch` and `cnpg.PITRBranch` hardcode `StorageSize: "10Gi"`
(`cnpg.go:181`, `cnpg.go:213`) instead of sizing from the source cluster's shape.

A branch of a `standard` therefore asks for a **10Gi** volume from a snapshot
whose `restoreSize` is **50Gi**. The CSI driver **rejects** a restore into a PVC
smaller than the snapshot, so the branch does not come up small — it does not come
up at all.

## Why now

T3.4c fixed the same class in `Render` and, in doing so, **widened this gap**:
`standard` went from 32Gi to 50Gi, so the mismatch grew from 32→10 to 50→10.
Found by T3.4c's architecture review.

Neither entry point is wired to a caller yet, which is why this is a follow-up
rather than a blocker — but the AC T3.4c claims ("the PVC is sized from the priced
`storage_gb`") is only true of `Render` until this lands.

## Acceptance criteria

1. A branch and a PITR restore size their volume from the **source service's**
   resolved `storage_gb`, never a constant.
2. A test asserts, for every size in `pricing.json`, that a branch of that size
   renders a volume at least as large as the source — reading the catalog, not a
   retyped list (the T3.4c pattern).
3. Mutation-verified: reinstating a hardcoded size is RED. Run the sweep on a
   harness whose no-mutation baseline is asserted GREEN — a module-only `cp -R`
   of `services/cell-agent` is red on arrival (three `parity_test.go` cases need
   the repo root).
