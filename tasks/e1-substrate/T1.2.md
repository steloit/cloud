## Goal

The production CNPG operator + OpenEBS ZFS-LocalPV storage layer deployed by Terraform/manifests — the substrate a customer database is born on, shaped by T1.0's measured findings.

## Why

Every customer Postgres (and the control-plane DB) runs on this layer; the spike proved the mechanics, this makes them the deployable, versioned shape (ADR-0003; one operator to know everywhere).

## Read first

- `docs/adr/0007-substrate-spike-findings.md` — the working storageclass/snapshotclass yaml and every measured constraint (this task productionizes exactly what worked)
- `docs/plan/e1-substrate-design.md` §1 (module shells to fill) + §2 (what the reconciler will later render — T1.2 installs platform, not per-customer clusters)
- `docs/architecture.md` §3 — CNPG ≤ 1.30 pin (in-tree Barman) and the version-knob note
- Don't read: console/UI docs.

## Approach

1. Fill `infra/modules/cnpg`: operator install (pinned ≤ 1.30 per architecture §3, via whichever mechanism the spike used), operator config, and the control-plane CNPG cluster (single instance, PITR to its own GCS bucket — invariant 10).
2. Fill the storage side of `infra/modules/gke-cell` + `infra/k8s/storage/`: OpenEBS ZFS-LocalPV install, `StorageClass` (the spike's parameters verbatim), `VolumeSnapshotClass` — the exact yaml T1.0 proved, no improvisation.
3. `infra/k8s/` manifests are plain yaml applied by Terraform (`kubernetes_manifest`/helm provider) — one apply path, no second tool.
4. WAL archiving defaults (`archive_timeout` per the measured RPO number) templated into cluster config; the value cites the findings ADR.
5. Wire into both envs; dev applies first; cell0 is identical shape.

## Edge cases

- CNPG version pin vs upgrades: the pin is a tracked knob (architecture §3) — a bump is a PR citing the barman-cloud issue status, never a drive-by.
- Local-SSD node replacement loses pool state by design — document the node-pool recreate procedure and blast radius (dev: acceptable; cell0: drains first).
- ZFS kernel module vs GKE node image — pin the image the spike proved.

## Security & performance

Operator in its own namespace, least-privilege RBAC as shipped upstream (no cluster-admin widening); storage pool nodes tainted `storage=zfs:NoSchedule` so only CNPG pods land there.

## Acceptance criteria

- [ ] WHEN `terraform validate` runs (dev, `-backend=false`) THEN it passes with the cnpg + storage modules filled
- [ ] WHEN manifests are parsed THEN all are valid yaml (verify) and match the spike's proven storageclass/snapshotclass parameters
- [ ] WHEN the operator version is grepped THEN it is pinned ≤ 1.30 with the architecture §3 citation beside it
- [ ] WHEN applied on dev (founder present for apply) THEN a test CNPG cluster reaches healthy and a snapshot→recovery round-trip succeeds (evidence in PR)

## Validation

`verify:` block locally + CI. Apply evidence (AC 4) recorded in the PR when P1/dev exists — authored-vs-applied split mirrors T1.1.

## Common mistakes

- Diverging from the spike's proven yaml "while cleaning it up" — productionize verbatim first; refactor as a separate reviewed change.
- Installing a second apply tool (kustomize/argo) — Terraform is the one apply path at this stage.
- Unpinned operator version.
