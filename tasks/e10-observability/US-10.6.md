## Goal

Pin `NotificationList.data[].kind` to the seven kinds the founder ruled, and
reconcile the rows already written under the old free-text column.

## Why

`kind` is a bare string today (`openapi.yaml:1984`) with no CHECK constraint, so
any writer can invent a value and N2's type chips cannot be trusted. The founder
ruled the taxonomy on 2026-07-20 (Option B, ledger row "[RULED — founder]").

## Blocked on

**A `00-sources` frame amendment the founder must make** — `docs/product/00-sources/**`
changes by human decision only (hook-enforced). Two edits are required before any
code moves:

1. **P6 routing matrix** — add a `Billing` row and a `Security` row alongside the
   existing six (Alerts · production / Alerts · non-production / Assistant
   proposals / Approvals assigned to me / Deploys / Lifecycle), each with its
   In-app / Email / Mobile push defaults.
2. **N2 type chips** — add the two corresponding filter chips.

Until both land, `Classify` (US-10.3) emits only kinds that have a frame row, and
this task stays `blocked`. Flip to `stub` when the frames are amended, then enrich.

## The ruled taxonomy — do not extend it

`alert · proposal · approval · deploy · lifecycle · billing · security`

**Seven. No more.** Any eighth kind is a new founder decision, not an engineering
call (§5 rule 10). `billing` and `security` are first-class because both are
already emitted and spec-mandated (`quota_warning.go:29`; `flows.md:19` requires
the 80% billing bell; design-spec P6's escalation paragraph and US-10.2's
`Urgent` presuppose a security class) — collapsing them into `alert` would make
N2's "Alerts" chip a filter that lies.

## Scope when unblocked

- Amend `openapi.yaml` `NotificationList.data[].kind` to the seven-value enum;
  Trap T2 order (`make gen-go` → `make gen-ts`), commit all generated files.
- Decide and implement the legacy-row reconciliation: rows already carrying
  `billing`/`security` become valid under the enum, so the question is whether
  any *other* stray value exists — audit before assuming none.
- Add a DB-level CHECK or a structural test so a new invented kind fails loudly
  rather than silently reaching the console.
- Extend `notify.Classify`'s table to cover the billing/security actions once
  their frame rows exist to source titles from.

## Out of scope

- Per-type routing preferences (P6's matrix columns) — `NotificationPrefs.channels`
  is `{email, inapp}` only and cannot express per-type or `Mobile push`. Separate
  contract change, separate task.
