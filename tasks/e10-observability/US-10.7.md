## The defect

`GET /v1/envs/{env}/events` uses the env path parameter **only to resolve the
org**, then pages the entire org's events (`events_http.go` → `reader.Page(ctx,
orgID, …)`). There is no env predicate anywhere in the read path.

Demonstrated (US-3.8 QA, 2026-07-27): two environments in one project, a manual
instance-pin applied in each. The **production** env's feed returns the
**staging** env's scale event, including the operator's free-text reason
verbatim.

Authorization is per-env — `rbac.Scope{OrgID, EnvID}` — and `rbac.go` states
that "environment-sensitive restrictions are ALWAYS policies". So a policy that
narrows `observe.read` to one environment is **defeated by the read path**: the
check passes for the env named in the URL, and the response then carries the
others. That is the gap between what the authorization model promises and what
the query does.

## Second defect, same file

**The `kind` filter filters nothing any test checks.** Replacing `kind = $3`
with `true` in `ListOrgEventsDesc` leaves the **entire API suite green**. The
same holds for `/orgs/{org}/audit`'s `actor` and `action` filters.

US-3.8 added a test whose stated premise is "ListEvents filters on kind, so the
release's kind is load-bearing for it appearing in the same filtered view" —
that premise is currently unpinned.

## Decide first, then build

**Is the org-wide read intended?** The path says `/envs/{env}/events` and the
authz scope is per-env, which argues no. But this is an endpoint-shape question
that predates US-3.8 and should be answered rather than assumed:

- **If env-scoped** (expected): add the predicate, and assert every returned
  subject belongs to the named env.
- **If org-wide by design**: say so in `openapi.yaml`'s summary, and the
  assertion becomes the opposite — plus the policy-narrowing story needs an
  answer, because today it does not hold.

## Notes

Found by US-3.8's QA sweep. Not fixed there: US-3.8 owns the pin, not the
observability read path, and the env-scoping question needs a decision before
code. US-3.8's feed test selects by subject, so it neither depends on nor
cements the org-wide behaviour — but it would keep passing if the leak were
never fixed, which is why this is filed rather than left implicit.

Related, low, same file: the 404-conversion prefix `key:` also catches
`key:not granted <perm>` — a key WITH standing in the org that merely lacks the
permission — which by `api-conventions.md`'s own logic is the key analogue of a
`role:` denial and should arguably be an honest 403. `policy_http.go` carries
the identical shape, so this is a convention-wide question, not a US-3.8 one.
Changing it in one endpoint would make that endpoint the outlier.
