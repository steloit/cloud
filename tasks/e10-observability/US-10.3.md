## Goal

The bell rings for what actually needs a person: notification-worthy spine events
project exactly once into per-user bell rows with frame-sourced titles, so the
rows a console badge counts are a projection of the spine and not of raw events.

## Why

S4 named the notifications family the highest-frequency gap (8 blocked surfaces).
T10.3 built the store, the routing matrix and webhook delivery — but nothing
rings the bell in a running system, and the console bumps the badge on **every**
spine event, so the badge and the list disagree today
(`spec-change-proposals.md:204` and `:225`, which names the N1 slice as owner).
This task is that slice.

## Approach

**No contract change.** The kind enum this task originally proposed is deferred
to a §8 proposal (§ Out of scope) — shipped rows already violate it. `Classify`
emits the frame vocabulary for *new* rows; `kind` stays a bare string on the wire.

1. **`notify.Classify(action string) (kind, title string, ok bool)`** — a pure,
   table-driven map from spine `action` → frame kind + title template. `ok=false`
   means **not notification-worthy**, and is the common case: silence is the
   default. Titles are copied from N1/N2; an action with no frame row returns
   `false` rather than a guessed title. Each table entry carries a comment citing
   its frame id + gallery line.
2. **A durable cursor, not row-absence, drives the scan.** Migration
   `bell_cursor`: a single row `(id bool PK DEFAULT true, last_at timestamptz,
   last_event_id text)`. This is the correction that makes the design work —
   see § Common mistakes for why mirroring the webhook query directly starves.
3. **`ListPendingBellEvents`** (`db/queries/notify.sql`) — keyset forward scan:
   `WHERE (e.at, e.id) > (@last_at, @last_event_id) ORDER BY e.at, e.id LIMIT
   @lim`. Keyset on the **pair**, because `ids.New` is random hex and `at`
   collides freely under batch projection.
4. **`Router.ProcessBell(ctx) (int, error)`** — one batch, **one transaction**:
   `SELECT … FROM bell_cursor FOR UPDATE` (this serializes replicas — see
   Security), scan, `Classify` each event, insert bell rows for the worthy ones,
   then advance the cursor to the **last scanned** event — worthy or not — and
   commit. Because the cursor advances past silent events, they can never
   re-enter the window; because the fan-out and the advance share one tx, a crash
   rolls back both and the retry re-fans **every** member. Still set `EventID` on
   each insert so the partial unique index dedupes as a second line of defence.
5. **Reuse `Notify`'s per-member prefs/quiet-hours fan**; do not fork it. Note
   `Notify` currently swallows a per-member insert error (`notify.go:112-120`
   logs and continues, returning nil) — inside a transaction that must become a
   hard error, or a partial fan-out commits and is never retried.
6. **Wire it** in `cmd/api/main.go` beside `RunOutbox` (`main.go:230`).
7. **Reconcile the second bell path.** `EmitQuotaWarning` (`quota_warning.go:28`)
   inserts a bell row directly, bypassing `Classify` and setting no `EventID`, so
   its rows are un-deduped. Either route it through the projection or record why
   it stays imperative — do **not** leave two unreconciled writers.
8. **File the deferrals** (§ Out of scope) as ledger rows in the same PR, and add
   the head-of-line lesson to `contexts/events-spine.md`'s mistake bank.

## Edge cases

- **A long run of non-worthy events** → the cursor advances past them; the next
  worthy event is still reached. This is the head-of-line case
  (`TestBellScanDoesNotHeadOfLineBlock`) and it is the whole reason for step 2.
- **Crash mid-fan-out** → the tx rolls back, the cursor does not advance, and the
  retry re-fans every member. A design where the cursor advanced independently,
  or where `Notify` swallowed a member error, would silently drop members 4–10 of
  a 10-member org forever.
- **Re-scan after a clean batch** → the cursor is past those events; zero new
  rows (`TestBellProjectionIsIdempotent` asserts the second call reports 0).
- **Quiet hours** → gate the **email route only**; the bell row is inserted
  regardless (routing ≠ recording; held by
  `TestQuietHoursRouteOnlyNeverRecordOrFire`, which is in `verify:` so this task
  cannot break it and stay green).
- **Late joiner** → gets no backfill *by construction*: the cursor is already past
  the org's history, and membership is read at projection time. Pin **both**
  halves — the new member has 0 rows and existing members are not re-notified.
- **Ordering** → the list orders by `created_at DESC` (`notify.sql:29`), which is
  *projection* time, not event time. After downtime a whole backlog lands at
  `now`, so N1's "then time" would show the wrong order. Persist the event's `at`
  onto the row and order by it.
- **Zero unread** → N3: the pill is **absent, not `0`**. A rendered `0 unread` is
  a defect against N3. (Console-side; this task only supplies the rows.)
- **Three `kind` vocabularies exist** — frames (`alert|proposal|approval|deploy|
  lifecycle`), the spine's own (`events.go:23`), and Go's ad-hoc
  `billing|lifecycle|security`. The frames win for **new** `Classify` output;
  legacy rows keep their values until the §8 proposal rules a mapping. Do not
  invent a mapping here (§5 rule 10).

## Security & performance

- `SELECT … FROM bell_cursor FOR UPDATE` serializes concurrent replicas: the
  second blocks, then resumes from the advanced cursor. Without it, two API
  replicas double-project — and while bell rows dedupe on the unique index, the
  **email** send has no ledger and no lease, so the user gets two mails.
- The batch is bounded (`LIMIT`) and the tx must not span a network call. Email
  send inside the projection tx would hold the cursor lock across SMTP —
  enqueue or send after commit, accepting at-least-once.
- Per-member fan-out is O(members) per worthy event; keep `Classify` pure and
  allocation-free so a large org does not stall the loop.
- No new error class (Trap T3) — reuse the existing catalog.

## Acceptance criteria

- [ ] WHEN a spine event has no frame-sourced classification THEN no notification
      row is created — silence is the default.
- [ ] WHEN 150 consecutive non-worthy events precede a worthy one THEN the worthy
      one still produces bell rows (the scan window cannot be poisoned).
- [ ] WHEN a notification-worthy event is projected THEN every current org member
      gets exactly one bell row, whose title's static skeleton appears **verbatim
      in the frame gallery source** (mechanically asserted, not eyeballed).
- [ ] WHEN `ProcessBell` runs twice over the same events THEN the second call
      reports 0 new rows and the row count is unchanged.
- [ ] WHEN a per-member insert fails mid-fan-out THEN the batch rolls back and a
      later run notifies **all** members — no member is silently skipped.
- [ ] WHEN a member joins after events were projected THEN they receive no
      backfill AND existing members are not re-notified.
- [ ] WHEN quiet hours are active THEN the bell row is still written and only the
      email route is suppressed (existing test, kept in `verify:`).

## Common mistakes

- **Mirroring `ListPendingWebhookEvents`' "handled" predicate.** That query is
  self-limiting only because its filter (`e.kind = ANY(w.events)`) is **in SQL**,
  so undeliverable events never enter the pending set, and `webhook_deliveries`
  records a terminal row for the rest. `Classify` runs **in Go**, so a non-worthy
  event would leave no row, permanently satisfy `WHERE n.id IS NULL`, and occupy
  a slot in every later `LIMIT` window — after one batch of silence the bell stops
  ringing forever. Advance a cursor for every *scanned* event, worthy or not.
- **Trusting `ON CONFLICT DO NOTHING` for idempotency while also skipping already-
  projected events.** The two are mutually exclusive: if the scan excludes them,
  the conflict never fires. The cursor is the mechanism; the index is the backstop.
- **Letting `Notify` swallow a member error inside the tx** — a partial fan-out
  that commits is never retried, and no return value reveals it.
- **Inventing a title.** No frame row → `Classify` returns `false`.
- **Adding an `unread_count` field or a count endpoint.** The design spec makes
  the count derived (`:410`); serving it creates a second truth that can drift.

## Out of scope

This task is **the server-side bell projection only**. Everything below is a
ledger row filed in this PR, not silent. The first four were carved out of an
earlier draft of this task on review — it was four concerns, not one (§5 rule 12).

- **The `kind` enum** `[alert, proposal, approval, deploy, lifecycle]` — §8
  proposal, **not inline**: shipped rows already carry `billing`
  (`quota_warning.go:29`) and `security`, so pinning the enum would make
  `listNotifications` emit contract-invalid values for existing rows. The
  proposal must rule the legacy mapping **and** the backfill-or-tolerant-read.
- **`unread=false` ⇒ read-only rows** — an invented semantic. N2's tabs are
  `All / Unread / Needs action`; no frame asks for a read-only view, and today's
  `IS NOT TRUE` is a defensible reading of "absent or false ⇒ unfiltered".
- **`testWebhook` HTTP-layer coverage** — own task; shares no code with the
  projection. **It carries a live defect** (below).
- **The console badge half** — `bumpLive()` counts every spine event
  (`features/notifications/data.ts`, `app/shell/ctx.tsx:57`). This task supplies
  correct rows; the console fix, plus the degraded-transport affordance
  `:225` also assigns to the N1 slice, is a console task with its own
  `pnpm --filter console lint/test` gates (Trap T6).
- `deleteWebhook` / `PATCH /webhooks/{wbh}` — absent from the contract entirely;
  adding an operation is a §8 proposal first (Trap T2).
- `needs-action` grouping (N1/N2) — depends on **approval threads**, proposed in
  §2c but never specced.
- SSE live delivery for `/me/notifications` — `x-streamable: true`
  (`openapi.yaml:955`) but no streamer, and `events.Hub` is org-keyed
  (`hub.go:15`), so a per-user stream needs a new subscription key.
- P6's **per-type** matrix and `Mobile push` — `NotificationPrefs.channels` is
  `{email, inapp}` only; "Alerts · production is always in-app, not a preference"
  is unexpressible in the current shape.
- `Urgent` source + the email-off-override ruling — E7/auth owns (`:239`).
- Webhook-per-org cap, webhook delivery lease — T10.3 review items.
- `models.md` documents neither `notifications` nor `webhooks` — S-process item.
