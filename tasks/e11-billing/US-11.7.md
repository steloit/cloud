## Goal

An org's hard monthly spend bound is ENFORCED by construction: a provision whose
acceptance would cross the cap is refused at accept time (402) with the math;
nothing running is affected; every cap hit is on the events spine. F9 flagship
"the cap is real" — a bound, not an alert.

## Read first

- internal/provisioning/services.go enforceBudget (T11.6): the cap check at the
  CreateService/scale gate (planFee + committed vs LimitCents).
- docs/product/08-api/openapi.yaml x-error-catalog: quota_exceeded (402, "hard
  quota: fails with remediation") is the SANCTIONED type — no new error class.
- messaging.md F9 "the cap is real" clause (founder-approved 2026-07-18).

## Approach

The enforcement machinery shipped with T11.6 (budget endpoint B1, enforceBudget
at the create + scale gates). US-11.7 ELEVATES it to the flagship guarantee:
1. The refusal is now 402 (quota_exceeded — the catalog's sanctioned hard-quota
   family), not the earlier 409, matching the F9 402 family. No new error class
   (the closed x-error-catalog forbids local additions).
2. Every cap hit emits a `billing.spend_cap_reached` spine event (cap, current,
   requested, projected cents) — auditable, not just a UI toast.
3. Tests prove BLOCKED-not-warned: the over-cap provision creates NO service;
   raising the cap resumes the same estimate; scale-up respects the cap too.

## Acceptance criteria

- [x] Accepting an estimate that would cross the cap is refused (402
  quota_exceeded) with the arithmetic in the message; the service is NOT created.
- [x] The cap is enforced at the API layer (create AND scale), never client-only.
- [x] Every cap hit is on the events spine (billing.spend_cap_reached).
- [x] Raising the cap resumes instantly (the same estimate provisions); nothing
  running is affected.

## Out of scope / findings

- "Soft-overage stops accruing at the cap" (AC2, quota-evaluator side) is the
  T11.5/US-11.2 metered-quota coupling — the provision cap (this flagship) is
  delivered; the soft-overage-halt-at-cap is recorded for US-11.2.

## Outcome

The hard spend cap is now the F9 "the cap is real" guarantee: enforceBudget
refuses an over-cap provision at accept time with a 402 quota_exceeded (the
x-error-catalog's sanctioned hard-quota family — NOT a new error class, which
the closed catalog forbids) carrying the arithmetic, and emits a
billing.spend_cap_reached spine event on every hit. The test proves the bound is
REAL: the over-cap create produces zero services (blocked, not warned), the
cap event lands on the spine, raising the cap resumes the same estimate, and a
scale-up past the cap is refused too (the create-only bypass is closed).
Deferred: the soft-overage-halt-at-cap coupling is US-11.2's metered-quota side.
