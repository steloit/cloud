## Goal

Invoice generator (accrue → open → paid/failed): lines carry usage_ref; totals
in integer cents; monthly close idempotent.

## Summary

**AC:** lines carry usage_ref; totals in integer cents; monthly close
idempotent.

## Outcome

`internal/invoice` freezes the meter on the billing anchor into an invoice
(B3: an invoice is DATA — every line expands to the meter rows behind it). The
migration adds `invoices(id, org_id, period, status, total_cents, lines jsonb,
tax, closed_at)` with `UNIQUE (org_id, period)`.

`Close(orgID, period)` builds the lines from the **same** sources the estimate
uses — the plan fee from the ONE billing table (`PlanFeeCents`; Enterprise is
custom-priced so no fee line) and one line per metered accrual from
`quota_usage` (the T6.3 rollup) — each carrying a `usage_ref` back to the B2
rows. The plan is read from the org's **own** plan row (`GetOrg`), never a
caller-supplied string — a wrong fee would be frozen permanently. Total = Σ line
cents, all **integer cents** (ADR-025), and the status is `open` (accrued → open
on close). The **monthly close is idempotent**: the `ON CONFLICT (org_id,
period) DO NOTHING` gate means a re-close returns the frozen invoice unchanged —
the meter is frozen once, never double-billed. The B3 read surface
(`GET /orgs/{org}/billing/invoices`, `billing.view`) lists them with lines +
usage_refs.

Verified against real Postgres: seeding the meter + closing produces plan-fee +
metered lines (each with a usage_ref), Σ lines == the integer-cent total, a
re-close returns the same invoice (one row for the period), a re-close **after a
`quota_usage` mutation does not re-price** the frozen invoice (the freeze is
real), and the list endpoint surfaces it.

Payment-status transitions (`open → paid/failed/disputed`) are driven by the
subscription/payment layer (T11.4/Stripe webhooks call `SetInvoiceStatus`).

**Findings (follow-ups filed — [spec-change-proposals.md](../../docs/product/claudedocs/spec-change-proposals.md)):**
`Close` has no production caller yet — nothing invokes it on the billing anchor.
The monthly-close scheduler (a periodic sweep that closes the *previous* period
for each org as its anchor passes, tracking closed periods) is separate infra,
deferred to a follow-up (candidate T11.6, alongside the T11.4 payment layer that
consumes the resulting `open` invoices). Mid-period plan changes are **not
prorated** — the fee line uses the org's plan at close time; proration is a
follow-up gated on real billing-anchor semantics.
