## Goal

The **flagship hard spend cap** (F9, elevated 2026-07-18): an org sets a monthly
bound and the platform *enforces* it — crossing it is impossible by
construction, not by vigilance — plus CSV exports of usage and invoices.

## Why

The cap is the wedge promise (feature-specs §31): "the cap is real; crossing it
is impossible by construction." It is the certainty story — a developer can hand
the platform their card knowing a runaway can't bankrupt them. Never alerts-only.

## Read first

- docs/product/05-features/feature-specs.md §31 — the cap semantics (VERBATIM
  law): set a hard monthly bound; at the bound new provisioning pauses and
  soft-overage stops accruing; **running services are never deleted, state kept,
  one click resumes on raise/renew**; the bound **composes with the estimate
  gate** — an estimate that would cross the cap is refused at accept with the
  math shown. AC: one arithmetic everywhere ($383 + $99 = $482 grammar).
- docs/product/08-api/openapi.yaml — `BillingOverview.budget` {limit_cents,
  used_percent, alert_thresholds} (read shape EXISTS); `getBillingOverview` (in
  the spec, not yet served). `setBudget` + export ops must be ADDED (owner-ruled
  2026-07-19: add to contract; CSV now, PDF deferred).
- services/api/internal/provisioning/services.go:117 — the estimate-accept gate
  (`est.Accept`) where cap enforcement hooks BEFORE provisioning.
- services/api/internal/estimates/service.go — `Shapes`/`Accept`; the estimate
  carries `total_cents` (monthly), the number the cap projects against.
- services/api/internal/invoice/invoice.go — the MTD-spend sources (plan fee via
  `billing.PlanFeeCents` + Σ `quota_usage.rate_cents`) to reuse verbatim.

## Approach

1. **Migration** `budgets` (org_id PK → orgs, limit_cents bigint NULL = no cap,
   alert_thresholds int[] default '{80}', updated_at). NULL/absent = uncapped.
2. **`internal/billing` cap helper** — `SpendToDate(plans, plan, usage) int64`
   = plan fee + Σ metered `rate_cents` (the SAME arithmetic as the invoice, so
   the shown number IS the enforced number). `Projected = SpendToDate + estimateCents`.
3. **`setBudget`** (`PUT /orgs/{org}/billing/budget`, `billing.manage_payment` or
   `subscription.change`) — upsert limit_cents + thresholds; a limit below the
   current MTD spend is allowed (it just pauses new provisioning immediately, it
   never deletes). Returns the budget object.
4. **`getBillingOverview`** — implement it (it owns the budget read): mtd_cents,
   plan/resources split, and `budget{limit_cents, used_percent, alert_thresholds}`.
   Keep it minimal-but-honest; by_project/forecast can be a follow-up if heavy.
5. **Enforcement at the accept gate** (`provisioning/services.go`): before
   `est.Accept`, load the org's budget; if `SpendToDate + estimate.total_cents >
   limit_cents`, **refuse at the API layer** (never client-only) with a
   problem+json carrying the math (`spend $X + estimate $Y = $Z > cap $C`) and
   remediation (raise the cap or shrink the shape). This is the estimate-gate
   composition — enforced where accept happens, so it is impossible to provision
   past the cap.
6. **CSV exports** (`exportUsage`, `exportInvoices`) — stdlib `encoding/csv`,
   `text/csv` + `Content-Disposition: attachment`. Rows are the same B2/B3 data.
   **PDF is a deferred follow-up** (frozen-stack dependency; owner-ruled).
7. Add the operationIds to `oapi-server.cfg.yaml`; `make gen`.

## Edge cases

- No budget row / limit_cents NULL → uncapped; accept always proceeds.
- Estimate exactly equals the remaining headroom → allowed (`>` not `>=`;
  the cap is a bound you may reach, not undershoot).
- Cap lowered below current MTD → new provisioning refused immediately; running
  services keep running + metering (cancel ≠ delete, US-11.5) — the cap pauses
  the FUTURE, never destroys the present.
- Soft-overage accrual past the bound stops (documented; the metering-side stop
  may be a follow-up if it lives in the rollup — record honestly if so).

## Security & performance

- Enforcement is at the API layer, never only a client (mirrors
  estimate-before-provision, an AGENTS.md hard rule).
- Budget read/write gated (`billing.*`); a non-billing member can't raise a cap.
- SpendToDate is one `GetQuotaUsage` read per accept — acceptable; cache only if
  the accept path shows it hot.

## Acceptance criteria

- [x] WHEN an org sets a budget THEN limit_cents + thresholds persist and the
  overview reports used_percent.
- [x] WHEN an accepted estimate would cross the cap THEN accept is refused at the
  API with problem+json showing the arithmetic (spend + estimate > cap).
- [x] WHEN under the cap THEN accept proceeds unchanged.
- [x] WHEN the cap is lowered below MTD THEN new provisioning refuses but no
  running service is touched.
- [x] usage + invoices export as CSV (text/csv, attachment).

## Common mistakes

- Enforcing the cap only in a handler read, not at the accept gate (must be
  impossible-by-construction, not advisory).
- Deleting/stopping running services at the cap — the cap pauses NEW provisioning
  only; state is always kept (US-11.5).
- A cap number that differs from the shown MTD — the enforced spend MUST be the
  same arithmetic the overview/invoice show (one arithmetic everywhere).
- Hand-writing the export types instead of generating from openapi.

## Outcome

The flagship hard spend cap (F9) is enforced **at the estimate-accept gate**, so
crossing it is impossible by construction. `budgets(org_id, limit_cents,
alert_thresholds)` stores the bound (NULL = uncapped). `setBudget`
(`PUT /orgs/{org}/billing/budget`, `billing.manage_payment`) upserts it;
`getBillingOverview` reports mtd + the plan/resources split + the budget with
`used_percent`.

**Enforcement** (`provisioning.enforceBudget`, called before `est.Accept` so a
capped-out create never burns the one-shot estimate): it projects the org's
committed **monthly run-rate** — plan fee + Σ active services' `monthly_estimate_cents`
(the new `SumOrgMonthlyEstimate` query, everything but `deleting`, conservative)
— plus this service's monthly cost, and refuses at the **API layer** (409
problem+json) with the arithmetic shown (`$current + $this = $projected > $cap`)
when it would cross. Uncapped orgs are untouched; **running services are never
stopped or deleted** — the cap pauses new provisioning only (US-11.5).

*Design note (one arithmetic, two honest views):* the cap projects the **monthly
run-rate** (a forecast — the "$383 + $99 = $482" grammar), while the overview's
`mtd_cents` is **actual accrued** spend so far this month. Both are exact and
explainable; they are different views (forecast vs actual) by design, not a
discrepancy.

**CSV exports** (`exportUsage`, `exportInvoices`) stream `text/csv` (stdlib
`encoding/csv`, `Content-Disposition: attachment`) — the same B2/B3 rows.
Registered pre-strict (a raw body, not typed JSON — the SSE/testWebhook pattern);
documented in the contract but out of the strict include list. **PDF is
deferred** (owner-ruled: CSV now, PDF a follow-up — frozen-stack dependency).

Verified against real Postgres: set a $1 cap → the overview reports it → a dev
Postgres estimate (~$29) is refused at accept with the math (409, `$` shown) and
the estimate is NOT burned → raising the cap lets the SAME estimate provision →
null removes the cap → both CSV exports stream their headers + rows. The
endpoint-permission coverage test gained `billing.manage_payment`.
