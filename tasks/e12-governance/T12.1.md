## Outcome

The four contract ops (createPolicy, listPolicies, getPolicy, updatePolicy) are
live on the strict server. A migration extends the T2.4 `policies` table with
`version`, the structured `rule`, `description`, the warn-first `enforce_from`
date, and `last_change_event`; a new append-only `policy_versions` table retains
every version so promote/revert is audited, not reconstructed.

Governed-resource contract (ADR-0006): every op authorizes through the
Authorizer under `policy.manage`; get/update are keyed by policy id and load the
row first, hiding a foreign org's policy as a 404 (never a 403 existence leak).
Each create/update emits a `policy.created`/`policy.updated` event to the
append-only spine and stamps its id back as `last_change_event` (G7);
`violation_count_30d` is read from the spine (denials attributed to the key over
30 days — the warn-mode telemetry that makes promote-to-enforce a data-backed
click, G12). Enforcement vocabulary is per-key: `ai-assistant` keeps
enabled|opt_in|disabled; rule policies use warn|enforce with a **warn-first**
default (G9). `?dry_run=true` returns a `PolicyImpact` (conflicts as a checklist
with resolutions, members affected) without persisting — the governance analog
of estimate-before-provision (G11); a real same-scope same-key conflict is a
409 checklist-with-fixes, refused before any write so the spine never records a
create that didn't happen.

Finding: the openapi `updatePolicy` body carries `config` but not `rule`, while
`createPolicy` carries `rule` — update patches enforcement/config/enforce_from;
rule edits go through the authoring create path. Recorded, not improvised.
