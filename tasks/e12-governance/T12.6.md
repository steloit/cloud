## Goal

Dashboards (DB8): SCOPE (org | project:prj_…) orthogonal to VISIBILITY
(personal | org | restricted). Scope decides WHAT data a dashboard reads;
visibility decides WHO sees the object. Dashboards READ, never provision.

## Read first

- openapi.yaml /orgs/{org}/dashboards + /dashboards/{dash}(/widgets) — the six
  operations; Dashboard/Widget/Visibility schemas.
- rbac/matrix.csv: dashboard.create (all roles), dashboard.share_org (billing N).
- docs/product/06-observe/*.md DB8 — scope ⊥ visibility; project-scoped born
  filtered; org-wide renders only viewer-accessible projects and says so.

## Approach

- Migration: dashboards (scope text, visibility check, owner_id, prebuilt,
  layout jsonb) + dashboard_widgets (source/query/viz/pos, checked enums).
- Handlers in the provisioning module (it already owns projectScoped +
  memberOrg + requireOrg — the exact scope/membership fencing dashboards need).
- Two independent gates: VISIBILITY (dashboardVisibleTo — personal/restricted =
  owner-only, org = any member) and SCOPE (a project-scoped dashboard is born
  filtered — create/read require project access, cross-org project rejected).
- create: personal needs dashboard.create; shared (org/restricted) needs
  dashboard.share_org (billing denied). Edit/delete/addWidget: owner or a
  share-org member on a shared dashboard.

## Acceptance criteria

- [x] project-scoped born filtered: a project-scoped dashboard requires project
  access to create and read; a cross-org project scope is rejected.
- [x] visibility ⊥ scope: a member sees org-visible dashboards, never another
  member's personal one (list omits + direct GET 404s); billing role can make a
  personal dashboard but not an org-shared one (403).
- [x] CRUD + widgets roundtrip (create → addWidget → GET renders → PATCH rename
  → DELETE → 404).

## Out of scope / findings

- "org-wide renders only viewer-accessible projects and says so": the DATA-side
  filtering + the "and says so" annotation is a render/data-plane concern (the
  Dashboard schema has no filtered-indicator field) — belongs to widget-query
  execution (later observe task). The backend enforces the object-model axes.
- `restricted` visibility is treated as owner-only (no restricted-share member
  surface exists in the contract yet).
- Dashboards live in the provisioning module for helper reuse, not a new
  observe package — recorded so a future observe module can claim them.

## Related

DB8 · rbac two-layer (matrix ceiling) · projectScoped (born-filtered reuse).

## Outcome

Six-endpoint CRUD with the DB8 orthogonality enforced as two independent gates:
`dashboardVisibleTo` (the visibility axis) and `requireScopeAccess` /
`projectScoped` (the scope axis, born-filtered). The integration tests prove
both axes independently — a developer member sees org dashboards but neither
lists nor GETs another member's personal one (404), a project scope is rejected
cross-org and accepted in-org, and the billing role (dashboard.create=Y,
dashboard.share_org=N) can make a personal dashboard but is 403'd on an
org-shared one. The coverage tripwire caught the perm-variable indirection
(dashboard.create was invisible to the literal scanner) → both permission
literals now sit at the requireOrg call site. Findings recorded: the data-side
"renders only viewer-accessible projects and says so" is a later render-plane
task (no schema field for the annotation), restricted=owner-only until a
share-member surface exists, and the provisioning-module home is a reuse call.
